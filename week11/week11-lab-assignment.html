Week 11 Lab — Incident Detection & Response

CS 55D: Security in Amazon Web Services  ·  Foothill College  ·  150 pts

Objective: Last week you set up monitoring for configuration drift, performance, and vulnerabilities — all inward-facing. This week, someone is doing something bad. An employee uploads sensitive data. A suspicious file lands in the photo bucket. A Lambda dependency has a known vulnerability. Set up Macie, GuardDuty, and Inspector to detect these threats, aggregate all findings in Security Hub, and automate alerting via EventBridge.

What changes this week: A new image-validation Lambda is deployed that uses Pillow to verify uploaded files are real images. This Lambda has a deliberately outdated dependency that Inspector will flag. Macie, GuardDuty, Security Hub, and EventBridge are all enabled for the first time.

Scenario this week: You play both sides — first you build the detection infrastructure (Macie, GuardDuty, Inspector, Security Hub, EventBridge), then you simulate the incidents (uploading PII and a suspicious file) and watch your own detections catch them.

Pre-flight checklist

Run the pre-flight script from CloudShell before starting:

cd ~
git -C aws-security-course pull

The script verifies your Week 10 environment is intact: CloudWatch alarms, AWS Config recorder and rules, Inspector enabled, Lambda function, S3 bucket, and the SNS topic. Address any errors before proceeding.

Part 1 Deploy the image validator Lambda

The Photo Viewer accepts file uploads from premium users, but it never checks whether the uploaded file is actually an image. Someone could rename malware.exe to vacation.jpg and upload it. Deploy a Lambda function that triggers on every S3 upload and uses the Pillow library to verify the file is a valid image.

Step 1Download the validator Lambda zip

The deployment package is pre-built in the course repository. Download it to your local machine — you will upload it to Lambda in the next step.

Open the course repo on GitHub and navigate to photoviewer/week11/image-validator.zip. Click the Download raw file button (down-arrow icon) to save the zip locally.

This zip contains a Python Lambda function (image_validator.py) and the Pillow 9.5.0 library. The function uses Image.open() to verify uploaded files are valid images.

Alternatively, if you have already cloned the course repo in CloudShell:

cd ~/aws-security-course/photoviewer/week11/
ls -lh image-validator.zip

Then use the CloudShell Actions → Download file menu to pull image-validator.zip down to your local machine.

Why Pillow 9.5.0? This version has known CVEs (including CVE-2023-50447, arbitrary code execution, CVSS 8.1). The vulnerable code paths are in ImageMath.eval — a function the validator never calls. But Inspector flags the package version, not the code paths your function uses. This mirrors real production environments where dependencies carry vulnerabilities in code you never invoke.

Step 2Create the Lambda function

Go to Lambda → Create function.

  • Function name: photoviewer-image-validator
  • Runtime: Python 3.11 (Pillow 9.5.0 requires 3.11 — it predates Python 3.12)
  • Execution role: Create a new role with basic Lambda permissions

After creation, upload the deployment package:

  • Go to Code → Upload from → .zip file
  • Upload image-validator.zip

Update the handler (the zip uses image_validator.py, not Lambda’s default lambda_function.py):

  • Scroll down to Runtime settings → Edit
  • Change Handler from lambda_function.lambda_handler to image_validator.lambda_handler
  • Click Save

Editor warning is expected. After uploading the zip, the Code tab will show “The editor could not be opened because the file was not found.” This is normal — the zip (3.7 MB) exceeds Lambda’s 3 MB inline editor limit. The function is deployed correctly; you just cannot view the code in the browser editor.

Add permissions to the Lambda execution role:

  • Go to Configuration → Permissions → click the role name
  • In IAM, choose Add permissions → Create inline policy → JSON
  • Paste the following policy, then click Next → name it photoviewer-validator-s3 → Create policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObjectTagging"
      ],
      "Resource": "arn:aws:s3:::photoviewer-[your-account-id]/*"
    },
    {
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "*"
    }
  ]
}

Replace photoviewer-[your-account-id] with your actual bucket name (e.g. photoviewer-644094189785).

Add the validator role to the KMS data key policy:

  • Go to KMS → Customer managed keys → photoviewer-data-key → Key policy
  • Scroll to Key users → Add
  • Search for validator and select the photoviewer-image-validator execution role
  • Click Add

Verify the grant landed: after adding the role, scroll the key policy and confirm it now appears under "Allow use of the key". You'll repeat this grant for Macie, GuardDuty, and the quarantine role later this week — verify each one the same way.

Don't see the visual editor view in KMS? This can happen if you have ever manually edited the data-key policy (for example, during the Week 8 revocation exercise) — the console then shows only the raw JSON policy view, with no Key users → Add button. Your key still works; this is expected. To restore the KMS visual editor, do the following:

  1. Open KMS → Customer managed keys → photoviewer-data-key → Key policy. Copy your main Lambda role ARN (the one under "Allow use of the key") into a scratch note — you'll need it in step 4.
  2. Open photoviewer-infra-key → Key policy → Switch to policy view, select the entire policy document, and copy it.
  3. Go back to photoviewer-data-key → Key policy → Edit, delete everything in the box, and paste the infra-key policy you just copied.
  4. The pasted policy names your authorizer role in two places — under "Allow use of the key" and under "Allow attachment of persistent resources". Replace the authorizer ARN with your main Lambda role ARN from step 1 in both places.
  5. Click Save changes and reload the page.

The visual editor (Key administrators / Key users, with the Add button) should now be back. Continue the lab normally, adding the validator, Macie, GuardDuty, and quarantine roles with Key users → Add. A short walkthrough video is also posted in the Week 11 announcement.

Least privilege + KMS dual authorization. The validator needs GetObject to download the file, PutObjectTagging to write validation tags, and kms:Decrypt because the bucket uses SSE-KMS with photoviewer-data-key (from the Week 8 encryption lab). Remember: KMS requires authorization from both the IAM policy and the key policy. The IAM policy alone is not enough — the role must also appear in the key policy.

Step 3Configure S3 event trigger

Go to S3 → your Photo Viewer bucket → Properties → Event notifications → Create event notification.

  • Event name: image-upload-validation
  • Prefix: photos/
  • Event types: s3:ObjectCreated:*
  • Destination: Lambda function → photoviewer-image-validator

Every file uploaded to the photos/ prefix will now trigger the validator. Note: this lab points the trigger (and the malware scan you configure later) at photos/ for simplicity — you will upload the test files there manually. In the app's real flow, user uploads land under uploads/; production would cover that prefix too (or the whole bucket).

Step 4Test the validator

Upload two files to photos/ via the S3 console:

  • Test 1: Upload a real JPEG photo. After a few seconds, check the object’s tags (S3 → object → Properties → Tags). You should see validation: PASSED and tags for image dimensions.
  • Test 2: Create a text file, rename it to suspicious.jpg, and upload it. Check tags — you should see validation: CAUTION. The .jpg extension does not fool the validator — Pillow reads the actual file bytes and fails because the content is ASCII text, not a valid image format.

Part 3 Macie — detecting sensitive data in uploads

Imagine a support engineer troubleshooting a customer issue drops a text file into the Photo Viewer’s S3 bucket. The file happens to contain a customer’s Social Security number and credit card number. The file is encrypted at rest (KMS) and access-controlled (presigned URLs) — but nobody knows the content is sensitive. Encryption protects confidentiality; Macie detects sensitive content. You will simulate this scenario.

Step 6Enable Macie

Go to Amazon Macie → Get started → Enable Macie.

Macie starts a 30-day free trial. It automatically discovers S3 buckets in the account.

Macie needs to decrypt objects in the KMS-encrypted bucket. Add the Macie service-linked role to the data key policy:

  • Go to KMS → Customer managed keys → photoviewer-data-key → Key policy
  • Scroll to Key users → Add
  • Search for macie and select AWSServiceRoleForAmazonMacie
  • Click Add

Week 8 keeps cascading. Every new service that reads objects from the KMS-encrypted bucket needs to be added to the key policy. This is the operational cost of customer-managed keys — you get fine-grained control over who can decrypt, but you must explicitly grant access to each new principal. Without this step, Macie can see that customer-data.txt exists but cannot read its contents to find the PII.

Step 7Upload sensitive data (simulate the incident)

Go to S3 → Photo Viewer bucket → photos/ and upload a text file named customer-data.txt with the following content:

Customer: Jane Doe
SSN: 123-45-6789
Credit Card: 4111-1111-1111-1111
Notes: Testing upload for support case #4472

This simulates a careless employee dropping PII into a bucket that is not designed for sensitive data.

Step 8Create a discovery job

Go to Macie → S3 buckets → Create job.

Bucket not showing up? Macie needs a minute or two to inventory the S3 buckets in your account after being enabled. Click the refresh button or wait and try again.

  • Select the Photo Viewer bucket
  • Job type: One-time job
  • Managed data identifiers: Leave defaults (includes SSN, credit card numbers, and other PII patterns)
  • Job name: photoviewer-pii-scan

Click Submit. The job will scan all objects in the bucket, including the customer-data.txt file you just uploaded.

Step 9Wait for Macie and review findings

Macie processing takes 5–15 minutes. While waiting, proceed to Part 4 (GuardDuty) and come back.

When complete, go to Macie → Findings. Macie should flag customer-data.txt with a finding for the Social Security number.

Note: Macie will not flag the credit card number — 4111-1111-1111-1111 is whitelisted as a card-issuer test value, so Macie does not generate a finding for it (see the “Credit card number” entry in the Macie financial data identifiers reference). An SSN-only finding is the correct result.

Click into the finding. Note the S3 object path, the PII type, and the severity.

✓ Verify

Macie detected PII in the uploaded file. The finding shows the S3 object, the type of sensitive data (SSN), and the severity level.

Part 4 GuardDuty — detecting malware in uploads

Now simulate a different incident: a file received from a customer turns out to contain malware. GuardDuty Malware Protection for S3 scans newly uploaded objects and flags malicious content.

Step 10Enable GuardDuty

Go to Amazon GuardDuty → Get started → Enable GuardDuty.

GuardDuty starts a 30-day free trial. It begins analyzing CloudTrail events, VPC flow logs, and DNS query logs for suspicious activity.

Step 11Enable Malware Protection for S3

Go to GuardDuty → Protection plans → Malware Protection for S3. Enable it for the Photo Viewer bucket.

  • Select the Photo Viewer bucket
  • Object prefix: photos/

The setup wizard creates an IAM role for GuardDuty to read objects from the bucket. GuardDuty needs to decrypt objects in the KMS-encrypted bucket. Add the Malware Protection role to the data key policy:

  • Go to KMS → photoviewer-data-key → Key policy
  • Scroll to Key users → Add
  • Search for guard and select the role starting with GuardDutyS3MalwareScanRole
  • Click Add

GuardDuty will now scan every new object uploaded to the photos/ prefix.

Wait 2–3 minutes before uploading the test file in the next step. Malware Protection for S3 needs a moment to fully activate after enabling. If you upload immediately, the scan may not trigger.

Step 12Upload a suspicious file (simulate the incident)

Create the EICAR test file. This is a standardized anti-malware test string — not actual malware, but every malware scanner recognizes it as a test indicator.

Create a file named test-photo.jpg with exactly this content:

X5O!P%@AP[4\PZX54(P^)7CC)7}$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!$H+H*

Upload it to S3 → Photo Viewer bucket → photos/.

After uploading, go to GuardDuty → Malware scans to confirm a scan was triggered. It may take a few minutes for the scan to appear and complete.

Note: The EICAR string is an industry-standard test pattern. It is not malware and cannot harm your system. Every anti-malware product — including GuardDuty Malware Protection — is designed to recognize and flag it.

Copy the string carefully: 68 characters, straight quotes only (no smart quotes), and the backslash \ intact. GuardDuty matches the EICAR signature and tolerates minor whitespace — a trailing newline is fine (the test files in the course repo have one and are detected reliably) — but altered characters or smart quotes will make the scan come back clean, and the rest of the lab will fail with no obvious cause. If your scan does not flag the file, copy the string directly from eicar.org rather than from this page, and confirm your editor did not add a trailing newline.

No scan triggered? Delete the file from S3 and re-upload it. Malware Protection only scans on new PutObject events — it does not scan existing objects.

Step 13Review GuardDuty findings

Wait a few minutes. Go to GuardDuty → Findings.

GuardDuty should generate a finding for the EICAR file. Look for a finding type related to malware detection — it will include the S3 object path, the threat name, and the severity.

Note: EICAR (S3 malware) findings from GuardDuty are always High severity — malware is a binary verdict, so no uploaded file will produce a Low or Medium finding. To see Low/Medium severity findings, use the sample findings below.

Generate sample findings for additional context: GuardDuty → Settings → Generate sample findings. This produces realistic threat indicators instantly — credential exfiltration, unusual API activity, reconnaissance. Browse three findings of different severity levels.

✓ Verify

GuardDuty detected the EICAR test file as malware. Sample findings show the breadth of threats GuardDuty monitors — credential compromise, unusual API calls, network reconnaissance.

Part 5 Security Hub — single pane of glass

You now have findings scattered across four dashboards: Inspector (Pillow CVE), Macie (PII in uploads), GuardDuty (malware), and Config (from last week). Security Hub aggregates them all into one place.

Step 14Enable Security Hub

Go to AWS Security Hub → Go to Security Hub. The onboarding page shows several options:

  • Delegated administrator account: Skip this — it is for AWS Organizations multi-account setups. Leave your account ID as-is.
  • Delegated administrator policy: Leave the default (Update delegation policy for me).
  • Check “I confirm that I have reviewed the policy”
  • Under Account enablement, check “Enable Security Hub for my account”
  • Click Configure

Security Hub enables the AWS Foundational Security Best Practices standard by default, which adds automated compliance checks on top of findings from other services.

Step 15Wait for findings to aggregate

Security Hub takes a few minutes to start showing findings. Wait ~5 minutes, then go to Security Hub → Findings.

Don’t wait here. Aggregation can take 10–15 minutes or longer. Proceed with Parts 6 and 7, then come back to Security Hub at the end to take your screenshot.

Seeing only “…should be enabled” checks (IAM, CloudTrail, KMS…) and not your Inspector / Macie / GuardDuty findings? That is expected, and you have done this step correctly. Two reasons:

  • Security Hub only ingests findings created after it is enabled — it does not backfill older ones. You enable it here in Step 14, after most of your findings were already generated, so those are not pulled in retroactively.
  • Services do not all forward every finding by default. For example, Macie does not publish sensitive-data findings (like the SSN) to Security Hub unless you change its publication settings, and a Malware Protection scan result is its own event type that does not reliably appear as a GuardDuty Finding.

So the goal of this step is simply to confirm that Security Hub is enabled and aggregating findings into one normalized (ASFF) dashboard — the standards/compliance findings demonstrate that. For your screenshot, Security Hub enabled and showing its aggregated Findings list is sufficient. If you also see detection findings from Inspector or GuardDuty, that is a bonus — it is not required, and you will not lose points if they do not appear. (If Security Hub looks completely empty, you probably checked too soon — wait 10–15 minutes after Step 19 and refresh.)

Every finding Security Hub receives is normalized to the AWS Security Finding Format (ASFF) with consistent severity scores, resource identifiers, and remediation recommendations — which is what makes one-dashboard triage possible.

Part 6 Quarantine Lambda

Detection without response is just a dashboard nobody checks at 3 AM. Build a quarantine Lambda that moves flagged files to a quarantine/ prefix automatically. You will wire it to EventBridge in Part 7.

Step 16Create the quarantine Lambda

Go to Lambda → Create function.

  • Function name: photoviewer-quarantine
  • Runtime: Python 3.12
  • Execution role: Create a new role with basic Lambda permissions

Paste the following code:

import json
import boto3

s3 = boto3.client('s3')

def lambda_handler(event, context):
    print(f'EVENT: {json.dumps(event)}')
    detail = event.get('detail', {})

    # Extract bucket and key from the Malware Protection scan result
    s3_object = detail.get('s3ObjectDetails', {})
    bucket = s3_object.get('bucketName', '')
    key = s3_object.get('objectKey', '')

    if not bucket or not key:
        print(f'Could not extract bucket/key from event: {json.dumps(event)}')
        return {'statusCode': 400, 'body': 'Missing S3 details'}

    # Skip files already in quarantine
    if key.startswith('quarantine/'):
        print(f'SKIP: {key} is already quarantined')
        return {'statusCode': 200, 'body': 'Already quarantined'}

    # Move to quarantine
    quarantine_key = f'quarantine/{key.split("/")[-1]}'
    print(f'Attempting: copy s3://{bucket}/{key} to s3://{bucket}/{quarantine_key}')

    s3.copy_object(
        Bucket=bucket,
        CopySource={'Bucket': bucket, 'Key': key},
        Key=quarantine_key
    )
    s3.delete_object(Bucket=bucket, Key=key)

    print(f'QUARANTINED: {key} -> {quarantine_key}')

    return {
        'statusCode': 200,
        'body': json.dumps({
            'action': 'quarantined',
            'original': key,
            'quarantine': quarantine_key
        })
    }

Click Deploy to save the function.

Create an inline policy for the Lambda execution role (same approach as Step 2 — Add permissions → Create inline policy → JSON, name it photoviewer-quarantine-s3). The quarantine function copies the file to quarantine/ then deletes the original. CopyObject is a compound operation that requires multiple S3 permissions (read source, write destination, copy tags, copy metadata) plus KMS permissions for the encrypted bucket:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:*",
      "Resource": "arn:aws:s3:::photoviewer-[your-account-id]/*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "kms:Decrypt",
        "kms:GenerateDataKey"
      ],
      "Resource": "*"
    }
  ]
}

Replace photoviewer-[your-account-id] with your actual bucket name.

Why s3:*? In the validator Lambda (Step 2), we scoped permissions to specific actions. Here, CopyObject internally requires a combination of read, write, tagging, and metadata permissions that is difficult to enumerate precisely. Scoping to s3:* on a single bucket is a pragmatic tradeoff — the bucket-level scope is the meaningful security boundary.

Add the quarantine role to the KMS data key policy (same as Step 2 — KMS → photoviewer-data-key → Key policy → Key users → Add, search for quarantine and select the execution role).

Part 7 EventBridge — automated alerting and remediation

A high-severity GuardDuty finding fires at 3 AM. Nobody is watching the Security Hub dashboard. EventBridge watches for you — it sends an alert via SNS and triggers the quarantine Lambda automatically. You need two rules because GuardDuty emits two different event types: standard findings and Malware Protection scan results.

Step 17Create an EventBridge notification rule

Go to Amazon EventBridge. On the landing page, select EventBridge Rule with event pattern and click Create rule.

  • Name: guardduty-high-severity-alert
  • Event bus: default

The Enhanced builder opens. On the Events tab, select GuardDuty → GuardDuty Finding from the left panel. It appears under Triggering Events.

In the Event pattern panel on the right, click Code to switch to JSON view. Replace the pattern with:

{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": [{ "numeric": [">=", 7] }]
  }
}

This matches any GuardDuty finding with severity 7 or higher (High and Critical).

Click the Targets tab. Drag SNS topic into the Targets area (or click to add), then select the SNS topic you created for billing alerts in Week 1. Leave all other settings as defaults.

Click Create (top right).

Step 18Create an EventBridge rule for malware quarantine

Malware Protection for S3 emits a different event type — GuardDuty Malware Protection Object Scan Result — with a different JSON structure than standard findings. It needs its own rule with two targets: SNS for notification and the quarantine Lambda for automated remediation.

Go to Amazon EventBridge → Rules → Create rule (same Enhanced builder as Step 17).

  • Name: guardduty-malware-quarantine
  • Event bus: default

On the Events tab, do not select from the left panel this time — the malware scan event type is not listed. Instead, go straight to the Event pattern panel on the right, click Code, and paste:

{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Malware Protection Object Scan Result"],
  "detail": {
    "scanResultDetails": {
      "scanResultStatus": ["THREATS_FOUND"]
    }
  }
}

A “Discrepancy detected” dialog may appear. Check “Overwrite Triggering events with the event source and detail type defined in the Event pattern (filter)” and click Accept change. This tells EventBridge to use your JSON pattern.

Click the Targets tab and add two targets:

  • Target 1: SNS topic — same billing alerts topic from Step 17
  • Target 2: Lambda function → photoviewer-quarantine

Click Create.

Step 19Test the full loop

Upload a new EICAR test file to photos/ (name it malware-test.jpg). This is the same EICAR content from Step 12, but a fresh upload is needed — GuardDuty only scans on new PutObject events, and the Step 12 upload happened before EventBridge and the quarantine Lambda existed.

When the scan result fires, the guardduty-malware-quarantine rule matches it → SNS sends an email and the quarantine Lambda runs. Don't expect a second email from guardduty-high-severity-alert: a Malware Protection scan result is its own event type and does not reliably generate a separate high-severity GuardDuty Finding — the high-severity email you saw earlier came from the sample findings in Step 13. One email here means it worked.

  • guardduty-high-severity-alert matches the high-severity finding → SNS sends an email
  • guardduty-malware-quarantine matches the scan result → SNS sends an email AND the quarantine Lambda moves the file from photos/ to quarantine/

Check the S3 bucket. The file should no longer be in photos/. It should be in quarantine/. Check your email for the SNS notifications.

Troubleshooting: If the file does not move, check the quarantine Lambda’s CloudWatch Logs for errors. The most common issue is missing S3 or KMS permissions on the Lambda execution role.

✓ Verify

The full detection-to-remediation loop works: GuardDuty detects malware → EventBridge matches → SNS sends an alert → Lambda quarantines the file. No human intervention required.

Cleanup

Week 12 does not depend on any services from this lab — or on Config or Inspector from Week 10. Disable or delete everything below to avoid charges. Keep CloudTrail and your CloudWatch alarms — CloudTrail is required for Week 12, and the alarms cost nothing.

  1. Disable Macie — Go to Macie → Settings → Disable Macie. Free trial runs for 30 days, then charges begin.
  2. Disable GuardDuty Malware Protection for S3 — Go to GuardDuty → Protection plans → Malware Protection for S3. Select the bucket plan and click Disable.
  3. Disable GuardDuty — Go to GuardDuty → Settings → Suspend → Disable GuardDuty.
  4. Disable Security Hub — Go to Security Hub → Settings → General → Disable Security Hub.
  5. Delete the four Config rules — Go to Config → Rules and delete s3-default-encryption-kms, s3-bucket-public-read-prohibited, cloud-trail-encryption-enabled, and iam-root-access-key-check. This is the deletion the Week 10 lab told you to hold off on — now is the right time, and the Week 10 demo video (~30:00) shows the exact flow. Do this after disabling Security Hub, so its auto-created securityhub-* rules are already gone.
  6. Stop the Config recorder — Go to Config → Settings → Edit and turn recording off. Config charges per configuration item recorded; with the course winding down there is nothing left for it to watch.
  7. Disable Inspector — Go to Inspector → Settings → General → Deactivate Inspector. Its 15-day free trial converts to real charges, and Week 12 does not use it.
  8. Delete EventBridge rules — Go to EventBridge → Rules. Delete both guardduty-high-severity-alert and guardduty-malware-quarantine. (Remove targets first, then delete the rule.)
  9. Delete Lambda functions — Go to Lambda → Functions. Delete photoviewer-image-validator and photoviewer-quarantine.
  10. Remove S3 event notification — Go to S3 → Photo Viewer bucket → Properties → Event notifications. Delete the image-upload-validation notification.
  11. Delete test files — Remove suspicious.jpg, test-photo.jpg, malware-test.jpg, customer-data.txt, and any test photos from both photos/ and quarantine/ prefixes.

Reflection Questions
Q1 — encryption vs detection10Encryption protects confidentiality — unauthorized users cannot read the data. Macie detects sensitive content — it identifies what kind of data is present (PII, credentials, etc.). Encryption does not prevent authorized services (like Macie) from reading and scanning the data. Different problems, different tools.
Q2 — upgrade despite unused code path9Yes, upgrade. Future code changes might use the vulnerable function. Automated compliance tools flag the version regardless. An attacker who gains code execution could import and call any function in the package. Defense in depth means not relying on one layer of protection.
Q3 — multi-service incident9Example: An attacker exploits the Pillow CVE (Inspector flagged it) to execute code, disables S3 encryption (Config detects drift), and exfiltrates data (GuardDuty detects unusual API calls). One incident, three services, three perspectives.
Q4 — notification vs remediation12Notification (SNS) tells a human something happened — response depends on someone reading the email and acting. Remediation (Lambda quarantine) acts immediately without waiting. Tradeoff: automated remediation can cause false-positive outages (quarantining a legitimate file). Start with notification, graduate to remediation as confidence in detection rules grows.
