Week 11 Lab — Incident Detection & Response

CS 55D: Security in Amazon Web Services  ·  Foothill College  ·  100 pts

Objective: Last week you set up monitoring for configuration drift, performance, and vulnerabilities — all inward-facing. This week, someone is doing something bad. An employee uploads sensitive data. A suspicious file lands in the photo bucket. A Lambda dependency has a known vulnerability. Set up Macie, GuardDuty, and Inspector to detect these threats, aggregate all findings in Security Hub, and automate alerting via EventBridge.

What changes this week: A new image-validation Lambda is deployed (by Jerry) that uses Pillow to verify uploaded files are real images. This Lambda has a deliberately outdated dependency that Inspector will flag. Macie, GuardDuty, Security Hub, and EventBridge are all enabled for the first time.

Roles this week: Jerry (security/infra engineer) builds the detection infrastructure — deploys the validator Lambda, enables Macie, GuardDuty, Security Hub, and EventBridge. Tom (customer support engineer) creates the incidents — uploads a file with PII and a suspicious file. Jerry’s infrastructure catches Tom’s mistakes.

Pre-flight checklist

Run the pre-flight script from CloudShell before starting:

cd ~
git -C aws-security-course pull
bash aws-security-course/photoviewer/week11/week11-preflight.sh

The script verifies your Week 10 environment is intact: CloudWatch alarms, AWS Config recorder and rules, Inspector enabled, Lambda function, S3 bucket, and the SNS topic. Address any errors before proceeding.

Part 1 Deploy the image validator Lambda (Jerry)

The Photo Viewer accepts file uploads from premium users, but it never checks whether the uploaded file is actually an image. Someone could rename malware.exe to vacation.jpg and upload it. Jerry deploys a Lambda function that triggers on every S3 upload and uses the Pillow library to verify the file is a valid image.

Step 1Download the validator Lambda zip

The deployment package is pre-built in the course repository. From CloudShell:

cd ~/aws-security-course/photoviewer/week11/
ls -lh image-validator.zip

This zip contains a Python Lambda function (image_validator.py) and the Pillow 9.5.0 library. The function uses Image.open() to verify uploaded files are valid images.

Why Pillow 9.5.0? This version has known CVEs (including CVE-2023-50447, arbitrary code execution, CVSS 8.1). The vulnerable code paths are in ImageMath.eval — a function the validator never calls. But Inspector flags the package version, not the code paths your function uses. This mirrors real production environments where dependencies carry vulnerabilities in code you never invoke.

Step 2Create the Lambda function

Go to Lambda → Create function.

  • Function name: photoviewer-image-validator
  • Runtime: Python 3.12
  • Execution role: Create a new role with basic Lambda permissions

After creation, upload the deployment package:

  • Go to Code → Upload from → .zip file
  • Upload image-validator.zip
  • Set the handler to image_validator.lambda_handler

Add permissions to the Lambda execution role:

  • Go to Configuration → Permissions → click the role name
  • Attach the managed policy AmazonS3FullAccess (in production you would scope this down — for the lab this is sufficient)
Step 3Configure S3 event trigger

Go to S3 → your Photo Viewer bucket → Properties → Event notifications → Create event notification.

  • Event name: image-upload-validation
  • Prefix: photos/
  • Event types: s3:ObjectCreated:*
  • Destination: Lambda function → photoviewer-image-validator

Every file uploaded to the photos/ prefix will now trigger the validator.

Step 4Test the validator

Upload two files to photos/ via the S3 console:

  • Test 1: Upload a real JPEG photo. After a few seconds, check the object’s tags (S3 → object → Properties → Tags). You should see validation: PASSED and tags for image dimensions.
  • Test 2: Create a text file, rename it to suspicious.jpg, and upload it. Check tags — you should see validation: CAUTION.
✓ Verify

The real photo is tagged validation: PASSED. The renamed text file is tagged validation: CAUTION. The Lambda is actively validating every upload.

S3 object tags showing validation: PASSED on the real photo
S3 object tags showing validation: CAUTION on the fake photo
Part 2 Inspector — vulnerability in the validator (Jerry)

Jerry deployed the image validator using Pillow 9.5.0. Inspector — which has been running since last week — will scan the new Lambda’s deployment package and find the known CVEs.

Step 5Check Inspector findings

Go to Inspector → Findings → By Lambda function. Find photoviewer-image-validator.

Inspector should report findings for Pillow 9.5.0. Look for:

  • CVE-2023-50447 — Arbitrary Code Execution via ImageMath.eval (CVSS 8.1, High)
  • CVE-2023-44271 — Denial of Service via ImageFont (CVSS 7.5, High)

Click into a finding. Note the CVE ID, the CVSS score, the affected package and version, and the link to the NIST NVD entry. In production, this finding would trigger a remediation workflow — update Pillow to the latest version and redeploy.

✓ Verify

Inspector has found at least one CVE in the Pillow package bundled with photoviewer-image-validator. The finding includes severity, affected version, and remediation guidance.

Inspector finding showing CVE details for Pillow in photoviewer-image-validator
Part 3 Macie — Tom uploads sensitive data

Tom is troubleshooting a customer support issue and needs to test a file upload. He drops a text file into the Photo Viewer’s S3 bucket. The file happens to contain a customer’s Social Security number and credit card number. The file is encrypted at rest (KMS) and access-controlled (presigned URLs) — but nobody knows the content is sensitive. Encryption protects confidentiality; Macie detects sensitive content.

Step 6Enable Macie (Jerry)

Go to Amazon Macie → Get started → Enable Macie.

Macie starts a 30-day free trial. It automatically discovers S3 buckets in the account.

Step 7Create a discovery job (Jerry)

Go to Macie → S3 buckets → Create job.

  • Select the Photo Viewer bucket
  • Job type: One-time job
  • Managed data identifiers: Leave defaults (includes SSN, credit card numbers, and other PII patterns)
  • Job name: photoviewer-pii-scan

Click Submit. The job will scan all objects in the bucket.

Step 8Tom uploads sensitive data

Switching to Tom’s perspective. Go to S3 → Photo Viewer bucket → photos/ and upload a text file named customer-data.txt with the following content:

Customer: Jane Doe
SSN: 123-45-6789
Credit Card: 4111-1111-1111-1111
Notes: Testing upload for support case #4472

This simulates a careless employee dropping PII into a bucket that is not designed for sensitive data.

Step 9Wait for Macie and review findings (Jerry)

Macie processing takes 5–15 minutes. While waiting, proceed to Part 4 (GuardDuty) and come back.

When complete, go to Macie → Findings. Macie should flag customer-data.txt with findings for:

  • Social Security number detected
  • Credit card number detected

No findings? If the one-time job completed before Tom uploaded customer-data.txt, it scanned the bucket before the file existed. Go to Macie → S3 buckets → Create job and run a new one-time job on the Photo Viewer bucket.

Click into a finding. Note the S3 object path, the PII type, and the severity.

✓ Verify

Macie detected PII in the file Tom uploaded. The finding shows the S3 object, the type of sensitive data (SSN, credit card), and the severity level.

Macie finding showing PII detected in customer-data.txt — SSN and credit card number
Part 4 GuardDuty — Tom uploads a suspicious file

Tom uploads another file to help with a support case — a file he received from a customer. He does not realize it contains malware. GuardDuty Malware Protection for S3 scans newly uploaded objects and flags malicious content.

Step 10Enable GuardDuty (Jerry)

Go to Amazon GuardDuty → Get started → Enable GuardDuty.

GuardDuty starts a 30-day free trial. It begins analyzing CloudTrail events, VPC flow logs, and DNS query logs for suspicious activity.

Step 11Enable Malware Protection for S3 (Jerry)

Go to GuardDuty → Protection plans → Malware Protection for S3. Enable it for the Photo Viewer bucket.

  • Select the Photo Viewer bucket
  • Object prefix: photos/

GuardDuty will now scan every new object uploaded to the photos/ prefix.

Step 12Tom uploads a suspicious file

Create the EICAR test file. This is a standardized anti-malware test string — not actual malware, but every malware scanner recognizes it as a test indicator.

Create a file named test-photo.jpg with exactly this content:

X5O!P%@AP[4\PZX54(P^)7CC)7}$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!$H+H*

Upload it to S3 → Photo Viewer bucket → photos/.

Note: The EICAR string is an industry-standard test pattern. It is not malware and cannot harm your system. Every anti-malware product — including GuardDuty Malware Protection — is designed to recognize and flag it.

Step 13Review GuardDuty findings (Jerry)

Wait a few minutes. Go to GuardDuty → Findings.

GuardDuty should generate a finding for the EICAR file. Look for a finding type related to malware detection — it will include the S3 object path, the threat name, and the severity.

Also generate sample findings for additional context: GuardDuty → Settings → Generate sample findings. This produces realistic threat indicators instantly — credential exfiltration, unusual API activity, reconnaissance. Browse three findings of different severity levels.

✓ Verify

GuardDuty detected the EICAR test file as malware. Sample findings show the breadth of threats GuardDuty monitors — credential compromise, unusual API calls, network reconnaissance.

GuardDuty finding for the EICAR malware detection in the Photo Viewer bucket
Three sample findings of different severity levels (Low, Medium, High)
Part 5 Security Hub — single pane of glass (Jerry)

Jerry now has findings scattered across four dashboards: Inspector (Pillow CVE), Macie (PII in uploads), GuardDuty (malware), and Config (from last week). Security Hub aggregates them all into one place.

Step 14Enable Security Hub

Go to AWS Security Hub → Go to Security Hub → Enable Security Hub.

Enable the AWS Foundational Security Best Practices standard. This adds additional automated checks on top of the findings from other services.

Step 15Wait for findings to aggregate

Security Hub takes a few minutes to ingest findings from connected services. Wait ~5 minutes, then go to Security Hub → Findings.

You should see findings from multiple sources:

  • Inspector: Pillow CVE in photoviewer-image-validator
  • Macie: PII in customer-data.txt
  • GuardDuty: Malware detection + sample findings
  • Config: Any non-compliant rules from last week

All findings are normalized to the AWS Security Finding Format (ASFF) with consistent severity scores, resource identifiers, and remediation recommendations.

✓ Verify

Security Hub shows findings from at least three different sources (Inspector, Macie, GuardDuty) in a single dashboard. One place to see everything.

Security Hub dashboard showing aggregated findings from multiple services
Part 6 EventBridge — automated alerting (Jerry)

A high-severity GuardDuty finding fires at 3 AM. Nobody is watching the Security Hub dashboard. EventBridge watches for you and sends an alert via SNS.

Step 16Create an EventBridge rule

Go to Amazon EventBridge → Rules → Create rule.

  • Name: guardduty-high-severity-alert
  • Event bus: default
  • Rule type: Rule with an event pattern

Event pattern:

{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": [{ "numeric": [">=", 7] }]
  }
}

This matches any GuardDuty finding with severity 7 or higher (High and Critical).

Step 17Set the target

Target: SNS topic — select the same topic used for CloudWatch alarms and billing alerts.

Click Create rule.

Step 18Test the alert

Go to GuardDuty → Settings → Generate sample findings again. This produces findings across all severity levels.

Check your email. You should receive SNS notifications for the high-severity sample findings. The email contains the finding type, affected resource, severity, and a description.

✓ Verify

You received an email alert from EventBridge via SNS for a high-severity GuardDuty finding. At 3 AM, this would wake someone up — no dashboard-watching required.

Email notification showing a high-severity GuardDuty finding delivered via EventBridge → SNS
Part 7 Automated remediation — quarantine Lambda (Jerry)

Email notifications tell Jerry something happened. But the malicious file is still sitting in the photos/ prefix, accessible to users, while Jerry reads his email and opens the console. Automated remediation closes this gap — a Lambda function moves the flagged object to a quarantine/ prefix immediately, without waiting for a human.

Step 19Create the quarantine Lambda

Go to Lambda → Create function.

  • Function name: photoviewer-quarantine
  • Runtime: Python 3.12
  • Execution role: Create a new role with basic Lambda permissions

Paste the following code:

import json
import boto3

s3 = boto3.client('s3')

def lambda_handler(event, context):
    detail = event.get('detail', {})

    # Extract bucket and key from the Malware Protection scan result
    s3_object = detail.get('s3ObjectDetails', {})
    bucket = s3_object.get('bucketName', '')
    key = s3_object.get('objectKey', '')

    if not bucket or not key:
        print(f'Could not extract bucket/key from event: {json.dumps(event)}')
        return {'statusCode': 400, 'body': 'Missing S3 details'}

    # Move to quarantine
    quarantine_key = f'quarantine/{key.split("/")[-1]}'

    s3.copy_object(
        Bucket=bucket,
        CopySource={'Bucket': bucket, 'Key': key},
        Key=quarantine_key
    )
    s3.delete_object(Bucket=bucket, Key=key)

    print(f'QUARANTINED: {key} -> {quarantine_key}')

    return {
        'statusCode': 200,
        'body': json.dumps({
            'action': 'quarantined',
            'original': key,
            'quarantine': quarantine_key
        })
    }

Add AmazonS3FullAccess to the Lambda execution role (same as the image validator).

Step 20Create an EventBridge rule for malware scan results

The rule from Step 16 matches standard GuardDuty findings (credential compromise, unusual API calls). Malware Protection for S3 emits a different event type — GuardDuty Malware Protection Object Scan Result — with a different JSON structure. It needs its own rule.

Go to Amazon EventBridge → Rules → Create rule.

  • Name: guardduty-malware-quarantine
  • Event bus: default
  • Rule type: Rule with an event pattern

Event pattern:

{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Malware Protection Object Scan Result"],
  "detail": {
    "scanResultDetails": {
      "scanResultStatus": ["THREATS_FOUND"]
    }
  }
}

This matches any Malware Protection scan that found threats. Add two targets:

  • Target 1: SNS topic — same topic as the standard findings rule
  • Target 2: Lambda function → photoviewer-quarantine

Click Create rule.

You now have two EventBridge rules: one for standard GuardDuty findings (notification only), one for malware scan results (notification + quarantine). The malware rule has two targets — SNS tells Jerry, Lambda acts immediately.

Step 21Test the full loop

Upload a new EICAR test file to photos/ (name it malware-test.jpg).

Wait for GuardDuty Malware Protection to scan and generate a scan result (this may take several minutes). When the scan result fires:

  • EventBridge matches the guardduty-malware-quarantine rule (scan result = THREATS_FOUND)
  • SNS sends Jerry an email (notification)
  • The quarantine Lambda moves the file from photos/ to quarantine/ (remediation)

Check the S3 bucket. The file should no longer be in photos/. It should be in quarantine/.

Troubleshooting: If the file does not move, check the quarantine Lambda’s CloudWatch Logs for errors. The most common issue is missing S3 permissions on the Lambda execution role.

✓ Verify

The full detection-to-remediation loop works: GuardDuty detects malware → EventBridge matches → SNS notifies Jerry → Lambda quarantines the file. No human intervention required.

S3 bucket showing the EICAR file moved from photos/ to quarantine/
Email notification AND quarantined file — both happened automatically

Cleanup

Disable or delete resources to avoid unexpected charges:

  • Disable Macie — free trial runs for 30 days, then charges begin. Go to Macie → Settings → Disable Macie.
  • Disable GuardDuty — free trial runs for 30 days, then charges begin. Go to GuardDuty → Settings → Suspend/Disable GuardDuty.
  • Delete test files — remove suspicious.jpg (Step 4), test-photo.jpg (Step 12), malware-test.jpg (Step 21), customer-data.txt (Step 8), and any test photos uploaded in Step 4 from both photos/ and quarantine/ prefixes.
  • Keep Security Hub running — it provides ongoing visibility into your security posture across services.
  • Keep both Lambda functions — the image validator and quarantine Lambda demonstrate real detection and remediation.

Reflection Questions

Question 1

In Part 3, Tom uploaded a file containing a credit card number. The file is encrypted at rest with KMS (from the earlier encryption lab). Explain why KMS encryption did not prevent Macie from detecting the PII. What problem does encryption solve, and what problem does Macie solve?

Question 2

The image validator Lambda uses Pillow 9.5.0, which has CVE-2023-50447 (arbitrary code execution in ImageMath.eval). The validator code only calls Image.open() — it never uses ImageMath.eval. Should you still upgrade Pillow? Explain your reasoning.

Question 3

You now have findings from five services in Security Hub: CloudWatch (alarms), Config (compliance), Inspector (CVEs), Macie (PII), and GuardDuty (threats). Describe a scenario where a single incident would generate findings in at least three of these services simultaneously.

Question 4

In Part 6, EventBridge sends an SNS email notification. In Part 7, EventBridge triggers a Lambda that quarantines the file. Compare these two response strategies. When would you use notification only? When would you add automated remediation? What is the risk of automating remediation too aggressively?

Reflection Q1 — encryption vs detection8Encryption protects confidentiality — unauthorized users cannot read the data. Macie detects sensitive content — it identifies what kind of data is present (PII, credentials, etc.). Encryption does not prevent authorized services (like Macie) from reading and scanning the data. Different problems, different tools.
Reflection Q2 — upgrade despite unused code path7Yes, upgrade. Future code changes might use the vulnerable function. Automated compliance tools flag the version regardless. An attacker who gains code execution could import and call any function in the package. Defense in depth means not relying on one layer of protection.
Reflection Q3 — multi-service incident7Example: An attacker exploits the Pillow CVE (Inspector flagged it) to execute code, disables S3 encryption (Config detects drift), and exfiltrates data (GuardDuty detects unusual API calls). One incident, three services, three perspectives.
Reflection Q4 — notification vs remediation9Notification (SNS) tells a human something happened — response depends on someone reading the email and acting. Remediation (Lambda quarantine) acts immediately without waiting. Tradeoff: automated remediation can cause false-positive outages (quarantining a legitimate file). Start with notification, graduate to remediation as confidence in detection rules grows.
