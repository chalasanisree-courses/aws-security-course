Incident Detection & Response

This course builds a Photo Viewer application across twelve weeks, adding one AWS security layer per week. This page shifts from inward-facing monitoring to adversarial thinking — detecting when someone is doing something bad and responding automatically.

Learning objectives

  • Distinguish between monitoring (inward-facing) and detection (adversary-facing)
  • Identify three threat categories addressed this week: careless data exposure, malicious content, and vulnerable dependencies
  • Explain how Macie classifies sensitive data in S3 objects by scanning content patterns
  • Explain how GuardDuty detects threats by analyzing CloudTrail, VPC flow logs, DNS logs, and S3 object scans
  • Explain how Security Hub normalizes findings from multiple services into a single dashboard using ASFF
  • Describe how EventBridge event patterns enable automated response to security findings
  • Implement automated remediation by wiring a quarantine Lambda as an EventBridge target
  • Distinguish between encryption (protects confidentiality) and classification (identifies content)

1. Where we left off

The monitoring infrastructure is in place. CloudWatch watches performance. Config watches configuration. Inspector watches dependencies. Trusted Advisor provides account-level health checks. But all of this is inward-facing — checking our own work. Two problems remain:

Uploaded files are still not scanned for malicious content
▼

A user could upload a file containing credit card numbers, or an image that is actually a disguised executable. Encryption protects these files at rest, but encryption does not inspect content. Two services address this: Macie detects PII patterns (SSN, credit card numbers) and GuardDuty Malware Protection scans for malware signatures. Both are addressed this week.

No detection of adversarial behavior
▼

If someone exfiltrates IAM credentials and makes API calls from an unfamiliar IP, none of the monitoring tools from the prior week would flag it. CloudWatch sees no errors. Config sees no configuration change. Inspector sees no new vulnerability. The attacker is doing something bad — but everything looks normal from the inside. GuardDuty detects adversarial behavior by analyzing patterns across CloudTrail, VPC flow logs, and DNS queries. Addressed this week.

The shift this week: from “is our system healthy?” to “is someone doing something bad?”

Aggregation — Security Hub

After the three detection scenarios, Jerry has findings scattered across Inspector, Macie, and GuardDuty — plus Config and CloudWatch findings from the prior week. Five different dashboards. Security Hub aggregates them all.

Security Hub normalizes every finding to the AWS Security Finding Format (ASFF) — a standard schema with consistent fields for severity, resource identifiers, remediation recommendations, and compliance status. A GuardDuty malware finding and a Macie PII finding look structurally the same in Security Hub, making it possible to sort, filter, and prioritize across services.

Response — EventBridge

Security Hub shows findings in a dashboard. But dashboards require someone watching. EventBridge closes the loop by matching finding events against patterns and routing them to targets automatically.

1
Event source: GuardDuty Malware Protection scans an uploaded S3 object and publishes a scan result.
2
Event bus: The scan result is published to the default EventBridge event bus as a structured JSON event.
3
Rule matches: An EventBridge rule matches on source = aws.guardduty and scanResultStatus = THREATS_FOUND.
4
Target 1 — notification: The rule sends the event to an SNS topic. SNS delivers an email to Jerry.
5
Target 2 — remediation: The same rule triggers a quarantine Lambda that moves the flagged S3 object from photos/ to quarantine/.
6
At 3 AM: Nobody is watching the dashboard. The email arrives, and the malicious file is already quarantined. Jerry wakes up and the situation is already contained.

One rule, two targets, two response types running simultaneously. Notification tells a human; remediation acts immediately. A second EventBridge rule matches standard GuardDuty findings (credential compromise, unusual API calls) at severity ≥ 7, routing those to SNS for notification. Different event types require separate rules — but the pattern is the same. In production, automated remediation requires careful tuning — quarantining a legitimate file is a false-positive outage. Most organizations start with notifications and graduate to automated remediation as they gain confidence in their detection rules.

4. Key concepts

The threat scenarios above explain the detection services. The concepts below go deeper into the patterns that connect them.

Encryption vs classification — why KMS does not prevent Macie from reading

KMS encryption controls who can decrypt. Macie has a service-linked role with permission to call kms:Decrypt — it is an authorized reader. Encryption prevents unauthorized access (an attacker without the key). Classification identifies what kind of data is stored (PII, financial data, credentials). These are orthogonal concerns.

An analogy: a locked filing cabinet (encryption) prevents someone from opening the drawer. A classification label on the folder inside (Macie) tells authorized people that the contents are sensitive. You need both. The lock without the label means authorized users do not know to handle the file carefully. The label without the lock means anyone can access it.

ASFF — how Security Hub normalizes findings

The AWS Security Finding Format (ASFF) is a JSON schema that standardizes how findings are represented. Every finding — regardless of source — has the same fields:

FieldPurposeExample
Severity.LabelNormalized severityHIGH, CRITICAL, MEDIUM
ResourcesAffected AWS resourcesS3 bucket ARN, Lambda function ARN
ProductNameWhich service generated itMacie, GuardDuty, Inspector
RemediationHow to fix itUpgrade Pillow, delete PII file
Compliance.StatusCompliance stateFAILED, PASSED

This normalization is what makes Security Hub more than just a dashboard — it enables filtering, sorting, and automated workflows across services that otherwise have completely different finding formats.

EventBridge event patterns — matching on structure, not strings

EventBridge rules match events by their JSON structure, not by string searching. GuardDuty emits two different event types, each requiring its own pattern:

Standard findings (credential compromise, unusual API calls):

{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": [{ "numeric": [">=", 7] }]
  }
}

Malware Protection scan results (malicious files in S3):

{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Malware Protection Object Scan Result"],
  "detail": {
    "scanResultDetails": {
      "scanResultStatus": ["THREATS_FOUND"]
    }
  }
}

The first pattern matches on severity — only High and Critical findings trigger the rule. The second matches on scan result — only objects where threats were found. Different event types, different JSON structures, but the same pattern-matching language.

This pattern language works for any AWS service event. You could match Config compliance changes, Inspector findings above a threshold, or Macie findings of specific PII types. EventBridge is the universal router for security automation.

The detection spectrum — from passive scanning to automated response

The detection services in this course form a spectrum from passive to active:

ServiceWhen it runsWhat it doesResponse
InspectorContinuous (background)Scans packages against CVE databasesFinding only — human decides
MacieScheduled or on-demandScans S3 content for PII patternsFinding only — human decides
GuardDutyContinuous (real-time)Analyzes logs for threat patternsFinding + optional EventBridge automation
EventBridge + LambdaEvent-driven (instant)Matches findings against rulesAutomated — SNS notification + Lambda quarantine

Moving right on this spectrum means faster response and less human intervention — but also more risk of false positives triggering automated actions. In the lab, both notification and remediation are wired to the same EventBridge rule. Most organizations start with notifications only and add automated remediation as they gain confidence in their detection rules.

5. What’s still missing

One pillar remains on the running side of the diagram.

No organizational guardrails
▼

Everything built so far applies to a single AWS account. In production, workloads run across multiple accounts — production, staging, development, audit. A single misconfigured account can compromise the entire organization. Service Control Policies (SCPs) enforce guardrails that no individual account can override — preventing CloudTrail deletion, public S3 buckets, or resource creation in unauthorized regions. Control Tower automates the creation of new accounts with baseline security controls already in place.
