Incident Detection & Response

This course builds a Photo Viewer application across twelve weeks, adding one AWS security layer per week. This page shifts from inward-facing monitoring to adversarial thinking — detecting when someone is doing something bad and responding automatically.

Learning objectives

  • Distinguish between monitoring (inward-facing) and detection (adversary-facing)
  • Identify three threat categories addressed this week: careless data exposure, malicious content, and vulnerable dependencies
  • Explain how Macie detects sensitive data in S3 objects using managed data identifiers (regex patterns + machine learning)
  • Explain how GuardDuty detects threats by analyzing CloudTrail, VPC flow logs, DNS logs, and S3 object scans
  • Explain how Security Hub normalizes findings from multiple services into a single dashboard using ASFF
  • Describe how EventBridge event patterns enable automated response to security findings
  • Implement automated remediation by wiring a quarantine Lambda as an EventBridge target
  • Explain why KMS encryption does not prevent Macie from detecting sensitive data

1. Where we left off

The monitoring infrastructure is in place. CloudWatch watches performance. Config watches configuration. Inspector watches dependencies. Trusted Advisor provides account-level health checks. But all of this is inward-facing — checking our own work. Two problems remain:

Uploaded files are still not scanned for malicious content
▼

A user could upload a file containing credit card numbers, or an image that is actually a disguised executable. Encryption protects these files at rest, but encryption does not inspect content. Two services address this: Macie detects PII patterns (SSN, credit card numbers) and GuardDuty Malware Protection scans for malware signatures. Both are addressed this week.

No detection of adversarial behavior
▼

If someone exfiltrates IAM credentials and makes API calls from an unfamiliar IP, none of the monitoring tools from the prior week would flag it. CloudWatch sees no errors. Config sees no configuration change. Inspector sees no new vulnerability. The attacker is doing something bad — but everything looks normal from the inside. GuardDuty detects adversarial behavior by analyzing patterns across CloudTrail, VPC flow logs, and DNS queries. Addressed this week.

The shift this week: from “is our system healthy?” to “is someone doing something bad?”

Response

Detection generates findings. Response acts on them. EventBridge connects the two — matching finding events against rules and routing them to targets automatically.

1
Event source: GuardDuty Malware Protection scans an uploaded S3 object and publishes a scan result.
2
Event bus: The scan result is published to the default EventBridge event bus as a structured JSON event.
3
Rule matches: An EventBridge rule matches on source = aws.guardduty and scanResultStatus = THREATS_FOUND.
4
Target 1 — notification: The rule sends the event to an SNS topic. SNS delivers an email to Jerry.
5
Target 2 — remediation: The same rule triggers the quarantine Lambda.
6
File quarantined: The Lambda moves the flagged object from photos/ to quarantine/ in the Photo Viewer’s S3 bucket. At 3 AM, nobody is watching the dashboard. The email arrives, and the malicious file is already gone. Jerry wakes up and the situation is contained.

EventBridge can match different event types, each with its own rule. In this lab, two rules handle two different scenarios. The malware quarantine rule matches Malware Protection scan results where threats were found — it has two targets (SNS and Lambda) running simultaneously. The high-severity findings rule matches standard GuardDuty findings (credential compromise, unusual API calls) at severity ≥ 7 — it routes to SNS only. Different event types require separate rules, but the pattern is the same: match on structure, route to targets.

In production, automated remediation requires careful tuning — quarantining a legitimate file is a false-positive outage. Most organizations start with notifications only and add automated remediation as they gain confidence in their detection rules.

EventBridge event patterns — matching on structure, not strings

EventBridge rules match events by their JSON structure, not by string searching. GuardDuty emits two different event types, each requiring its own rule:

High-severity findings rule (credential compromise, unusual API calls):

{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": [{ "numeric": [">=", 7] }]
  }
}

Malware quarantine rule (malicious files in S3):

{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Malware Protection Object Scan Result"],
  "detail": {
    "scanResultDetails": {
      "scanResultStatus": ["THREATS_FOUND"]
    }
  }
}

The first pattern matches on severity — only High and Critical findings trigger the rule. The second matches on scan result — only objects where threats were found. Different event types, different JSON structures, but the same pattern-matching language.

This pattern language works for any AWS service event — not just GuardDuty. Every detection service publishes events to EventBridge: Macie findings, Inspector findings, Config compliance changes. You can write rules against any of them.

There are two automation paths. In the direct path, you match on each service’s native event fields:

// GuardDuty native event
"detail": {
  "severity": 8,
  "type": "Trojan:S3/DropPoint"
}

In the Security Hub path, Security Hub normalizes findings to ASFF and re-publishes them as events. You match on normalized fields instead:

// Security Hub ASFF event
"detail": {
  "findings": [{
    "Severity": { "Label": "HIGH" },
    "ProductName": "GuardDuty"
  }]
}

EventBridge is schema-agnostic — it matches whatever JSON fields you point it at. The advantage of the Security Hub path is consistency: you write rules against normalized labels like HIGH and CRITICAL instead of remembering that GuardDuty uses 0–10 numbers, Inspector uses CVSS scores, and Macie uses its own severity scale. One vocabulary for all services.

In this lab we use the direct path — students see the native event structure and learn what each service actually emits. Production environments often use the Security Hub path to manage automation from a single source.

4. Key concepts

Stepping back from the individual services to see how they fit together.

Detection services at a glance
ServiceWhat it scansWhat triggers a scanWhat it finds
InspectorLambda packages, EC2 instances, container imagesNew deployment, new CVE published by NISTKnown vulnerabilities (CVE ID + CVSS score)
MacieS3 object contentScheduled job or on-demand discoverySensitive data patterns (SSN, credit card, API keys)
GuardDutyCloudTrail events, VPC flow logs, DNS logs, S3 uploadsContinuous analysis of incoming logs and eventsAdversarial behavior and malware (credential theft, unusual API calls, trojans)

All three generate findings. None of them auto-remediate on their own. Automated response — notification, quarantine, or any other action — is a separate layer: EventBridge + Lambda. Any detection service’s findings can be wired to EventBridge for automation. In this lab we automate GuardDuty malware findings; the same pattern works for Macie PII findings or Inspector CVE findings.

5. What’s still missing

One issue remains.

No organizational guardrails
▼

Everything built so far applies to a single AWS account. Three problems follow from this. Development and production share the same account — a bad deployment takes the app down for real users. The same person who sets up security controls can also delete them — there is no separation between rule-makers and rule-followers. And the application runs entirely in us-east-1 — it is not set up for regional scaling or data sovereignty requirements. AWS Organizations, Service Control Policies (SCPs), Control Tower, and Route 53 address these gaps.
