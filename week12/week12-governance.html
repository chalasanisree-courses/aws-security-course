Security Governance

This course builds a Photo Viewer application across twelve weeks, adding one AWS security layer per week. This final page addresses the seventh pillar — organizational guardrails that ensure what you built cannot be undone by a single misconfigured account.

Learning objectives
  • Distinguish between enforcement (Config rules) and governance (SCPs) — who sets the boundaries, and can they be bypassed?
  • Identify four categories of governance: security, data, identity, and cost
  • Describe how SCPs create a ceiling that no IAM principal in a member account can exceed
  • Explain the management account exemption and why workloads should never run there
  • Describe how data sovereignty requirements drive multi-region, multi-account design
  • Explain how Control Tower automates Landing Zone creation with baseline guardrails
  • Explain Route 53 concepts: latency-based routing, geolocation routing, health checks, DNSSEC

1. Where we left off

The Photo Viewer is a secure application with detection and response mechanisms in place. If someone uploads malware, GuardDuty catches it. If sensitive data lands in the bucket, Macie flags it. If a dependency has a known vulnerability, Inspector finds it. Security Hub aggregates everything. EventBridge automates the response.

But all of this exists in the context of a single AWS account. The prior concept page flagged this: “Everything built so far applies to a single AWS account. A single misconfigured account can compromise the entire organization.” Three specific gaps remain. Click each to expand.

No account-level separation Addressed this week

The problem: The development team building the Photo Viewer, the operations staff running it, and the security team governing it all share the same AWS account. A developer testing a new Lambda deployment can break the live application. An operations engineer troubleshooting an issue can accidentally weaken a security control. There is no separation between the team that governs and the teams that operate.

The gap: In the Identity Center lab, you moved your account into the Production OU. But that account is also the management account — the account that owns Organizations, manages Identity Center, and handles billing. It defines the organizational boundaries. The people who define the policies and the people who operate under them are the same people in the same account.

A quick refresher: When you created Organizations in the Identity Center lab, your account became the management account. This is the single account that controls the organization. Any other account you create or invite becomes a member account — an account that runs workloads and is subject to organizational policies. Right now, you have one management account and zero member accounts.

Addressed this week: The security management team gets a dedicated management account (governance only, zero workloads). The development teams get their own member accounts inside Production and Staging OUs. The account that defines the boundaries is separate from the accounts that operate within them.

No separation between boundary-setters and operators Addressed this week

The problem: Jerry set up Config rules, CloudWatch alarms, Inspector scanning, Macie discovery jobs, and GuardDuty. But Jerry can also delete all of them. The same person who set up the security controls can remove them. If Jerry’s credentials are compromised, the attacker can disable every security control and delete the evidence.

Why this is hard to fix in a single account: In a single account, any administrator can change any policy. There is no “higher authority” that prevents an admin from undoing security controls. You need a mechanism that sits above individual accounts and defines boundaries that nobody inside the account can override. That mechanism is called a Service Control Policy (SCP) — explained in Section 2.

The deeper issue: The management account — the account that would define these boundaries — is exempt from them. Organizational policies only restrict member accounts. Since the Photo Viewer runs in the management account, it cannot be governed by its own policies.

Addressed this week: Once the accounts are separated (Issue 1), the security management team in the management account can write SCPs that restrict what the development teams can and cannot do in their member accounts. The operators cannot change or remove these boundaries — even with AdministratorAccess, even as root.

Not set up for regional scaling Addressed this week

The problem: The Photo Viewer runs entirely in us-east-1. Users in Asia experience 400ms latency. More critically, data sovereignty laws in several Asian jurisdictions require that user-uploaded photos and account data remain within local borders.

Why not just deploy in a second region within the same account? Because data sovereignty is not just about where data is stored — it is about who can access it. An IAM admin in a single account can read S3 objects in any region. Separate accounts create a hard boundary that IAM alone cannot provide.

Addressed this week: This requires both previous solutions. Separate member accounts per region provide account-level isolation (Issue 1). The security management team applies different boundaries for different regional teams — region-lock SCPs for data sovereignty, centralized identity management to ensure compliance with local regulations (Issue 2). Route 53 (AWS’s DNS service) with geolocation routing ensures users in each country are directed to the correct regional deployment.

What is Governance?

Governance answers one question: who gets to set the boundaries, and can they be bypassed? In every prior week, the person who built the control is the same person who can remove it. Governance introduces a hierarchy: the organization sets the boundaries, the accounts operate within those boundaries, and nobody in the account can exceed the ceiling.

Enforcement (Config)Governance (SCPs)
Who creates the rule?Same person who operates the systemA separate organizational authority
Can the rule be deleted?Yes — by any admin in the accountNo — only the management account can change SCPs
Does root bypass it?Yes — root can delete Config rulesNo — root in member accounts is subject to SCPs
What happens if credentials are compromised?Attacker can disable enforcementAttacker is still bound by the SCP ceiling

Four Categories of Governance

The three solutions above address Governance across four distinct categories:

🔒
Security governance
“What security controls cannot be removed?”
CloudTrail logging cannot be stopped. S3 public access block cannot be weakened. (Solution 2 — baseline SCPs)
🌍
Data governance
“Where can data live, and who can access it?”
Asia user data stays in ap-southeast-1. No cross-region access. (Solution 3 — regional SCPs + account isolation)
👥
Identity governance
“Who can grant access, and from where?”
Identity Center is centralized. No local identity providers in member accounts. (Solution 2 — baseline SCP + centralized Identity Center)
💰
Cost governance
“What services and regions are permitted?”
Region-lock SCPs prevent accidental resource creation in expensive regions. (Solution 3 — regional SCPs)

4. Key concepts

Organizational controls

📜
SCPs — the ceiling IAM cannot exceed
Filter, not grant · applies to root in member accounts · management account exempt
▶

An SCP is a JSON policy — structurally identical to an IAM policy — but it operates at a fundamentally different level. It does not grant permissions. It restricts the maximum permissions available to an entire account. Even if every IAM policy in the account says Allow, the SCP ceiling applies.

Example region-lock SCP:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyNonApSoutheast1",
    "Effect": "Deny",
    "NotAction": ["iam:*", "sts:*", "organizations:*", "support:*"],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {"aws:RequestedRegion": "ap-southeast-1"}
    }
  }]
}

The NotAction exclusion is critical — IAM, STS, Organizations, and Support are global services that don't operate in a specific region. Without this exclusion, the SCP would break basic account functionality like creating roles or assuming cross-account permissions.

SCPs can only be created, modified, and attached from the management account using the Organizations API. No principal in a member account can call these APIs — they are simply not available.

⚠
The management account exemption
By design · prevents organizational lockout · why workloads don’t run here
▶

This exemption exists to prevent organizational lockout — if an overly broad SCP could apply to the management account, it could make the entire organization unrecoverable. The trade-off: any workload running in the management account operates without SCP guardrails. This is why the management account must be dedicated to governance — Organizations, Identity Center, billing — and nothing else.

In the lab: You attach SCPs to the Production OU and try to stop CloudTrail. It succeeds — because your account is the management account. This demonstrates the exemption directly.
🏗
Control Tower — automating what you built by hand
Landing Zone · preventive + detective guardrails · account factory
▶

Over twelve weeks, you manually configured: an Organization, OUs, Identity Center, permission sets, CloudTrail, Config, and SCPs. Control Tower automates all of this. A Landing Zone creates:

  • A multi-account structure with management, log archive, and audit accounts
  • Baseline SCPs (deny public S3, require CloudTrail, restrict regions)
  • Centralized logging (CloudTrail and Config aggregated in the log archive account)
  • Identity Center pre-configured with SSO groups
  • Guardrails categorized as preventive (SCPs) and detective (Config rules)

When the Asia team needs a new account, an administrator provisions it through Control Tower. The account is created with all baseline controls already in place — region-locked, CloudTrail enabled, encryption required, Identity Center access centralized. No manual configuration, no risk of forgetting a step.

Regional scaling and data sovereignty

📚
Data sovereignty — why geography matters for security
GDPR · PDPA · data localization laws · region-lock SCPs
▶

Data sovereignty laws require that certain data be stored and processed within a specific geographic jurisdiction:

  • GDPR (EU) — personal data of EU residents must be protected under EU standards, with restrictions on transfer outside the EU
  • PDPA (Singapore, Thailand) — personal data transfers outside the country require adequate protections and consent
  • Data localization laws (India, Indonesia, Vietnam) — certain categories of data must remain within national borders

Multi-region deployment with region-lock SCPs addresses data sovereignty at the infrastructure level. It is not enough to deploy in the right region — you must also prevent data from being copied, replicated, or accessed from another region. Region-lock SCPs enforce this: no principal in the Asia account can create an S3 bucket in us-east-1, even accidentally.

🌐
Route 53 — routing users to the right region
Geolocation · latency-based · health checks · DNSSEC · alias records
▶

Geolocation routing: Routes based on the user’s geographic location (country or continent). A user in Singapore always gets ap-southeast-1; a user in New York always gets us-east-1. The mapping is deterministic — same country, same answer, every time. This is the correct choice for data sovereignty, where legal requirements mandate that users in a specific country always hit a specific region.

Latency-based routing: Route 53 measures network latency from the user’s location to each AWS region and returns the record for the lowest-latency endpoint. Optimizes for performance, and geography usually correlates — but not always. A network anomaly could route an Asia user to us-east-1. Use latency-based when performance matters more than compliance.

Health checks: Route 53 monitors endpoint health and automatically routes traffic away from unhealthy regions. If the Asia deployment is down, Asia users can fail over to the US deployment — though cross-region failover must account for data sovereignty requirements.

DNSSEC: DNS Security Extensions that cryptographically sign DNS records. Prevents an attacker from spoofing DNS responses to redirect photoviewer.com to a malicious server.

Alias records: Route 53’s special record type that maps a hostname directly to an AWS resource (CloudFront, ALB, S3) without a CNAME indirection.
