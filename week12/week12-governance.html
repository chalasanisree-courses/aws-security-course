Security Governance

This course builds a Photo Viewer application across twelve weeks, adding one AWS security layer per week. This final page addresses the seventh pillar — organizational guardrails that ensure what you built cannot be undone by a single misconfigured account.

Learning objectives
  • Distinguish between enforcement (Config rules) and governance (SCPs) — who makes the rules, and can they be bypassed?
  • Identify four categories of governance: security, data, identity, and cost
  • Describe how SCPs create a ceiling that no IAM principal in a member account can exceed
  • Explain the management account exemption and why workloads should never run there
  • Describe how data sovereignty requirements drive multi-region, multi-account design
  • Explain how Control Tower automates Landing Zone creation with baseline guardrails
  • Explain Route 53 concepts: latency-based routing, geolocation routing, health checks, DNSSEC

1. Where we left off

The Photo Viewer is a secure application with detection and response mechanisms in place. If someone uploads malware, GuardDuty catches it. If sensitive data lands in the bucket, Macie flags it. If a dependency has a known vulnerability, Inspector finds it. Security Hub aggregates everything. EventBridge automates the response.

But all of this exists in the context of a single AWS account. The prior concept page flagged this: “Everything built so far applies to a single AWS account. A single misconfigured account can compromise the entire organization.” Three specific gaps remain. Click each to expand.

No separation between development and production Addressed this week

The problem: The Photo Viewer — the live application serving real users — runs in the same account where you develop, test, and experiment. A bad Lambda deployment takes the app down for customers. A developer testing IAM policies could accidentally open S3 to the public. There is no boundary between “trying things out” and “serving real traffic.”

The gap: In the Identity Center lab, you moved your account into the Production OU. But that account is also the management account — the account that owns Organizations, manages Identity Center, and handles billing. It defines the organizational policies. In production, the management account should not also be the account running workloads — the organization that defines the rules should not also be the one following them.

A quick refresher: When you created Organizations in the Identity Center lab, your account became the management account. This is the single account that controls the organization. Any other account you create or invite becomes a member account — an account that runs workloads and is subject to organizational policies. Right now, you have one management account and zero member accounts.

Addressed this week: In the production architecture, a dedicated management account handles governance only. The Photo Viewer runs in a member account inside the Production OU. A separate staging member account in the Staging OU gives the team a safe place to test.

No separation between rule-makers and rule-followers Addressed this week

The problem: Jerry set up Config rules, CloudWatch alarms, Inspector scanning, Macie discovery jobs, and GuardDuty. But Jerry can also delete all of them. The same person who enforces the rules can remove the enforcement. If Jerry’s credentials are compromised, the attacker can disable every security control and delete the evidence.

Why this is hard to fix in a single account: In a single account, any administrator can change any policy. There is no “higher authority” that prevents an admin from undoing security controls. Even the root user — the most powerful principal — operates within the same account. You need a mechanism that sits above individual accounts and defines limits that nobody inside the account can override. That mechanism is called a Service Control Policy (SCP) — explained in Section 2.

The deeper issue: The management account — the account that would define these organizational policies — is exempt from them. Organizational policies only restrict member accounts. Since the Photo Viewer runs in the management account, it cannot be governed by its own policies.

Addressed this week: In production, the management account is dedicated to governance — it runs zero workloads and defines the rules. Member accounts run the Photo Viewer and follow the rules. The people operating the Photo Viewer cannot change or remove the organizational policies that govern them.

Not set up for regional scaling Addressed this week

The problem: The Photo Viewer runs entirely in us-east-1. Users in Asia experience 400ms latency. More critically, data sovereignty laws in several Asian jurisdictions require that user-uploaded photos and account data remain within local borders.

Why not just deploy in a second region within the same account? Because data sovereignty is not just about where data is stored — it is about who can access it. An IAM admin in a single account can read S3 objects in any region. Separate accounts create a hard boundary that IAM alone cannot provide.

Addressed this week: This issue requires both previous solutions working together. Separate member accounts per region provide account-level isolation. Organizational policies lock each account to a single region so data cannot accidentally (or deliberately) leave its jurisdiction. Route 53 latency-based routing connects users to the closest deployment automatically.

2. This week’s solution

Governance answers one question: who gets to set the rules, and can they be bypassed? In every prior week, the person who built the control is the same person who can remove it. Governance introduces a hierarchy: the organization sets the rules, the accounts operate within those rules, and nobody in the account can exceed the ceiling.

Enforcement vs governance

Enforcement (Config)Governance (SCPs)
Who creates the rule?Same person who operates the systemA separate organizational authority
Can the rule be deleted?Yes — by any admin in the accountNo — only the management account can change SCPs
Does root bypass it?Yes — root can delete Config rulesNo — root in member accounts is subject to SCPs
What happens if credentials are compromised?Attacker can disable enforcementAttacker is still bound by the SCP ceiling

4. Key concepts

Organizational controls

📜
SCPs — the ceiling IAM cannot exceed
Filter, not grant · applies to root in member accounts · management account exempt
▼

IAM policies define what a principal can do. SCPs define what an account cannot do:

IAM PolicySCP
ScopeSingle principalEntire account (all principals)
EffectGrants permissionsRestricts maximum available permissions
OverrideAny admin can changeOnly management account can change
Root userRoot bypasses IAM policiesRoot is subject to SCPs (in member accounts)

Example region-lock SCP:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyNonApSoutheast1",
    "Effect": "Deny",
    "NotAction": ["iam:*", "sts:*", "organizations:*", "support:*"],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {"aws:RequestedRegion": "ap-southeast-1"}
    }
  }]
}

The NotAction exclusion is critical — IAM, STS, Organizations, and Support are global services that don’t operate in a specific region. Without this exclusion, the SCP would break basic account functionality.

⚠
The management account exemption
By design · prevents organizational lockout · why workloads don’t run here
▼

The management account is exempt from all SCPs. This is by design — if SCPs could lock out the management account, an overly broad SCP could make the entire organization unrecoverable.

The consequence: any workload running in the management account operates without SCP guardrails. In this course, the Photo Viewer runs in the management account because students have a single AWS account. In production, this is unacceptable. The management account should contain only Organizations, Identity Center, and consolidated billing.

🏗
Control Tower — automating what you built by hand
Landing Zone · preventive + detective guardrails · account factory
▼

Over twelve weeks, you manually configured: an Organization, OUs, Identity Center, permission sets, CloudTrail, Config, and SCPs. Control Tower automates all of this. A Landing Zone creates:

  • A multi-account structure with management, log archive, and audit accounts
  • Baseline SCPs (deny public S3, require CloudTrail, restrict regions)
  • Centralized logging (CloudTrail and Config aggregated in the log archive account)
  • Identity Center pre-configured with SSO groups
  • Guardrails categorized as preventive (SCPs) and detective (Config rules)

When the Asia team needs a new account, an administrator provisions it through Control Tower. The account is created with all baseline controls already in place — region-locked, CloudTrail enabled, encryption required, Identity Center access centralized. No manual configuration, no risk of forgetting a step.

DNS and edge networking

🌐
Route 53 — routing users to the right region
Latency-based · geolocation · health checks · DNSSEC
▼

Latency-based routing: Route 53 measures network latency from the user’s location to each AWS region and returns the record for the lowest-latency endpoint. A user in Tokyo gets ap-southeast-1; a user in New York gets us-east-1. Performance optimization naturally aligns with data sovereignty.

Geolocation routing: Routes based on the user’s geographic location (country or continent), regardless of latency. Useful when legal requirements mandate that users in a specific country always hit a specific region — even if another region would be faster.

Health checks: Route 53 monitors endpoint health and automatically routes traffic away from unhealthy regions. If the Asia deployment is down, Asia users fail over to the US deployment (with appropriate data handling considerations).

DNSSEC: DNS Security Extensions that cryptographically sign DNS records. Prevents an attacker from spoofing DNS responses to redirect photos.example.com to a malicious server.

Alias records: Route 53’s special record type that maps a hostname directly to an AWS resource (CloudFront, ALB, S3) without a CNAME indirection.

📚
Data sovereignty — why geography matters for security
GDPR · PDPA · data localization laws
▼

Data sovereignty laws require that certain data be stored and processed within a specific geographic jurisdiction:

  • GDPR (EU) — personal data of EU residents must be protected under EU standards, with restrictions on transfer outside the EU
  • PDPA (Singapore, Thailand) — personal data must be stored and processed domestically
  • Data localization laws (India, Indonesia, Vietnam) — certain categories of data must remain within national borders

Multi-region deployment with region-lock SCPs addresses data sovereignty at the infrastructure level. It is not enough to deploy in the right region — you must also prevent data from being copied, replicated, or accessed from another region. Region-lock SCPs enforce this: no principal in the Asia account can create an S3 bucket in us-east-1, even accidentally.

5. Course retrospective — the complete Photo Viewer

Twelve weeks. Seven pillars. One application. The Photo Viewer started as a public S3 bucket with pre-seeded photos and evolved into a fully secured, monitored, and governed application.

✓ Authentication & Access Control
▼

Cognito user pool with Google OAuth. PKCE authorization code flow. JWT-based session management. Cognito groups (free, premium) driving RBAC. Lambda authorizer validating tokens. Owner-scoped operations preventing IDOR. Identity Center with Tom (customer support) and Jerry (security engineer). Permission sets scoped to specific KMS keys.

✓ Network Security
▼

CloudFront distribution with HTTPS enforcement and origin access control. VPC with public and private subnets. Security groups restricting traffic. WAF with rate limiting. API Gateway replacing ALB. Lambda authorizer verifying origin secret. Shield Standard for DDoS protection.

✓ Data Encryption
▼

Customer-managed KMS keys. Two-key architecture: infra key (operational secrets) and data key (user content). SSE-KMS on S3 and DynamoDB. Secrets Manager encrypted with the infra key. Key policies creating an authorization layer independent of IAM. Separation of duties.

✓ Update & Patch Management
▼

Inspector enabled for Lambda scanning. Continuous CVE monitoring against the NIST NVD. Found real Pillow CVEs in the image validator Lambda. Findings flow to Security Hub.

✓ Security Monitoring & Auditing
▼

CloudWatch alarms on Lambda errors and duration. AWS Config with managed rules for S3 encryption, public access, CloudTrail, and root key checks. Drift detection with break/fix validation. Trusted Advisor security checks. SNS notification backbone.

✓ Incident Detection & Response
▼

Image validator Lambda using Pillow. Macie for PII detection. GuardDuty for malware and adversarial behavior. Security Hub aggregating findings from Inspector, Macie, GuardDuty, and Config. EventBridge with dual targets — SNS notification and Lambda quarantine for automated remediation.

✓ Security Governance
▼

AWS Organizations with OU structure. SCPs enforcing region locks, denying CloudTrail deletion, preventing public S3, and centralizing identity management. Control Tower as the automation layer for Landing Zone creation. Route 53 for latency-based routing across regions. Data sovereignty enforced at the organizational level.
