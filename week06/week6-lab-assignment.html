Week 6 Lab — User Identity and Authentication

CS 55D: Security in Amazon Web Services  ·  Foothill College  ·  100 pts

Objective: Add login to the Photo Viewer using Amazon Cognito with Google as a federated identity provider. Move the origin secret from a Lambda environment variable to AWS Secrets Manager. Update the Lambda authorizer to validate JWTs and fetch the secret at runtime. By the end of this lab, the Photo Viewer will have three distinct experiences: unauthenticated visitors see public photos only, free users and premium users see all photos after logging in with Google.

Architecture after this lab: Browser → WAF/CloudFront → API Gateway → Lambda authorizer (checks origin secret from Secrets Manager + validates JWT from Cognito) → main Lambda (filters by group) → DynamoDB

Pre-flight checklist

Before building anything, verify your Week 5 environment is intact. Open CloudShell and run:

cd ~
git clone https://github.com/chalasanisree-courses/aws-security-course.git 2>/dev/null || git -C aws-security-course pull
bash aws-security-course/photoviewer/week06/week6-preflight.sh

The script checks: Lambda function exists and returns photos, Lambda authorizer is attached, CloudFront routes /photos correctly, WAF Web ACL is attached, and DynamoDB has at least 5 items. Address any failures before proceeding.

Part 1 Cognito User Pool
Step 1 Create the Cognito User Pool

Go to Cognito → Create user pool. AWS now shows a single-page setup wizard. Fill it in as follows:

Application type

  • Select Single-page application (SPA) — this is a JavaScript app running in the browser. This setting tells Cognito not to generate a client secret, which is correct: browser apps cannot keep a secret safe because anyone can view the source.

Name your application

  • Application name: photoviewer-web-client
  • This name identifies the app client — the record Cognito uses to know which application is allowed to request tokens. Each application that integrates with Cognito gets its own app client with its own settings.

Configure options

  • Sign-in identifiers: check Email only — this is the attribute Cognito uses to identify a user in the User Pool. Even though Google handles the actual authentication, Cognito still stores a local user record keyed by email.
  • Self-registration: uncheck "Enable self-registration" — we want Google federation only. If left enabled, anyone could create a Cognito account directly with email and password, bypassing Google entirely.
  • Required attributes: leave empty

Add a return URL

  • Return URL: https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net/callback
  • Replace YOUR_CLOUDFRONT_DOMAIN with your actual CloudFront domain from the pre-flight output (e.g. d1kbm2nphud61r.cloudfront.net)
  • This is the URL Cognito is allowed to redirect back to after a successful login. Cognito enforces this as an allowlist — if app.js sends a redirect_uri that doesn't exactly match this value, Cognito rejects the login attempt. This prevents an attacker from redirecting the auth code to their own server.

Click Create user directory.

After creation you will land on the User Pool overview page. Note down two values — you need them in Step 9:

  • User Pool ID — shown on the overview page (e.g. us-east-1_XXXXXXXXX)
  • App client ID — go to App integration → App clients → photoviewer-web-client

Also note your Cognito domain — go to App integration → Domain. It will look like photoviewer-web-client-XXXXXXXX.auth.us-east-1.amazoncognito.com. You need the full domain for Step 3 (Google redirect URI) and the prefix for app.js in Step 13.

Next, set a sign-out URL and fix the scopes. Go to App integration → App clients → photoviewer-web-client → Login pages tab → Managed login pages configuration → Edit:

  • Sign-out URLs: add https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net — this is where Cognito redirects the browser after logout. Same allowlist enforcement as the callback URL.
  • OAuth 2.0 grant types: confirm Authorization code grant is checked — this is the flow where Cognito returns a short-lived auth code to the browser, which app.js then exchanges for tokens. The alternative (Implicit grant) returns tokens directly in the URL, which is less secure and deprecated.
  • OpenID Connect scopes: the defaults include phone which we don't need. Uncheck phone, and check Profile — so the final set is Email, OpenID, Profile. openid is required to get an ID token at all. email gives the user's email address. profile adds the user's name to the token claims.
  • Click Save changes
Cognito App client page showing App client ID, Hosted UI settings with callback URL and sign-out URL configured, and no client secret present

Part 2 Google Federation

What this part does: You will configure Google as an identity provider in Cognito. When a user clicks "Login with Google", Cognito redirects them to Google, which authenticates them and returns an auth code directly to Cognito. Cognito exchanges the code using the client secret you generate here, then issues its own JWT to the browser.

Step 3 Create OAuth 2.0 credentials in Google Cloud Console

Open a new browser tab and go to console.cloud.google.com. Sign in with your Google account.

  1. Create or select a project: Click the project selector at the top → New Project → name it photoviewer → Create. Select the project.
  2. Configure the OAuth consent screen (now called Google Auth Platform): In the left nav go to APIs & Services → Google Auth Platform. You will see a "Project configuration" wizard with four sections: App Information, Audience, Contact Information, Finish.
    • App Information: App name: PhotoViewer · User support email: your email → click Next
    • Audience: select External → click Next
    • Contact Information: Developer contact email: your email → click Next
    • Finish: click Create
  3. Create OAuth 2.0 credentials: In the left nav go to Clients → Create client (or go to APIs & Services → Credentials → Create Credentials → OAuth client ID).
    • Application type: Web application
    • Name: photoviewer-cognito
    • Authorized redirect URIs — click Add URI and enter your Cognito domain callback URL:
      https://YOUR_COGNITO_DOMAIN.auth.us-east-1.amazoncognito.com/oauth2/idpresponse
      (Replace YOUR_COGNITO_DOMAIN with the full domain from Step 1, e.g. photoviewer-web-client-a1b2c3d4)
    • Click Create

A dialog shows your Client ID and Client Secret. Copy both — you need them in Step 4. Do not close this dialog until you have copied both values.

Part 3 Move the Origin Secret to Secrets Manager
Step 6 Create the secret in Secrets Manager

Go to AWS Secrets Manager → Store a new secret.

  • Secret type: Other type of secret
  • Key/value pairs: Key = value, Value = the same secret you generated in Week 5 for ORIGIN_SECRET (retrieve it from your Lambda authorizer's environment variables before deleting it)
  • Click Next
  • Secret name: photoviewer/origin-verify-secret
  • Description: CloudFront origin verification secret for API Gateway
  • Click Next → Next → Store

Note the full Secret ARN — you will need it for the IAM policy in the next step.

Secrets Manager showing photoviewer/origin-verify-secret created with the secret ARN visible
Step 7 Grant the Lambda authorizer permission to read the secret

Go to Lambda → photoviewer-authorizer → Configuration → Permissions → click the execution role name to open it in IAM.

Click Add permissions → Create inline policy → JSON tab and paste:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "secretsmanager:GetSecretValue",
    "Resource": "arn:aws:secretsmanager:us-east-1:[your-account-id]:secret:photoviewer/origin-verify-secret-*"
  }]
}

Replace [your-account-id] with your AWS account ID (available in the top-right of the console). The trailing -* accounts for the random suffix Secrets Manager appends to ARNs.

Policy name: photoviewer-secrets-read → Create policy.

Why scope to the specific ARN? secretsmanager:GetSecretValue on * would let the function read any secret in your account. Scoping to the specific ARN means a compromised function can only read the one secret it actually needs.

IAM role for photoviewer-authorizer showing the new photoviewer-secrets-read inline policy with the GetSecretValue action scoped to the specific secret ARN
Step 8 Remove ORIGIN_SECRET from the Lambda environment variable

Go to Lambda → photoviewer-authorizer → Configuration → Environment variables → Edit. Delete the ORIGIN_SECRET entry → Save.

The secret is no longer visible in the Lambda console. Any developer with lambda:GetFunction permission can no longer see it.

Part 4 Update the Lambda Authorizer
Step 9 Deploy the updated authorizer code

Go to Lambda → photoviewer-authorizer → Code tab. Replace the entire contents with the code from photoviewer/week06/authorizer.py in the GitHub repo.

The updated authorizer does two things in sequence:

  1. Origin secret check (required): fetches photoviewer/origin-verify-secret from Secrets Manager and checks the x-origin-verify header. If missing or wrong → isAuthorized: False immediately.
  2. JWT validation (optional): if an Authorization: Bearer header is present, fetches Cognito's JWKS public keys, verifies the JWT signature, checks expiry, and extracts the cognito:groups claim. If the JWT is invalid → isAuthorized: False. If no JWT → passes through as unauthenticated.

You also need to add two environment variables to the authorizer. Go to Configuration → Environment variables → Edit → Add:

  • Key: COGNITO_USER_POOL_ID — Value: your User Pool ID (e.g. us-east-1_XXXXXXXXX)
  • Key: COGNITO_APP_CLIENT_ID — Value: your App client ID

Click Save. Then go back to the Code tab and click Deploy.

Click Deploy. The Lambda console is an editor — changes are not live until you deploy. If you skip this step the old code keeps running and the authorizer will fail.

Lambda authorizer Code tab showing the new authorizer code deployed, and the Configuration tab showing the two Cognito environment variables
Step 10 Update the main Lambda to filter by group

Go to Lambda → photoviewer-lambda → Code tab. Replace the contents with photoviewer/week06/lambda_function.py from the GitHub repo.

The updated function reads the groups context passed by the authorizer:

  • If groups is non-empty (any authenticated user) → returns all photos, no is_public filter
  • If groups is empty (unauthenticated) → returns only is_public = true photos

Click Deploy.

Lambda function Code tab showing the updated code deployed
Step 11 Verify the authorizer still works with no JWT

Test that the unauthenticated path still works after the authorizer update:

✓ CloudShell verify
# Should still return Unauthorized (no origin secret)
curl -s https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos

# Should return public photos (origin secret present, no JWT)
curl -s https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos \
  -H "x-origin-verify: YOUR_SECRET"

Expected: first command returns {"message":"Unauthorized"}. Second returns a JSON array of photos. If the second fails, the authorizer is rejecting the request — check that you deployed the updated code and that the Secrets Manager secret value matches what CloudFront is configured to send.

Part 5 Seed a Private Photo
Step 12 Add a private photo to DynamoDB

The meaningful test for Week 6 is unauthenticated vs authenticated — not free vs premium. You need at least one item with is_public = false so you can verify that unauthenticated visitors don't see it but logged-in users do.

Open CloudShell and run:

aws dynamodb put-item \
  --region us-east-1 \
  --table-name photoviewer-photos \
  --item '{
    "photo_id":    {"S": "photo-private-001"},
    "s3_key":      {"S": "photos/photo1.jpg"},
    "is_public":   {"BOOL": false},
    "owner":       {"S": "premium-user"},
    "uploaded_at": {"S": "2024-06-01"}
  }'

This reuses an existing S3 key — the test is about the is_public flag, not about a new photo file. The item will appear in the authenticated view but not the unauthenticated view.

Part 6 Update app.js
Step 13 Deploy the updated app.js to S3

The updated app.js from photoviewer/week06/app.js adds:

  • A Login / Logout button in the UI
  • On login click: redirects the browser to the Cognito Hosted UI
  • On page load: checks for a ?code= parameter in the URL — if present, exchanges the auth code with Cognito for a JWT (ID token), stores the JWT in sessionStorage, and reloads the page
  • On every /photos call: if a JWT is stored, sends it as Authorization: Bearer <token>
  • Checks the JWT exp claim before each call and refreshes silently if expired

Before uploading, edit app.js and replace these placeholders with your actual values:

  • YOUR_COGNITO_DOMAIN → your Cognito domain prefix (e.g. photoviewer-644094189785)
  • YOUR_APP_CLIENT_ID → your App client ID from Step 1
  • YOUR_CLOUDFRONT_DOMAIN → your CloudFront domain name

Upload to S3:

aws s3 cp app.js s3://photoviewer-9876543210/app.js \
  --content-type "application/javascript" \
  --region us-east-1

Then invalidate the CloudFront cache so the browser gets the new file:

aws cloudfront create-invalidation \
  --distribution-id YOUR_DISTRIBUTION_ID \
  --paths "/app.js" "/callback"

Wait for the invalidation to complete — check status in CloudFront → Invalidations tab.

Troubleshooting

If something isn't working, work through these checks in order. Each one isolates a specific layer.

Check 1 — Authorizer rejects all requests (401 after update)

If the authorizer is rejecting every request including ones with the correct origin secret, the most likely cause is that the Secrets Manager fetch is failing.

# Test the authorizer directly with just the origin secret
curl -s https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos \
  -H "x-origin-verify: YOUR_SECRET"

If this returns {"message":"Unauthorized"}, check: the IAM policy on the authorizer role includes secretsmanager:GetSecretValue on the correct ARN; the secret name in the code matches photoviewer/origin-verify-secret; you clicked Deploy after updating the code.

Check 2 — Google login fails with redirect_uri_mismatch

This means the redirect URI you entered in Google Cloud Console doesn't match what Cognito is sending. The Cognito redirect URI must be exactly: https://YOUR_COGNITO_DOMAIN.auth.us-east-1.amazoncognito.com/oauth2/idpresponse. Check the Google Cloud Console → Credentials → your OAuth client → Authorized redirect URIs and confirm it matches exactly, including the protocol and path.

Check 3 — Callback URL returns a browser error after login

After Google authentication, the browser is redirected to https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net/callback?code=XXXX. If you see a 403 or the page doesn't load the app, check: the callback URL in Cognito App client settings matches your CloudFront domain exactly; CloudFront serves index.html for the /callback path (check the default root object is set).

Check 4 — JWT present but still seeing only 5 photos

If the Authorization header is being sent but Lambda is still filtering to public photos, check the authorizer is passing group context correctly. Go to CloudWatch → /aws/lambda/photoviewer-authorizer and look for log entries. If you see the JWT being validated but no group context, check that the user is actually in a Cognito group — go to Cognito → Users → your user → Groups tab.

Check 5 — JWT validation fails (invalid signature)

This usually means the COGNITO_USER_POOL_ID or COGNITO_APP_CLIENT_ID environment variable in the authorizer is wrong. The JWKS endpoint the authorizer fetches is derived from the User Pool ID — a wrong ID means the wrong public keys are used for verification. Double-check both values match exactly what's shown in the Cognito console.

Check 6 — Full end-to-end via CloudFront

curl -s https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net/photos

Expected: JSON array of 5 public photos. If this fails but the direct API Gateway call works, the issue is in CloudFront — verify the /photos behavior is still using the photoviewer-apigw-origin and has AllViewerExceptHostHeader as the origin request policy.

Answer all three questions in 2–3 sentences each.

Question 1

In Week 5, the ORIGIN_SECRET was stored as a Lambda environment variable. In Week 6, it is fetched from AWS Secrets Manager at runtime. Explain three specific security improvements this change provides, and describe one scenario where a secret in an environment variable could be exposed that Secrets Manager prevents.

Question 2

The Photo Viewer uses Cognito as a broker rather than trusting Google JWTs directly. The Lambda authorizer validates Cognito's JWT — not Google's. Explain what problem this design solves, and what would break if you added a second identity provider (e.g. Facebook) to a system that validated each IdP's JWT directly.

Question 3

The Lambda authorizer performs two checks on every /photos request: the origin secret check and the JWT validation. One check is required for every request; the other is optional. Explain which is which, why unauthenticated requests must be allowed through, and what security property each check provides independently.
