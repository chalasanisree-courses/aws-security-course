Week 6 Lab — User Identity and Authentication

CS 55D: Security in Amazon Web Services  ·  Foothill College  ·  125 pts

Objective: Add login to the Photo Viewer using Amazon Cognito with Google as a federated identity provider. Move the origin secret from a Lambda environment variable to AWS Secrets Manager. Update the Lambda authorizer to validate JWTs and fetch the secret at runtime. By the end of this lab, the Photo Viewer will have three distinct experiences: unauthenticated visitors see public photos only, free users and premium users see all photos after logging in with Google.

Architecture after this lab: Browser → WAF/CloudFront → API Gateway → Lambda authorizer (checks origin secret from Secrets Manager + validates JWT from Cognito) → main Lambda (filters by group) → DynamoDB

📊 Understanding the Flow: Before you start, review the Week 6 Login and Logout Flows to see the complete architecture and understand which URLs go where.

Part 2 Google Federation

What this part does: You will configure Google as an identity provider in Cognito. When a user clicks "Login with Google", Cognito redirects them to Google, which authenticates them and returns an auth code directly to Cognito. Cognito exchanges the code using the client secret you generate here, then issues its own JWT to the browser.

Step 3 Get your Cognito redirect URI

Go to your Cognito User Pool → Branding → Domain in the left nav. You will see your Cognito domain listed under "Cognito domain", e.g.:

https://us-east-1xxxxxxxxx.auth.us-east-1.amazoncognito.com

The redirect URI you need to register with Google is your Cognito domain with /oauth2/idpresponse appended. Construct it now and copy it:

https://YOUR_COGNITO_DOMAIN.auth.us-east-1.amazoncognito.com/oauth2/idpresponse

Why this URI? After the user signs in with Google, Google redirects back with an auth code. The destination is Cognito's /oauth2/idpresponse endpoint — not your CloudFront URL. Cognito sits between Google and your app: it receives the auth code from Google, exchanges it server-to-server using the Google client secret, then issues its own JWT to your browser. You're registering this URI with Google so it knows where to send the auth code.

    • App Information: App name: PhotoViewer · User support email: your email → click Next

    • Name: photoviewer-cognito

A dialog shows your Client ID and Client Secret. Copy both — you need them in Step 5. Do not close this dialog until you have copied both values.

Part 3 Move the Origin Secret to Secrets Manager
Step 7 Create the secret in Secrets Manager

Go to AWS Secrets Manager → Store a new secret.

  • Secret type: Other type of secret
  • Key/value pairs: Key = ORIGIN_SECRET, Value = the same secret you generated in Week 5 (retrieve it from your Lambda authorizer's environment variables before deleting it). The secret will be stored as {"ORIGIN_SECRET": "your-secret-here"} — the same name as the environment variable it replaces, making the migration easy to follow.
  • Click Next
  • Secret name: photoviewer/origin-verify-secret
  • Description: CloudFront origin verification secret for API Gateway
  • Click Next → Next → Store

Note your AWS account ID — you need it for the IAM policy in the next step. It's visible in the top-right of the AWS console (12-digit number).

Secrets Manager showing photoviewer/origin-verify-secret created with the secret ARN visible
Step 8 Grant the Lambda authorizer permission to read the secret

Go to Lambda → photoviewer-authorizer → Configuration → Permissions → click the execution role name to open it in IAM.

Click Add permissions → Create inline policy → JSON tab and paste:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "secretsmanager:GetSecretValue",
    "Resource": "arn:aws:secretsmanager:us-east-1:[your-account-id]:secret:photoviewer/origin-verify-secret-*"
  }]
}

Replace [your-account-id] with your 12-digit AWS account ID and leave everything else exactly as shown — in particular do not replace the -* at the end. Secrets Manager appends a random suffix to every secret ARN, and the -* wildcard covers that suffix without you needing to know what it is.

Policy name: photoviewer-secrets-read → Create policy.

Why scope to the specific ARN? secretsmanager:GetSecretValue on * would let the function read any secret in your account. Scoping to the specific ARN means a compromised function can only read the one secret it actually needs.

IAM role for photoviewer-authorizer showing the new photoviewer-secrets-read inline policy with the GetSecretValue action scoped to the specific secret ARN
Step 9 Remove ORIGIN_SECRET from the Lambda environment variable

Go to Lambda → photoviewer-authorizer → Configuration → Environment variables → Edit. Delete the ORIGIN_SECRET entry → Save.

The secret is no longer visible in the Lambda console. Any developer with lambda:GetFunction permission can no longer see it.

Part 4 Update the Lambda Authorizer
Step 10 Deploy the updated authorizer code

Go to Lambda → photoviewer-authorizer → Code tab. Replace the entire contents with the code from photoviewer/week06/authorizer.py in the GitHub repo.

The updated authorizer does two things in sequence:

  1. Origin secret check (required): fetches photoviewer/origin-verify-secret from Secrets Manager and checks the x-origin-verify header. If missing or wrong → isAuthorized: False immediately.
  2. JWT validation (optional): if an Authorization: Bearer header is present, fetches Cognito's JWKS public keys, verifies the JWT signature, checks expiry, and extracts the cognito:groups claim. If the JWT is invalid → isAuthorized: False. If no JWT → passes through as unauthenticated.

You also need to add two environment variables to the authorizer. Go to Configuration → Environment variables → Edit → Add:

  • Key: COGNITO_USER_POOL_ID — Value: your User Pool ID (e.g. us-east-1_XXXXXXXXX)
  • Key: COGNITO_APP_CLIENT_ID — Value: your App client ID

Click Save. Then go back to the Code tab and click Deploy.

Click Deploy. The Lambda console is an editor — changes are not live until you deploy. If you skip this step the old code keeps running and the authorizer will fail.

Lambda authorizer Code tab showing the new authorizer code deployed, and the Configuration tab showing the two Cognito environment variables
Step 11 Update the main Lambda to filter by group

Go to Lambda → photoviewer-lambda → Code tab. Replace the contents with photoviewer/week06/lambda_function.py from the GitHub repo.

The updated function reads the groups context passed by the authorizer:

  • If groups is non-empty (any authenticated user) → returns all photos, no is_public filter
  • If groups is empty (unauthenticated) → returns only is_public = true photos

Part 6 Update app.js
Step 14 Deploy the updated app.js to S3

The updated app.js from photoviewer/week06/app.js adds:

  • A Login / Logout button in the UI

Part 7 Verify End-to-End
Step 15 Configure CloudFront to serve index.html for /callback

When Cognito redirects the browser to /callback?code=XXXX after login, CloudFront looks for a file called callback in S3 — it doesn't exist, so CloudFront returns a 403. The fix is a custom error response that serves index.html instead. Once app.js loads on that page it sees the ?code= in the URL and handles the token exchange automatically.

Go to CloudFront → your distribution → Error pages tab → Create custom error response:

  • HTTP error code: 403
  • Customize error response: Yes
  • Response page path: /index.html
  • HTTP response code: 200
  • Click Create custom error response

Wait for the distribution status to return to Deployed before continuing.

Why 403 and not 404? CloudFront with OAC returns 403 (not 404) when a requested path doesn't exist in S3 — S3 treats a missing object as access denied when accessed through OAC. Both 403 and 404 can be configured this way, but 403 is what CloudFront actually returns here.

CloudFront Error pages tab showing the custom 403 error response configured to return index.html with a 200 status
Step 16 Add a CloudFront behavior to bypass the origin check for /callback

The default CloudFront behavior has a CloudFront Function that checks the x-origin-verify header on every request — this is the Week 5 origin secret check. When Cognito redirects the browser to /callback, the browser doesn't send that header, so CloudFront rejects the request with a 403 before it even reaches S3. The custom error page never fires because the error is generated by the CloudFront Function, not the origin.

The fix is a separate behavior for /callback that has no function associations, letting the request pass through to S3 (which returns a 403 for the missing file), triggering the custom error page, which serves index.html.

Go to CloudFront → your distribution → Behaviors tab → Create behavior:

  • Path pattern: /callback
  • Origin: your S3 bucket
  • Viewer protocol policy: Redirect HTTP to HTTPS
  • Function associations: leave all as No association
  • Click Create behavior

Wait for the distribution to deploy, then invalidate:

aws cloudfront create-invalidation \
  --distribution-id YOUR_DISTRIBUTION_ID \
  --paths "/*"
CloudFront Behaviors tab showing the /callback behavior with no function associations

Troubleshooting

If something isn't working, work through these checks in order. Each one isolates a specific layer.

Check 1 — Authorizer rejects all requests (401 after update)

If the authorizer is rejecting every request including ones with the correct origin secret, the most likely cause is that the Secrets Manager fetch is failing.

# Test the authorizer directly with just the origin secret
curl -s https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos \
  -H "x-origin-verify: YOUR_SECRET"

If this returns {"message":"Unauthorized"}, check: the IAM policy on the authorizer role includes secretsmanager:GetSecretValue on the correct ARN; the secret name in the code matches photoviewer/origin-verify-secret; you clicked Deploy after updating the code.

Check 2 — Google login fails with redirect_uri_mismatch

This means the redirect URI you entered in Google Cloud Console doesn't match what Cognito is sending. The Cognito redirect URI must be exactly: https://YOUR_COGNITO_DOMAIN.auth.us-east-1.amazoncognito.com/oauth2/idpresponse. Check the Google Cloud Console → Credentials → your OAuth client → Authorized redirect URIs and confirm it matches exactly, including the protocol and path.

Check 3 — Callback URL returns 403 after login

After Google authentication, the browser is redirected to https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net/callback?code=XXXX. If you see a persistent 403 even after completing Steps 15 and 16, there are two possible causes: (1) the CloudFront custom error response for 403 hasn't deployed yet — wait for the distribution to show Deployed status; (2) the /callback behavior from Step 16 is missing — the default CloudFront Function blocks requests without the x-origin-verify header before they reach S3, so the custom error page never fires. Verify the /callback behavior exists in the Behaviors tab with no function associations.

Check 4 — JWT present but still seeing only 5 photos

If the Authorization header is being sent but Lambda is still filtering to public photos, check the authorizer is passing group context correctly. Go to CloudWatch → /aws/lambda/photoviewer-authorizer and look for log entries. If you see the JWT being validated but no group context, check that the user is actually in a Cognito group — go to Cognito → Users → your user → Groups tab.

Check 5 — JWT validation fails (invalid signature)

This usually means the COGNITO_USER_POOL_ID or COGNITO_APP_CLIENT_ID environment variable in the authorizer is wrong. The JWKS endpoint the authorizer fetches is derived from the User Pool ID — a wrong ID means the wrong public keys are used for verification. Double-check both values match exactly what's shown in the Cognito console.

Check 6 — Full end-to-end via CloudFront

curl -s https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net/photos

Expected: JSON array of 5 public photos. If this fails but the direct API Gateway call works, the issue is in CloudFront — verify the /photos behavior is still using the photoviewer-apigw-origin and has AllViewerExceptHostHeader as the origin request policy.

Part 8 Analyze the JWT

Now that login is working, analyze the JWT (JSON Web Token) that Cognito issues after authentication to understand how user identity and permissions are embedded in the token.

A JWT consists of three parts separated by dots: Header (algorithm), Payload (claims), and Signature (verification)

Step 1 Extract the JWT from your browser

After logging into the Photo Viewer with Google (Step 18), the JWT is stored in your browser's sessionStorage.

In your Photo Viewer page:

  1. Open DevTools (F12 or right-click → Inspect)
  2. Go to the Console tab
  3. Type: sessionStorage.getItem('pv_id_token') and press Enter
  4. Copy the entire token (long string with two dots)
Step 2 Decode the JWT at jwt.io
  1. Go to https://jwt.io
  2. Paste your JWT into the "Encoded" box on the left
  3. The decoded sections appear on the right
  4. Click the "Claims Breakdown" tab to see explanations of each claim

What you'll see: The HEADER shows the signing algorithm. The PAYLOAD contains claims about the user. Hover over timestamps like exp to see readable dates.

Step 3 Take a screenshot

Capture jwt.io showing both the encoded JWT (left) and the decoded header + payload (right). You can blur part of the encoded token for security.

Step 4 Answer the analysis questions

Based on your decoded JWT, answer these questions:

  1. What algorithm is used to sign the JWT? (Look in the HEADER section)
  2. When does your token expire? (Find the exp claim — hover over it or check the Claims Breakdown tab)
  3. What is in the cognito:username claim? What does this tell you about how you logged in?
  4. What Cognito group(s) are you in? (Look for cognito:groups. Note: If you see us-east-1_..._Google, this is the federated provider group, not the free/premium groups. Add yourself to free or premium in the Cognito console, then log in again.)
  5. What is the aud (audience) claim? Does it match your App Client ID?
  6. What is the iss (issuer) claim? What does this tell you about who issued the token?
  7. How does the Lambda authorizer use the cognito:groups claim? (Refer to your authorizer code — what groups does it check for?)
  8. What would happen if a free user modified their JWT to change "cognito:groups": ["free"] to "cognito:groups": ["premium"]? Try editing the payload in jwt.io — what happens to the signature? Would the Lambda authorizer accept this modified token? Why or why not?

Troubleshooting: If you don't see an email or name claim in your token, verify:

  • Step 1: OpenID Connect scopes include Email and Profile
  • Step 5: Attribute mapping includes email → email and name → name

If these are configured but claims are still missing, that's okay — the token still works for authentication.
