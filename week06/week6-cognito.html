User Identity and Authentication

Adding login to the Photo Viewer — federated identity with Google, JWT-based authorization, free vs premium tiers, and moving secrets out of environment variables.

Learning objectives
  • Explain the difference between authentication and authorization, and how Cognito handles each
  • Describe what a Cognito User Pool is, what it manages, and how it differs from IAM in purpose
  • Explain how federated identity works — Google authenticates, Cognito brokers, your app trusts Cognito
  • Describe what a JWT is, what claims it contains, and how the Lambda authorizer validates it
  • Explain how Cognito groups implement role-based access control at the application layer
  • Explain why storing secrets in Lambda environment variables is a security risk and how Secrets Manager addresses it
  • Describe how the Lambda authorizer is extended to handle both origin verification and identity in a single function

1. Where we left off

Week 5 delivered a fully serverless backend — Lambda, API Gateway, WAF, no servers to patch. But the Photo Viewer still has no concept of identity. Every visitor sees exactly the same thing. The DynamoDB table already has is_public and owner fields — the data model has always supported private photos and per-user access. What's been missing is knowing who is asking.

No authentication — /photos treats everyone the same Fixed this week

The limitation: Any request to /photos returns all public photos regardless of who is asking. API Gateway passes every request to Lambda without any identity context. The WAF rate-based rule limits flooding but has no concept of identity — it cannot distinguish a free user from a premium user.

Why it matters: The DynamoDB table already has is_public and owner fields. Private photos exist in the data model but Lambda always filters is_public = true because it has no way to know if the caller is entitled to see more. There is no login, no session, no way to build a premium tier.

Fixed this week: Amazon Cognito adds a User Pool with Google as a federated identity provider. Users log in via Google through the Cognito Hosted UI. Cognito issues a JWT. The Lambda authorizer validates the JWT on every request and passes the user's group membership to the main Lambda function. Lambda now knows who is asking and filters DynamoDB accordingly.

x-origin-verify secret in a Lambda environment variable Fixed this week

The vulnerability: The x-origin-verify secret — the value CloudFront adds to every origin request so the Lambda authorizer can reject direct calls — is currently stored as a Lambda environment variable. Environment variables in Lambda are:

  • Visible in plaintext in the AWS console to anyone with lambda:GetFunction permission
  • Potentially logged if a function accidentally prints its environment
  • Statically configured — rotation requires a function update and redeployment
  • Not audited — no CloudTrail event when the value is read by the function

Fixed this week: The secret is moved to AWS Secrets Manager. The Lambda authorizer fetches it at runtime using secretsmanager:GetSecretValue. The secret is no longer visible in the Lambda console, can be rotated without touching the function code, and every retrieval is logged in CloudTrail.

Week 6 adds identity to the Photo Viewer in two layers — who you are (authentication via Cognito + Google) and what you can see (authorization via Cognito groups). The Lambda authorizer is extended to handle both origin verification and identity validation in a single function. The origin secret moves to Secrets Manager.

3. Architecture

Week 6 adds Cognito alongside the existing stack. The core request path — CloudFront → API Gateway → Lambda → DynamoDB — is unchanged. Cognito sits to the side: it handles the login flow separately and issues a JWT that the browser then uses on subsequent API requests.

Login flow — Authorization Code via Cognito Hosted UI (one time)

API request flow — every /photos call

Key architectural point — Cognito is not in the request path

Cognito handles the login flow — it issues the JWT. But Cognito is not involved in validating every API request. The Lambda authorizer validates the JWT directly using Cognito's published public keys (JWKS endpoint). This means API Gateway does not need to call Cognito on every request — validation happens locally in the authorizer function. This is why JWTs scale well: the issuer (Cognito) doesn't need to be consulted every time.

4. How a request flows

Why one Lambda authorizer handles both checks: HTTP API Gateway supports only one authorizer per route. Rather than choosing between origin verification and JWT validation, the authorizer does both — first checks x-origin-verify (required, rejects if missing), then optionally validates the JWT if an Authorization header is present. Three outcomes: no origin secret → rejected; origin secret ✓ + no JWT → unauthenticated; origin secret ✓ + valid JWT → authenticated with group context.

5. Key concepts

Components

🏛
Amazon Cognito
Managed user directory · federated identity · groups · issues JWTs
▼

Amazon Cognito is AWS's managed identity service for application users — it handles who can access your application, not who can access your AWS account. Cognito has two distinct components that serve different purposes.

User Pool vs Identity Pool

User Pool — a managed user directory. Handles login, registration, and token issuance. Users authenticate and receive a JWT that your application validates. This is the right tool when users need to access your application.

Identity Pool (aka Cognito Federated Identities) — exchanges an identity token (from a User Pool, Google, or other IdP) for temporary AWS credentials via STS. Those credentials let the client call AWS services directly — S3, DynamoDB — without going through your backend. This is the right tool when the client needs direct access to AWS resources.

Cognito User Pool — details

A User Pool stores user accounts and handles the authentication flow. It supports two ways to manage users:

  • Native users — username/password accounts created and managed directly in Cognito
  • Federated identity providers — users log in via Google, Facebook, Apple, or any SAML/OIDC provider. Cognito acts as the broker and issues its own JWT regardless of which provider was used

User Pool groups

Users within a User Pool can be assigned to groups. When a user is in a group, their JWT includes a cognito:groups claim listing their memberships. Your Lambda reads this claim and decides what the user can do — no additional database lookup needed.

Groups are managed in the Cognito console. Changes take effect on the user's next login — the new membership is reflected in the next JWT issued.

How the Photo Viewer uses Cognito

The Photo Viewer uses a Cognito User Pool with Google as a federated identity provider. Cognito handles the full OAuth2 Authorization Code flow — holding the client secret and exchanging the auth code with Google server-to-server. The browser only ever receives Cognito's own JWT.

The User Pool has two groups — free and premium. The Lambda authorizer extracts the cognito:groups claim and passes it to the main Lambda, which uses it to filter DynamoDB results:

AWS Secrets Manager
Centralized secret storage · rotation · CloudTrail audit · never in env vars
▼

AWS Secrets Manager is a managed service for storing, retrieving, and rotating secrets — API keys, database credentials, OAuth tokens, and custom values. Unlike environment variables which are baked into the Lambda function configuration, Secrets Manager stores secrets externally and provides them on demand at runtime. Access is controlled by IAM and every retrieval is logged in CloudTrail.

Security concepts

🔗
OAuth 2.0 and OIDC
Authorization framework · identity layer · Authorization Code flow · three-party model
▼

OAuth 2.0 is an authorization framework — it defines how one application can grant another limited access to resources on a user's behalf, without sharing passwords. It defines several flows (grant types) for different scenarios. The Photo Viewer uses the Authorization Code flow — the most secure option for server-side applications.

OIDC (OpenID Connect) is an identity layer built on top of OAuth 2.0. OAuth 2.0 alone only handles authorization (what you can access) — it says nothing about who you are. OIDC adds authentication by defining a standardized ID token (a JWT) that carries identity claims. Google implements OIDC, which is what makes it suitable as a Cognito identity provider.

Three parties

Identity Provider (IdP) — Google: Verifies the user's identity via their Google account. Issues a short-lived authorization code directly to Cognito's callback URL — the browser never sees it.

Broker — Cognito: Holds the Google OAuth2 client secret. Exchanges the auth code with Google server-to-server, receives Google's tokens, then issues its own JWT to the browser. Your app never talks to Google directly.

Relying Party — Photo Viewer: Trusts Cognito's JWT. Validates the signature using Cognito's published public keys (JWKS endpoint). Never sees the auth code, the client secret, or Google's tokens.

Why broker through Cognito rather than trusting Google directly? If you trusted Google JWTs directly, adding a second identity provider would require changes throughout your application. With Cognito as the broker, your Lambda authorizer always validates the same Cognito JWT format — regardless of whether the user signed in with Google, Facebook, or a native Cognito account.

🎫
JSON Web Token (JWT) — identity mechanism
Header · payload · signature · self-contained · stateless · expiry
▼

A JWT is a compact, self-contained token that carries claims about a user. It has three parts separated by dots: header.payload.signature. Each part is Base64URL-encoded.

Header Algorithm and token type
{"alg": "RS256", "typ": "JWT"}
Payload — claims sub: unique user ID
email: user's email
cognito:groups: ["premium"]
exp: expiry timestamp
iss: issuer (Cognito pool URL)
Signature Signed with Cognito's private key.
Verified using Cognito's public key (JWKS endpoint).

Self-contained: The Lambda authorizer verifies the JWT locally using Cognito's published public keys — Cognito is not called on every request. This is why JWT-based auth scales well.

Stateless: No session is stored server-side. Any Lambda instance can validate any JWT independently.

JWTs are not encrypted — only signed

The payload is Base64URL-encoded, not encrypted. Anyone with the JWT can read its claims. Never put sensitive data in a JWT payload — the signature only guarantees the claims have not been tampered with.

Tokens Cognito issues at login

TokenExpiryPurpose
ID token1 hourContains identity claims — what your Lambda authorizer validates
Access token1 hourUsed to call Cognito APIs — not used by your authorizer

When the ID token expires after 1 hour, app.js clears it and returns to the logged-out view, and the user clicks Login to sign in again. Cognito manages its own session independently of Google's, so signing in again is usually quick — it doesn't go back to Google.

Premium user's functionality not yet implemented

The limitation: Cognito groups are fully configured and the JWT groups claim is read by the Lambda authorizer — but free and premium users currently see the same data, and premium users have no upload capability. The group infrastructure is in place but has no visible effect beyond unauthenticated vs authenticated.

What's next: Week 7 adds the capability layer. Premium users gain upload via S3 presigned PUT URLs. Uploaded photos are tracked by owner in DynamoDB. Users can delete their own uploads, with Lambda validating object-level ownership. Week 7 demonstrates two authorization patterns: endpoint-level (premium-only upload) and object-level (owner-only delete). The cognito:groups claim set up this week is exactly what Week 7's authorization checks will use.

How to verify groups are working in the lab: The meaningful test in Week 6 is unauthenticated vs authenticated. Seed one or two DynamoDB items with is_public = false — unauthenticated users should not see them, any logged-in user should.

Private photos are hidden from the catalog, but still fetchable from S3
click to expand

The limitation: Adding login gives is_public = false a privacy meaning it did not carry before — "only logged-in users should see these." But that filter is applied only to the /photos list response returned by Lambda. The S3 objects themselves are served via CloudFront with Origin Access Control, which has no concept of identity or ownership. Anyone who knows or guesses the CloudFront URL for a private photo can fetch the image, regardless of the is_public flag.

Catalog filtering ≠ object-level access control. Filtering the list hides the pointer. It does not hide the object.
