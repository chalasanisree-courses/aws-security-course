Understanding how authentication works with Cognito, Google, and your Photo Viewer app

Why You Might Get Auto-Logged Back In

If you click "Sign in" again right after logout, you might get authenticated instantly without seeing the Google login screen. This is normal — you're still logged into Google itself. Google's session is still active, so it issues a new auth code immediately without asking for your password again. This is how Single Sign-On works: authenticate once with Google, access many apps seamlessly.

Good to Know

Two Different Auth Codes

The OAuth flow involves two separate auth codes — they're not the same!

Google's auth code: Issued by Google, sent to Cognito. You don't see it (server-to-server). Cognito exchanges this with Google for tokens.

Cognito's auth code: Issued by Cognito, sent to your app. You see it in the URL as ?code=.... app.js exchanges this with Cognito for the JWT.

Why Cognito Acts as a Broker

Instead of your app trusting Google JWTs directly, Cognito sits in the middle. Cognito handles the Google exchange (holds the client secret securely) and issues a normalized JWT in its own format. Your Lambda authorizer always validates the same Cognito JWT — regardless of which identity provider the user chose. Want to add Facebook login later? Just configure it in Cognito — zero code changes in your authorizer. This is federated identity: one validation flow in your code, many identity providers supported.

Google OAuth Client Secret vs x-origin-verify Secret

Week 6 involves two different secrets:

Google OAuth client secret: Created in Google Cloud Console (Step 4), pasted into Cognito's identity provider configuration (Step 5). Stored server-side in Cognito. Cognito uses it to exchange auth codes with Google. This does not go in Secrets Manager.

x-origin-verify secret: Moved from Lambda environment variable to Secrets Manager (Steps 7-9). Used between CloudFront and API Gateway to reject direct API calls.
