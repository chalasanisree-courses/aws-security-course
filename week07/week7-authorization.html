Authorization Patterns

Week 7 — Presigned URLs, ownership checks, and group-based access control. Premium users can upload, delete, and control visibility of their own photos. The Cognito groups infrastructure from Week 6 now drives real capability differences.

Learning objectives
  • Explain the difference between endpoint-level authorization (RBAC) and object-level authorization (ownership), and why both are necessary
  • Describe how S3 presigned URLs work — PUT for upload, GET for retrieval — and what security properties they provide (time-limited, operation-scoped, key-scoped)
  • Explain how presigned URL conditions enforce server-side file validation without a Lambda invocation
  • Describe why CORS is required for browser-based S3 uploads and what the same-origin policy protects against
  • Explain how CloudTrail logs presigned URL operations and why "bypassing API Gateway" does not mean "bypassing audit"
  • Describe Broken Object-Level Authorization (BOLA/IDOR) and how the ownership check prevents it

The limitation: The JWT contains a cognito:groups claim and the Lambda authorizer extracts it — but the main Lambda does not use it. Free and premium users see the same data, and neither group can upload, delete, or edit anything. The group infrastructure exists but the capability layer does not.

Fixed this week: Three new API endpoints are gated to the premium group: upload (presigned PUT URL), delete (owner-only), and visibility toggle (owner-only). The Lambda checks cognito:groups on every mutation request and rejects non-premium users with a 403.

Private photos are hidden from the catalog but still fetchable from S3 Fixed this week

The limitation: The is_public flag filters the /photos list response, but the S3 objects themselves are served via CloudFront with OAC. Anyone who knows or guesses the CloudFront URL for a private photo can fetch the image directly.

Fixed this week: User-uploaded photos are stored under the uploads/ prefix in S3. The CloudFront Function is updated to block any request to the uploads/ path, returning 403. The /photos API response includes Lambda-generated S3 presigned GET URLs for uploaded photos — short-lived, scoped, and only issued to users entitled to see the photo. If a photo does not appear in your list response, you never receive a URL to fetch it.

3. Architecture

The core request path — CloudFront → API Gateway → Lambda authorizer → Lambda → DynamoDB — is unchanged from Week 6. What changes is that the main Lambda now handles four routes instead of one, and it interacts with S3 directly for presigned URL generation and object deletion.

Browse flow — GET /photos (any user)

Upload flow — two steps (premium only)

Why two steps?

API Gateway has a 6 MB payload limit. Presigned URLs bypass the API entirely — the browser uploads directly to S3, which supports objects up to 5 GB. Lambda is only involved in Step 1 (authorization + URL generation), not Step 2 (actual file transfer). This is how production file upload systems work.

Generates a photo_id, constructs s3_key = uploads/{cognito:sub}/{photo_id}.jpg, and writes the metadata record: photo_id, title, is_public, owner, s3_key, uploaded_at.

Lambda generates presigned PUT URL

Calls s3.getSignedUrl('putObject', ...) with a 15-minute TTL scoped to the s3_key. Returns { uploadUrl, photoId } to the browser.

6
Browser uploads directly to S3

app.js sends a PUT request with the file bytes to the presigned URL. The request goes directly to S3 — no Lambda, no API Gateway, no 6 MB payload limit. S3 validates the signature, checks the TTL, and stores the object.

What if the upload never happens? The DynamoDB record is created in Step 4 before the file is uploaded in Step 6. If the browser upload fails or the user closes the tab, an orphaned metadata record exists with no backing S3 object. A production system would use S3 event notifications to create metadata only after a confirmed upload. For this lab, orphaned records are an acceptable tradeoff — and a good interview-level discussion topic.

JWT in the Authorization header. For PATCH, the body contains { "is_public": false }.

2

Same as upload: origin secret + JWT validation. Group context passed through.

3
Main Lambda — checks premium group

If user is not in the premium group → 403 Forbidden. Same endpoint-level gate as upload.

4
Main Lambda — checks ownership

Fetches the item from DynamoDB using the photoId path parameter. Compares the item's owner field to the caller's cognito:sub from the JWT. If they do not match → 403 Forbidden. This is object-level authorization.

5
Lambda performs the action

Delete: Deletes the S3 object using s3.deleteObject(), then removes the DynamoDB record.

Toggle: Updates the is_public field in DynamoDB using UpdateItem. The S3 object is unchanged — visibility is controlled by whether the photo appears in future /photos list responses.

Why two checks (group + ownership)? The group check gates the capability — only premium users can mutate. The ownership check gates the scope — premium users can only mutate their own photos. A premium user cannot delete another premium user's upload. These are two independent security properties: endpoint-level authorization (RBAC) and object-level authorization (ABAC). Both must pass.

5. Key concepts

Components

🔗
S3 Presigned URLs
Time-limited, operation-scoped URLs that carry authorization in the query string
▼

A presigned URL is a regular S3 URL with additional query-string parameters that embed temporary credentials: a signature, an expiration timestamp, and the allowed operation. The URL is generated server-side by a principal (Lambda's execution role) that has the necessary S3 permissions. Anyone who receives the URL can perform the specified operation on the specified object — no AWS credentials needed — until the URL expires.

Security properties

  • Time-limited: The URL expires after the TTL. After expiry, S3 rejects the request with 403 AccessDenied.
  • Operation-scoped: A PUT URL cannot be used for GET, and vice versa.
  • Key-scoped: Each URL is bound to one specific S3 key. It cannot be modified to access a different object.
  • No credential exposure: The signature is derived from the Lambda role's credentials, but the credentials themselves are not in the URL.
  • Shareable within TTL: Anyone who obtains the URL can use it until it expires. This is by design for GET (the browser needs it to render <img src>), but is a consideration for PUT (keep TTLs short).

Presigned URL conditions

The server can embed conditions in the presigned URL that S3 enforces on upload. If a condition is violated, S3 rejects the request — even though the URL signature is otherwise valid.

ConditionWhat it enforcesIn this lab
Content-TypeOnly allows specific MIME typesimage/jpeg or image/png
Content-Length-RangeMin/max file size in bytes0 – 5 MB (5,242,880 bytes)

Conditions are part of the signed policy — the client cannot remove or modify them without invalidating the signature. This provides partial server-side file validation without a Lambda invocation on upload. It does not replace full validation (magic bytes, virus scanning) but it rejects obviously wrong uploads at the S3 layer.

CloudTrail audit

Operations performed via presigned URLs are logged in CloudTrail just like any other S3 API call. The PutObject event records the IAM principal that generated the presigned URL (the Lambda execution role), the S3 key, the timestamp, and the source IP of the client that used the URL. This means "bypassing API Gateway" for the file upload does not mean "bypassing audit" — CloudTrail sees everything.

This connects back to Week 1: the all-regions CloudTrail trail you created in your first lab captures these events automatically. Every upload and every deletion in Week 7 is auditable.

Presigned URLs are bearer tokens

There is no additional identity check when the URL is used. If a presigned GET URL is leaked, anyone can fetch the photo until the TTL expires. This is why the TTL for GET is short (5 minutes) and why the URL is regenerated on every /photos call. It is not a persistent link.

🌐
S3 CORS (Cross-Origin Resource Sharing)
Browser security policy that gates cross-origin requests — must be configured for presigned PUT
▼

Browsers enforce the same-origin policy: JavaScript on one origin (e.g. https://d1234.cloudfront.net) cannot make HTTP requests to a different origin (e.g. https://photoviewer-9876543210.s3.us-east-1.amazonaws.com) unless the target explicitly permits it. This is a browser-side security control — it does not apply to server-side calls, CLI tools, or curl.

When app.js sends a PUT request to a presigned S3 URL, the browser sees a cross-origin request and performs a preflight check: it sends an OPTIONS request to S3 asking "does this origin allow PUT requests?" If S3 has no CORS configuration, the browser blocks the upload before it even starts — the presigned URL's authorization is irrelevant because the browser never sends the actual request.

What the S3 CORS configuration does

CORS rules on the bucket tell S3 how to respond to preflight OPTIONS requests:

  • AllowedOrigins: Which domains can make cross-origin requests (your CloudFront domain)
  • AllowedMethods: Which HTTP methods are allowed (PUT for uploads)
  • AllowedHeaders: Which request headers the browser is allowed to send (Content-Type)

CORS is a browser-side control, not a server-side one

CORS does not protect S3. A curl command or any non-browser client ignores CORS entirely and uses the presigned URL directly. The presigned URL is the server-side authorization — CORS just determines whether the browser will send the request. They solve different problems: CORS is about browser sandboxing, presigned URLs are about S3 access control.

Security concepts

🚧
Endpoint-level authorization (RBAC)
Can this user call this endpoint at all? — checked before processing the request
▼

Role-Based Access Control (RBAC) grants or denies access based on the user's role or group membership. In the Photo Viewer, the Lambda function checks whether the caller is in the premium Cognito group before processing any POST, DELETE, or PATCH request. If the user is in the free group (or has no group at all), the request is rejected with 403 — the function never reaches the business logic.

This check answers one question: is this user allowed to perform this type of action? It does not answer who owns the target resource — that is object-level authorization.

Object-level authorization (ownership)
Does this user own this specific resource? — checked per item
▼

Object-level authorization checks whether the caller has the right to act on a specific resource, not just a class of actions. In the Photo Viewer, the Lambda function fetches the target photo's DynamoDB record and compares the owner field to the caller's cognito:sub. If they do not match, the request is rejected — even if the caller is in the premium group.

This check answers: is this specific photo yours?

BOLA / IDOR — the #1 API vulnerability

Broken Object-Level Authorization (BOLA), also known as Insecure Direct Object Reference (IDOR), is the most common API vulnerability in the OWASP API Security Top 10. It occurs when an API accepts an object identifier (like photoId) from the client and uses it to fetch or modify data without verifying that the caller owns or is entitled to that object.

Example attack: Alice is a premium user. She uploads a photo and gets photoId = abc123. She inspects the network request when she deletes one of her photos and sees it calls DELETE /photos/abc123. She tries DELETE /photos/xyz789 — Bob's photo. Without an ownership check, Lambda would delete Bob's photo because Alice has the premium group (endpoint-level check passes) and the API takes the photoId at face value.

The fix: Before performing any mutation, Lambda fetches the DynamoDB record and checks item.owner === caller.sub. If it does not match, return 403. This single check prevents the entire class of BOLA attacks.

Two checks, two properties: Endpoint-level authorization (group check) and object-level authorization (ownership check) protect different things. The group check prevents free users from accessing mutation endpoints. The ownership check prevents premium users from accessing each other's data. Both must pass.

6. What's still missing

Click to expand.

No file validation on upload
click to expand

The limitation: The presigned PUT URL accepts any file the browser sends. There is no server-side check on file type (the Content-Type header is client-controlled), file size, or file content. A premium user could upload a 500 MB executable, a PHP script, or a file with embedded malware — S3 will store whatever arrives.

What production systems do: Validate Content-Type and magic bytes on upload, enforce file size limits via presigned URL conditions, scan uploaded files with antivirus (Lambda + ClamAV or a third-party service), and reject non-image files before they reach the photo catalog.

User uploads share the same S3 bucket as the static site
click to expand

The limitation: User-uploaded files land in the same S3 bucket that hosts the Photo Viewer HTML, CSS, and JavaScript. Although uploads go to the uploads/ prefix and the CloudFront Function blocks direct access to that path, a misconfiguration could expose untrusted content alongside application code.

What production systems do: Use a separate S3 bucket for user-generated content. This isolates untrusted uploads from application assets, allows different bucket policies, lifecycle rules, and access logging, and limits the blast radius of a compromised upload.

Orphaned metadata records if upload fails
click to expand

The limitation: The DynamoDB metadata record is created in the POST /photos handler (Step 1) before the browser uploads the file (Step 2). If the upload fails or the user closes the browser, a metadata record exists with no backing S3 object.

What production systems do: Create metadata only after a confirmed upload using S3 event notifications — when S3 receives the object, it triggers a Lambda that writes the DynamoDB record. Alternatively, mark records as pending on creation and promote to active via an S3 event, with a TTL that cleans up stale pending records.
