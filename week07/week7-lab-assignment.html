Week 7 Lab — Upload & Delete with Access Control

CS 55D: Security in Amazon Web Services  ·  Foothill College  ·  125 pts

Objective: Add upload, delete, and visibility-toggle capabilities to the Photo Viewer — all restricted to premium users and scoped to their own uploads. Update photo delivery so user-uploaded photos are served via presigned GET URLs instead of static CloudFront URLs. By the end of this lab, Cognito groups will drive real capability differences: premium users can upload, delete, and control visibility of their own photos, while free users can only browse.

Architecture after this lab: Browser → WAF/CloudFront → API Gateway (4 routes) → Lambda authorizer (origin secret + JWT) → main Lambda (group check + ownership check) → DynamoDB + S3 (presigned URLs for uploads)

Two authorization patterns in this lab:

Endpoint-level (RBAC): POST, DELETE, and PATCH routes are restricted to the premium Cognito group. Free users get 403.

Object-level (ownership): DELETE and PATCH check that item.owner === caller.sub before acting. Premium users cannot modify each other's photos.

Part 1 Block direct CloudFront access to uploads

User-uploaded photos will be stored under the uploads/ prefix in S3. They should only be accessible via presigned GET URLs — not via CloudFront. You will create a new CloudFront behavior that blocks any request to the /uploads/* path.

Step 1 Create a CloudFront Function to block uploads

Go to CloudFront → Functions → Create function. Name it photoviewer-block-uploads. In the Build tab, replace the default code with:

function handler(event) {
    return {
        statusCode: 403,
        statusDescription: 'Forbidden'
    };
}

Click Save changes, then go to the Publish tab and click Publish function.

Step 2 Add a /uploads/* behavior to CloudFront

First, update the existing /photos behavior. Week 7 adds routes like DELETE /photos/{photoId} — CloudFront's exact path /photos won't match /photos/abc123, so those requests would fall through to the S3 default behavior and fail. Go to CloudFront → your distribution → Behaviors tab, select the /photos behavior, click Edit, and change the path pattern to /photos*. Save changes.

Why /photos* instead of /photos? CloudFront path matching is literal. /photos matches only the exact path /photos. The wildcard pattern /photos* matches both /photos (GET, POST) and /photos/abc123 (DELETE, PATCH). Without this change, mutation requests would never reach API Gateway.

Next, create the new /uploads/* behavior. Click Create behavior.

  • Path pattern: /uploads/*
  • Origin: select your S3 origin (photoviewer-[your-account-id].s3...)
  • Viewer protocol policy: Redirect HTTP to HTTPS
  • Cache policy: CachingOptimized
  • Function associations → Viewer request: CloudFront Functions → select photoviewer-block-uploads

Click Create behavior. Your behaviors tab should now show four behaviors:

PrecedencePath patternOriginPurpose
0/photos*API GatewayAPI routes (W5, updated W7)
1/callbackS3OAuth redirect (W6)
2/uploads/*S3Block direct access (W7)
3Default (*)S3HTML/JS/CSS + pre-seeded photos

Why a separate behavior? CloudFront evaluates behaviors by path specificity. Requests to /uploads/photo.jpg match the /uploads/* behavior (which returns 403) before they reach the Default (*) behavior (which would serve the file from S3). The existing allowlist function on the default behavior is unchanged from Week 5 — each week's work is additive.

✓ Verify

Test the block by visiting https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net/uploads/test.jpg — you should see a 403 response.

Part 2 Configure S3 bucket — IAM permissions and CORS

The main Lambda needs S3 permissions to generate presigned URLs and delete objects. The bucket also needs a CORS configuration so the browser can upload directly to S3 from your CloudFront domain.

Step 3 Create an inline policy for uploads

Go to Lambda → Functions → photoviewer-lambda → Configuration tab → Permissions. Under Execution role, click the role name link — this opens the exact IAM role that this function uses. Click Add permissions → Create inline policy → JSON and paste:

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "PhotoViewerUploads",
            "Effect": "Allow",
            "Action": [
                "s3:PutObject",
                "s3:GetObject",
                "s3:DeleteObject"
            ],
            "Resource": "arn:aws:s3:::photoviewer-[your-account-id]/uploads/*"
        }
    ]
}

Name the policy photoviewer-uploads. Click Create policy.

Least privilege: The Resource is scoped to the uploads/* prefix only. Lambda cannot read, write, or delete objects in the root of the bucket (where your HTML/CSS/JS live). This is the same least-privilege principle from Week 6's Secrets Manager policy — scope to the specific resource ARN, not *.

Why does this work when the bucket policy only names CloudFront? Your Week 3 bucket policy allows s3:GetObject for the CloudFront service principal — it does not mention Lambda. But the policy has no explicit Deny. For same-account IAM principals like your Lambda role, S3 evaluates the IAM policy and the bucket policy together. If the IAM policy explicitly allows the action and the bucket policy does not explicitly deny it, access is granted. Block Public Access stays on and has no effect here — Lambda's requests are authenticated IAM requests, not public ones.

IAM role showing the photoviewer-uploads inline policy attached
Step 4 Configure CORS on the S3 bucket

When the browser uploads a file to the presigned S3 URL, it is a cross-origin request — your app runs on https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net but the PUT goes to https://photoviewer-[your-account-id].s3.us-east-1.amazonaws.com. Without CORS, the browser blocks the upload before it starts.

Go to S3 → your bucket → Permissions tab → scroll to Cross-origin resource sharing (CORS) → Edit and paste:

[
    {
        "AllowedHeaders": ["Content-Type"],
        "AllowedMethods": ["PUT"],
        "AllowedOrigins": ["https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net"],
        "ExposeHeaders": ["ETag"],
        "MaxAgeSeconds": 3600
    }
]

Replace YOUR_CLOUDFRONT_DOMAIN with your actual CloudFront domain. Click Save changes.

Why only PUT? The CORS rule only allows the PUT method because that is the only cross-origin S3 operation the browser performs. GET requests for presigned photo URLs also go directly to S3, but browsers do not enforce CORS preflight for <img src> tags — image loading is exempt from the same-origin policy. Only programmatic fetch() or XMLHttpRequest calls (like the upload PUT) trigger CORS.

Do not use * for AllowedOrigins. Wildcards allow any website to upload to your bucket using a presigned URL. Always restrict to your specific CloudFront domain.

S3 bucket Permissions tab showing the CORS configuration with your CloudFront domain
Part 3 Add API Gateway routes

Add three new routes to your existing HTTP API. All routes point to the same photoviewer-lambda function and use the same Lambda authorizer — the function handles routing internally based on the HTTP method and path.

The five HTTP calls in app.js — four to API Gateway, plus one direct-to-S3 PUT:

  1. GET /photos — list photos (with the url field already populated by Lambda)
  2. POST /photos — request a presigned PUT URL + create the DynamoDB record
  3. PUT {presignedUrl} — browser uploads bytes straight to S3, bypassing API Gateway
  4. DELETE /photos/{photoId} — remove S3 object + DynamoDB item
  5. PATCH /photos/{photoId} — flip is_public

How GET /photos maps to user tiers — Lambda branches on what the authorizer tells it:

CallerWhat authHeaders() sendsLambda returns
Unauthenticatedno Authorization headeritems where is_public=true
FreeAuthorization: Bearer <jwt>, no premium in cognito:groupsall items
PremiumAuthorization: Bearer <jwt>, premium in groupsall items (+ frontend shows owner controls where photo.owner === sub)
Step 5 Create the POST /photos route

Go to API Gateway → your HTTP API → Routes → Create.

  • Method: POST
  • Path: /photos

Click Create. Then click the new route → Attach integration → select your existing photoviewer-lambda integration. Then click Attach authorization → select your existing Lambda authorizer.

Step 6 Create the DELETE /photos/{photoId} route

Create another route:

  • Method: DELETE
  • Path: /photos/{photoId}

Attach the same Lambda integration and the same authorizer.

Path parameter: The {photoId} in the path is a variable. API Gateway extracts the value and passes it to Lambda in event.pathParameters.photoId. This is how Lambda knows which photo the client wants to delete.

Create the third route:

  • Method: PATCH
  • Path: /photos/{photoId}

Attach the same Lambda integration and authorizer.

Part 4 Deploy updated Lambda code

Two Lambda functions need updates. The authorizer now passes the caller's identity (sub) alongside group membership. The main Lambda uses that identity for ownership checks on delete and toggle.

Step 9 Update the Lambda authorizer

The authorizer from Week 6 passes only groups in its context. Week 7's ownership checks need the caller's sub (cognito:sub from the JWT) — without it, Lambda cannot verify who owns a photo. In CloudShell:

cd ~/aws-security-course/photoviewer/week07
zip -j authorizer.zip authorizer.py
aws lambda update-function-code \
    --function-name photoviewer-authorizer \
    --zip-file fileb://authorizer.zip
aws lambda wait function-updated-v2 --function-name photoviewer-authorizer

What changed: One line in the authorizer response — 'sub': sub is added to the context dict alongside 'groups'. The JWT validation, origin secret check, and everything else is unchanged from Week 6.

Step 10 Update the main Lambda function

In CloudShell, run:

cd ~/aws-security-course/photoviewer/week07
zip -j lambda-function.zip lambda/lambda_function.py
aws lambda update-function-code \
    --function-name photoviewer-lambda \
    --zip-file fileb://lambda-function.zip

Wait for the update to complete:

aws lambda wait function-updated-v2 --function-name photoviewer-lambda

What changed in the code: The handler reads event['routeKey'] to determine which route was called (e.g. GET /photos, POST /photos, DELETE /photos/{photoId}). Mutation routes check cognito:groups from the authorizer context. DELETE and PATCH also fetch the DynamoDB item and compare owner to the caller's sub. The GET handler generates presigned GET URLs for items with an s3_key starting with uploads/.

Presigned URL conditions: The POST handler generates the presigned PUT URL with embedded conditions: Content-Type must be image/jpeg or image/png, and file size must be under 5 MB. These conditions are part of the signed policy — S3 enforces them on upload and rejects requests that violate them, even though no Lambda runs during the upload itself.

✓ Verify

Run aws lambda get-function --function-name photoviewer-lambda --query 'Configuration.LastModified' — should show a recent timestamp.

Step 11 Set the S3 bucket name as an environment variable

The Lambda function needs to know the bucket name for presigned URL generation. Go to Lambda → Functions → photoviewer-lambda → Configuration tab → Environment variables → Edit.

Click Add environment variable:

  • Key: PHOTO_BUCKET
  • Value: photoviewer-[your-account-id] (your actual bucket name)

Click Save.

Not a secret: The bucket name is not sensitive — it is a configuration value, not a credential. Environment variables are appropriate here. Secrets (like the origin-verify token) go in Secrets Manager. Configuration values (like bucket names, table names, region) go in environment variables.

Step 12 Assign your Cognito user to the premium group

Go to Cognito → your User Pool → Users. Find your user (the one you logged in with via Google in Week 6). Click on the username → Group memberships → Add user to group → select premium → Add.

Step 21 Test presigned URL conditions

Switch your user back to the premium group, log out, and log back in. Upload a valid JPEG — this should succeed. Then test the conditions:

Test 1 — wrong Content-Type: The presigned URL has a Content-Type condition embedded. Test it from CloudShell using the presigned URL from a successful POST /photos response:

# Use the uploadUrl from a POST /photos response
curl -X PUT "PRESIGNED_URL_HERE" \
  -H "Content-Type: text/plain" \
  --data-binary "this is not an image"

S3 should reject with 403 AccessDenied because the Content-Type does not match the signed condition.

Test 2 — file too large: Find or create an image file larger than 5 MB. Try uploading it through the UI. The presigned URL has a Content-Length-Range condition (max 5,242,880 bytes). S3 should reject the upload.

Where is the validation happening? No Lambda runs during the upload — the browser sends the file directly to S3. S3 itself enforces the conditions that were embedded in the presigned URL at signing time. This is server-side validation without a server invocation.

DevTools Network tab showing S3 rejecting an invalid upload (403 response on the PUT request)
Part 8 CloudTrail verification

Presigned URL operations bypass API Gateway and Lambda, but they do not bypass CloudTrail. Every S3 operation is logged — the audit trail from Week 1 captures everything.

Step 22 Find your upload and delete events in CloudTrail

Go to CloudTrail → Event history. Filter by:

  • Event source: s3.amazonaws.com
  • Event name: PutObject

Find the event for the photo you uploaded. Click to expand it and note:

  • userIdentity → arn: This is the Lambda execution role that generated the presigned URL — not the end user. CloudTrail records the IAM principal that signed the URL.
  • sourceIPAddress: This is the IP of the browser that used the presigned URL — the actual uploader.
  • requestParameters → key: The S3 key (e.g. uploads/{sub}/{photoId}.jpg).

Now filter by DeleteObject and find the event for the photo you deleted in Step 19. The same fields are present.

Why this matters: "Bypassing API Gateway" sounds like it might bypass audit — it does not. Every presigned URL operation is an S3 API call, and CloudTrail logs every S3 API call. The Lambda role's identity in the event tells you which function signed the URL. The source IP tells you who used it. This is the same CloudTrail trail you created in Week 1 — it has been capturing these events all along.

CloudTrail Event history showing a PutObject event with the Lambda role ARN and the uploads/ key path
Part 9 Reflection questions

Question 1

The browser uploads the photo file directly to S3 using a presigned PUT URL — it does not send the file through API Gateway or Lambda. Explain why this design is used instead of uploading through the API. Identify at least two specific technical limitations that presigned URLs avoid.

Question 2

A presigned GET URL is included in the /photos response for each uploaded photo. If a logged-in user copies that URL and shares it with someone who is not logged in, what happens? How does the TTL limit the exposure, and what is the residual risk?

Question 3

This lab implements two authorization checks on the DELETE endpoint: a group check (is the user premium?) and an ownership check (does the user own this photo?). Explain what attack each check prevents independently. Then explain why both checks are necessary — what would happen if you removed one but kept the other?
