Week 8 Lab — Encryption at Rest with KMS

CS 55D: Security in Amazon Web Services  ·  Foothill College  ·  100 pts

Objective: Replace AWS-managed encryption with customer-managed KMS keys across S3, DynamoDB, and Secrets Manager. Create two keys with distinct key policies to enforce separation of duties. Update the Lambda function to use Signature Version 4 and include KMS encryption parameters in presigned URLs. Demonstrate that KMS key policies create an authorization layer independent of IAM, and use CloudTrail to audit decryption events.

What changes this week: Two KMS keys are created. Encryption is switched on three services. The Lambda function is updated to use SigV4 and include KMS parameters in presigned PUT URLs. The frontend is updated to send encryption headers. S3 CORS is updated to allow encryption headers. No new API routes or UI features — the changes are invisible to the user.

Pre-flight checklist

Run the pre-flight script from CloudShell before starting:

cd ~
git -C aws-security-course pull
bash aws-security-course/photoviewer/week08/week8-preflight.sh

The script verifies your Week 7 environment is intact: Lambda functions, DynamoDB table, S3 bucket, CloudFront distribution, Cognito User Pool with groups, and Secrets Manager secret. Address any errors before proceeding.

Part 1 Create the KMS keys
Step 1 Create the photoviewer-infra-key

Go to KMS → Customer managed keys → Create key.

  • Key type: Symmetric
  • Key usage: Encrypt and decrypt
  • Alias: photoviewer-infra-key
  • Description: Encrypts infrastructure secrets (origin-verify, future credentials)

On the Define key administrative permissions page, select your IAM admin user. On the Define key usage permissions page, select the Lambda authorizer execution role (photoviewer-authorizer-role-*). This is the role that reads the origin secret from Secrets Manager on every request.

Why the authorizer role? When Secrets Manager encrypts the secret with this key, any principal that reads the secret also needs kms:Decrypt permission on the key. The authorizer Lambda reads the secret on every invocation — so its execution role must be in the key policy.

Step 2 Create the photoviewer-data-key

Go to KMS → Customer managed keys → Create key.

  • Key type: Symmetric
  • Key usage: Encrypt and decrypt
  • Alias: photoviewer-data-key
  • Description: Encrypts photos (S3) and photo metadata (DynamoDB)

On the Define key administrative permissions page, select your IAM admin user. On the Define key usage permissions page, select the main Lambda execution role (photoviewer-lambda-role-*). This is the role that reads and writes photos and DynamoDB records.

Two keys, two scopes: The infra key protects operational secrets — only the authorizer can decrypt. The data key protects user content — only the main Lambda can decrypt. Neither role can decrypt the other key's data. This is separation of duties enforced by cryptography.

KMS console showing both keys: photoviewer-infra-key and photoviewer-data-key
Key policy for each key showing the correct Lambda role. Infra key → authorizer role. Data key → main Lambda role.
Part 2 Update Lambda and frontend

S3 presigned URLs require explicit encryption parameters when using SSE-KMS. The presigned URL must be signed with Signature Version 4 (not V2), and the browser must send encryption headers that match what was signed. Deploy all code changes now, while the bucket is still using SSE-S3. Once the code is ready, you'll flip encryption on in Parts 3–5.

Step 3 Deploy updated Lambda code

Go to Lambda → Functions → photoviewer-lambda → Code. Replace the code with the Week 8 version from the GitHub repo. Two changes from Week 7:

  1. Signature Version 4: The S3 client is configured with config=Config(signature_version='s3v4'). SSE-KMS requires SigV4 — the default SigV2 is rejected by S3.
  2. KMS parameters in presigned URL: When KMS_DATA_KEY_ID is set, the presigned PUT URL includes ServerSideEncryption and SSEKMSKeyId parameters. The browser must send matching headers.

Click Deploy.

Why is a code change needed for S3 but not Secrets Manager? Secrets Manager handles encryption transparently — Lambda calls get_secret_value() and Secrets Manager decrypts internally. S3 presigned URLs are different: the browser uploads directly to S3, and the encryption parameters must be in the signed URL and the request headers. Lambda generates the URL, so Lambda must include the KMS parameters.

Lambda code editor showing config=Config(signature_version='s3v4')
Step 4 Add the KMS_DATA_KEY_ID environment variable

Go to Lambda → Functions → photoviewer-lambda → Configuration → Environment variables → Edit. Click Add environment variable:

  • Key: KMS_DATA_KEY_ID
  • Value: the Key ID of photoviewer-data-key — find it in KMS → photoviewer-data-key. Use the Key ID at the top of the page (the UUID-format identifier, e.g. 1234abcd-12ab-34cd-56ef-1234567890ab). Not the alias photoviewer-data-key, and not the full ARN.

Click Save.

This env var activates KMS in the Lambda code. When KMS_DATA_KEY_ID is empty (Week 7), the Lambda generates presigned URLs without encryption parameters. When set (Week 8), it includes ServerSideEncryption and SSEKMSKeyId in every presigned PUT URL. The same code works for both weeks.

Lambda Environment variables panel showing KMS_DATA_KEY_ID set to the data key's Key ID
Step 5 Deploy updated frontend

The updated app.js reads encryption parameters from the Lambda response and includes them as headers in the PUT request to S3.

Before uploading, edit app.js and replace the three placeholders at the top with your actual values — the same ones you used in Week 7:

  • YOUR_COGNITO_DOMAIN — found in Cognito → User pool → App integration → Domain
  • YOUR_APP_CLIENT_ID — found in Cognito → User pool → App integration → App clients
  • YOUR_CLOUDFRONT_DOMAIN — your CloudFront distribution domain (e.g. dXXXXXXXXXXXXX.cloudfront.net)

If you skip this, login and logout will redirect to a nonexistent domain and break your app.

Once the placeholders are replaced, upload app.js to your S3 bucket the same way you did in Week 7 — either through the S3 console Upload button or via CloudShell aws s3 cp. Then invalidate your CloudFront cache so the new file is served.

Go to CloudFront → your distribution → Invalidations tab → Create invalidation. In the Object paths box, enter:

/app.js

Click Create invalidation. Wait for the status to change to Completed — this usually takes 30–60 seconds.

Alternatively, in CloudShell:

aws cloudfront create-invalidation \
    --distribution-id YOUR_DISTRIBUTION_ID \
    --paths "/app.js"

Replace YOUR_DISTRIBUTION_ID with your CloudFront distribution ID (from the CloudFront console → Distributions list).

What changed in app.js: The upload function reads encryption and kmsKeyId from the POST response. If present, it adds x-amz-server-side-encryption and x-amz-server-side-encryption-aws-kms-key-id headers to the PUT request. When KMS is not configured (Week 7), these fields are absent and no extra headers are sent.

Why deploy code before switching encryption? The bucket is still using SSE-S3 at this point, so uploading app.js works normally. If you switched encryption first, app.js would be encrypted with the KMS data key. CloudFront’s OAC is not in that key policy — and shouldn’t be, since static assets aren’t sensitive data — so CloudFront would get a 403 from S3 and serve an error page instead of the JavaScript file. By deploying code first, you avoid this entirely.

If you need to re-upload app.js after Step 8 (after bucket encryption is switched to SSE-KMS), add --sse AES256 to the S3 copy command to override the bucket default: aws s3 cp app.js s3://your-bucket/app.js --sse AES256 --content-type "application/javascript". Or upload through the S3 console and select SSE-S3 under encryption settings. This ensures CloudFront can still serve the file.

✓ Verify

Load the Photo Viewer in your browser. The app should work exactly as it did in Week 7. The new code is deployed but KMS encryption is not active yet — the bucket and services still use AWS-managed encryption.

Part 3 Encrypt Secrets Manager
Step 6 Switch the origin secret to the infra key

Go to Secrets Manager → photoviewer/origin-verify-secret → Actions → Edit encryption key. Change from aws/secretsmanager (AWS-managed) to photoviewer-infra-key. Click Save.

No code change needed. Secrets Manager handles the re-encryption transparently. The authorizer Lambda reads the secret the same way — Secrets Manager decrypts it using the new key before returning it. The authorizer role has kms:Decrypt on the infra key, so this works without any Lambda changes.

✓ Verify

Load the Photo Viewer in your browser. Login should still work. If it fails, check that you selected the correct authorizer role in the infra key policy.

Secrets Manager showing photoviewer/origin-verify-secret encrypted with photoviewer-infra-key
Part 4 Encrypt S3
Step 7 Update S3 CORS to allow encryption headers

Go to S3 → photoviewer-[your-account-id] → Permissions → Cross-origin resource sharing (CORS) → Edit. Update the CORS configuration to include the two KMS headers:

[
    {
        "AllowedHeaders": [
            "Content-Type",
            "x-amz-server-side-encryption",
            "x-amz-server-side-encryption-aws-kms-key-id"
        ],
        "AllowedMethods": ["PUT"],
        "AllowedOrigins": ["https://YOUR_CLOUDFRONT_DOMAIN"],
        "ExposeHeaders": []
    }
]

Replace YOUR_CLOUDFRONT_DOMAIN in AllowedOrigins with your actual CloudFront domain (e.g. https://dXXXXXXXXXXXXX.cloudfront.net). If you already had a CORS configuration from Week 7, add the two new AllowedHeaders to your existing config.

Why CORS needs updating: The browser now sends two extra headers with the PUT request: x-amz-server-side-encryption and x-amz-server-side-encryption-aws-kms-key-id. S3 CORS must explicitly allow these headers, otherwise the browser's preflight check fails.

Step 8 Set the bucket default encryption and verify existing objects

Go to S3 → photoviewer-[your-account-id] → Properties → Default encryption → Edit. Change from SSE-S3 to SSE-KMS. Select photoviewer-data-key from the dropdown. Click Save changes.

Now verify that existing objects were not affected. Go to S3 → your bucket → photos/ and click on any pre-seeded photo to open the object detail page. Scroll down to Server-side encryption settings. You should see:

  • Encryption type: SSE-S3

Changing the default does not re-encrypt existing objects. The pre-seeded photos were uploaded before the switch, so they still use SSE-S3. The new default only applies to objects uploaded from this point forward. Both encryption types work in the same bucket — S3 tracks encryption per object, not per bucket. The app continues to serve these photos normally because SSE-S3 decryption is transparent and requires no KMS access.

S3 bucket Properties showing default encryption set to SSE-KMS with photoviewer-data-key
S3 object detail page for a pre-seeded photo in photos/, showing Server-side encryption settings with encryption type SSE-S3
Step 9 Upload a new photo and verify KMS encryption

Log in as a premium user and upload a photo through the app. After the upload succeeds, verify that S3 encrypted it with the data key:

Go to S3 → your bucket → uploads/. Find the photo you just uploaded and click on its name to open the object detail page. Scroll down to Server-side encryption settings. You should see:

  • Encryption type: SSE-KMS
  • KMS key ARN: the ARN of photoviewer-data-key
✓ Verify

The uploaded photo’s encryption settings show SSE-KMS with the photoviewer-data-key ARN. If the upload fails with 400, check that all changes from Parts 2 and 4 are deployed: Lambda code, KMS_DATA_KEY_ID env var, app.js, and CORS.

S3 object detail page for the uploaded photo, showing Server-side encryption settings with encryption type SSE-KMS and KMS key ARN pointing to photoviewer-data-key
Part 5 Encrypt DynamoDB
Step 10 Switch the DynamoDB table to the data key

Go to DynamoDB → Tables → photoviewer-photos → Additional settings → Encryption. Click Manage encryption. Change from Owned by Amazon DynamoDB to Customer managed key. Select photoviewer-data-key. Click Save changes.

No code change needed. Unlike S3 presigned URLs, DynamoDB handles encryption transparently. Lambda calls table.scan() and table.put_item() the same way — DynamoDB encrypts and decrypts using the KMS key internally. The Lambda role needs kms:Decrypt and kms:GenerateDataKey on the data key, which the key policy already grants.

✓ Verify

Load the Photo Viewer and browse photos. All photos should appear and the counter should show the correct number.

DynamoDB table encryption settings showing photoviewer-data-key
Part 6 Demonstrate KMS as an independent authorization layer
Step 11 Revoke Lambda's access to the data key

Go to KMS → photoviewer-data-key → Key policy → Edit. Find the statement that grants the main Lambda execution role access ("Sid": "Allow use of the key"). Remove the Lambda role ARN from that statement. Click Save changes.

Only remove the Lambda role — not your admin user. If you remove yourself from the key administrators, you will lose the ability to edit the key policy and cannot restore access. Only delete the Lambda execution role ARN from the key users section.

This will break the app. That's the point. IAM still allows dynamodb:Scan and s3:GetObject — those permissions haven't changed. But KMS will deny decryption because the Lambda role is no longer in the key policy.

Step 12 Observe the failure

Load the Photo Viewer. The page loads (HTML/CSS/JS are served from CloudFront) but GET /photos returns a 500 error. Check the Lambda logs:

Go to CloudWatch → Log groups → /aws/lambda/photoviewer-lambda and open the most recent log stream. You should see an AccessDeniedException on a KMS operation — Lambda can still call DynamoDB and S3, but the services cannot decrypt the data because KMS denied the key usage.

Alternatively, in CloudShell:

aws logs tail /aws/lambda/photoviewer-lambda --since 5m --format short
Lambda logs showing AccessDeniedException on kms:Decrypt
Step 13 Restore access

Go back to KMS → photoviewer-data-key → Key policy → Edit. Re-add the Lambda execution role ARN to the usage statement. Click Save changes.

✓ Verify

Reload the Photo Viewer. Photos appear again. One key policy change, instant revocation and restoration — no code deployment, no IAM policy changes.

The teaching moment: IAM said yes the entire time — dynamodb:Scan and s3:GetObject were never revoked. KMS said no. Two independent authorization layers. You can revoke data access by editing either one.

Photo Viewer loading normally after re-adding Lambda role to key policy
Part 7 Audit decryption with CloudTrail
Step 14 Find KMS events in CloudTrail

Go to CloudTrail → Event history. Filter by:

  • Event source: kms.amazonaws.com

You should see Decrypt, GenerateDataKey, and possibly Encrypt events. Click into a successful Decrypt event (one with no error code — there will be many of these from normal app activity) and examine the details:

  • userIdentity.arn — which IAM role triggered the decryption
  • requestParameters.keyId — which KMS key was used
  • eventTime — when it happened

This audit trail didn't exist before. With AWS-managed keys, CloudTrail logged GetObject and Scan calls but no KMS events. You knew someone called the API — you didn't know if they decrypted the data. With customer-managed keys, every decryption is a separate, auditable event.

CloudTrail event detail showing a successful kms:Decrypt call (no error code) with the Lambda role ARN and the data key ARN
Step 15 Find the denied event

Still in CloudTrail Event history, look for a Decrypt event with Error code: AccessDeniedException — this is from Step 12 when you revoked Lambda's key access.

CloudTrail events can take 5–15 minutes to appear. If you don't see the denied event yet, wait a few minutes and refresh.

✓ Verify

The denied event shows the same Lambda role ARN and key ARN, but with an error code. This is the forensic record.

CloudTrail showing a denied kms:Decrypt event with AccessDeniedException

Reflection Questions

Question 1

An employee with s3:GetObject permission downloads a private photo. With AWS-managed encryption (before this lab), how would you detect this? With customer-managed KMS keys (after this lab), how would you detect it and how would you prevent it?

Question 2

This lab uses two KMS keys — photoviewer-infra-key and photoviewer-data-key. Explain the security benefit of this separation. What would be the risk of using a single key for both Secrets Manager and S3/DynamoDB?
