Week 8 Lab — Encryption at Rest with KMS

CS 55D: Security in Amazon Web Services  ·  Foothill College  ·  100 pts

Objective: Replace AWS-managed encryption with customer-managed KMS keys across S3, DynamoDB, and Secrets Manager. Create two keys with distinct key policies to enforce separation of duties. Demonstrate that KMS key policies create an authorization layer independent of IAM, and use CloudTrail to audit decryption events.

Architecture after this lab: Same as Week 7 — no new services or API routes. What changes is the encryption layer underneath: all data at rest is now encrypted with customer-managed KMS keys whose key policies you control.

Pre-flight checklist

Run the pre-flight script from CloudShell before starting:

cd ~
git -C aws-security-course pull
bash aws-security-course/photoviewer/week08/week8-preflight.sh

The script verifies your Week 7 environment is intact: Lambda functions, DynamoDB table, S3 bucket, CloudFront distribution, Cognito User Pool with groups, and Secrets Manager secret. Address any errors before proceeding.

Part 1 Create the infrastructure key
Step 1 Create the photoviewer-infra-key

Go to KMS → Customer managed keys → Create key.

  • Key type: Symmetric
  • Key usage: Encrypt and decrypt
  • Alias: photoviewer-infra-key
  • Description: Encrypts infrastructure secrets (origin-verify, future credentials)

On the Define key administrative permissions page, select your IAM admin user. On the Define key usage permissions page, select the Lambda authorizer execution role (photoviewer-authorizer-role-*). This is the role that reads the origin secret from Secrets Manager on every request.

Why the authorizer role? When Secrets Manager encrypts the secret with this key, any principal that reads the secret also needs kms:Decrypt permission on the key. The authorizer Lambda reads the secret on every invocation — so its execution role must be in the key policy.

KMS key details page showing photoviewer-infra-key with the authorizer role in the key policy
Part 2 Create the data key
Step 2 Create the photoviewer-data-key

Go to KMS → Customer managed keys → Create key.

  • Key type: Symmetric
  • Key usage: Encrypt and decrypt
  • Alias: photoviewer-data-key
  • Description: Encrypts photos (S3) and photo metadata (DynamoDB)

On the Define key usage permissions page, select the main Lambda execution role (photoviewer-lambda-role-*). This is the role that reads and writes photos and DynamoDB records.

Two keys, two scopes: The infra key protects operational secrets — only the authorizer can decrypt. The data key protects user content — only the main Lambda can decrypt. Neither role can decrypt the other key's data. This is separation of duties enforced by cryptography.

KMS console showing both keys: photoviewer-infra-key and photoviewer-data-key
Part 3 Encrypt Secrets Manager
Step 3 Switch the origin secret to the infra key

Go to Secrets Manager → photoviewer/origin-verify-secret → Actions → Edit encryption key. Change from aws/secretsmanager (AWS-managed) to photoviewer-infra-key. Click Save.

✓ Verify

Load the Photo Viewer in your browser. Login should still work — the authorizer reads the secret, and its role has kms:Decrypt on the infra key. If login fails, check that you selected the correct authorizer role in the key policy.

Secrets Manager showing photoviewer/origin-verify-secret encrypted with photoviewer-infra-key
Part 4 Encrypt S3
Step 4 Set the bucket default encryption to the data key

Go to S3 → photoviewer-[your-account-id] → Properties → Default encryption → Edit. Change from SSE-S3 to SSE-KMS. Select photoviewer-data-key from the dropdown. Enable Bucket Key (reduces KMS API calls). Click Save changes.

Existing objects are not re-encrypted. Changing the default encryption only affects new objects. Existing pre-seeded photos are still encrypted with the old AWS-managed key. You'll re-encrypt them in Step 6.

S3 bucket Properties showing default encryption set to SSE-KMS with photoviewer-data-key
Step 5 Upload a new photo and verify encryption

Log in as a premium user and upload a photo through the app. After the upload, go to S3 → your bucket → uploads/ → your photo. Click the photo and check Server-side encryption settings.

✓ Verify

The new photo shows encryption type SSE-KMS with key ARN pointing to photoviewer-data-key.

Step 6 Re-encrypt pre-seeded photos

Existing photos still use the old AWS-managed key. Re-encrypt them by copying in place from CloudShell:

BUCKET=$(aws s3api list-buckets --query "Buckets[].Name" --output text | tr '\t' '\n' | grep photoviewer)
KEY_ARN=$(aws kms describe-key --key-id alias/photoviewer-data-key --query "KeyMetadata.Arn" --output text)

for obj in $(aws s3 ls s3://$BUCKET/photos/ --recursive | awk '{print $4}'); do
  aws s3 cp s3://$BUCKET/$obj s3://$BUCKET/$obj \
    --sse aws:kms --sse-kms-key-id $KEY_ARN
done

Verify by clicking a pre-seeded photo in S3 — it should now show photoviewer-data-key in the encryption settings.

Copy-in-place: The aws s3 cp command with the same source and destination re-uploads the object with the new encryption settings. S3 creates a new version encrypted with the specified KMS key. The old version (with the old key) is overwritten.

S3 object properties for a pre-seeded photo showing SSE-KMS with photoviewer-data-key
Part 5 Encrypt DynamoDB
Step 7 Switch the DynamoDB table to the data key

Go to DynamoDB → Tables → photoviewer-photos → Additional settings → Encryption. Click Manage encryption. Change from Owned by Amazon DynamoDB to Customer managed key. Select photoviewer-data-key. Click Save changes.

✓ Verify

Load the Photo Viewer and browse photos. All photos should still appear and the counter should show the correct number. The main Lambda role has kms:Decrypt on the data key, so DynamoDB reads work.

DynamoDB table encryption settings showing photoviewer-data-key
Part 6 Demonstrate KMS as an independent authorization layer
Step 8 Revoke Lambda's access to the data key

Go to KMS → photoviewer-data-key → Key policy → Edit. Find the statement that grants the main Lambda execution role kms:Decrypt and kms:GenerateDataKey. Remove the Lambda role ARN from that statement. Click Save changes.

This will break the app. That's the point. IAM still allows dynamodb:Scan and s3:GetObject — those permissions haven't changed. But KMS will deny decryption because the Lambda role is no longer in the key policy.

Step 9 Observe the failure

Load the Photo Viewer. The page loads (HTML/CSS/JS are served from CloudFront) but GET /photos returns a 500 error. Check the Lambda logs:

aws logs tail /aws/lambda/photoviewer-lambda --since 5m --format short

You should see an AccessDeniedException on a KMS operation — the Lambda can still call DynamoDB and S3, but the services cannot decrypt the data because KMS denied the key usage.

Lambda logs showing AccessDeniedException on kms:Decrypt
Step 10 Restore access

Go back to KMS → photoviewer-data-key → Key policy → Edit. Re-add the Lambda execution role ARN to the usage statement. Click Save changes.

✓ Verify

Reload the Photo Viewer. Photos appear again. One key policy change, instant revocation and restoration — no code deployment, no IAM policy changes.

The teaching moment: IAM said yes the entire time — dynamodb:Scan and s3:GetObject were never revoked. KMS said no. Two independent authorization layers. You can revoke data access by editing either one.

Part 7 Audit decryption with CloudTrail
Step 11 Find KMS events in CloudTrail

Go to CloudTrail → Event history. Filter by:

  • Event source: kms.amazonaws.com

You should see Decrypt, GenerateDataKey, and possibly Encrypt events. Click into a Decrypt event and examine the details:

  • userIdentity.arn — which IAM role triggered the decryption
  • requestParameters.keyId — which KMS key was used
  • eventTime — when it happened

This audit trail didn't exist before. With AWS-managed keys, CloudTrail logged GetObject and Scan calls but no KMS events. You knew someone called the API — you didn't know if they decrypted the data. With customer-managed keys, every decryption is a separate, auditable event.

CloudTrail event detail showing a kms:Decrypt call with the Lambda role ARN and the data key ARN
Step 12 Find the denied event

Still in CloudTrail Event history, look for a Decrypt event with Error code: AccessDeniedException — this is from Step 9 when you revoked Lambda's key access.

✓ Verify

The denied event shows the same Lambda role ARN and key ARN, but with an error code. This is the forensic record: if you ever need to prove that a principal's access was revoked and the revocation was effective, this event is the evidence.

CloudTrail showing a denied kms:Decrypt event with AccessDeniedException
Part 8 Disable the key (optional demo)
Step 13 Disable and re-enable the data key

Go to KMS → photoviewer-data-key → Key actions → Disable. Confirm the action.

Load the Photo Viewer — GET /photos fails. No data is deleted, but all data encrypted with this key is cryptographically inaccessible. Uploaded photos, pre-seeded photos, and DynamoDB records are all unreadable.

Go back to KMS → photoviewer-data-key → Key actions → Enable. Reload — everything works again.

The "break glass" scenario: If you discover a data breach, disabling the key instantly makes all copies of the data — including backups, replicas, and any exfiltrated copies — useless. No attacker can decrypt the data without the key, and the key is disabled. Re-enable when the breach is contained.

Reflection Questions

Question 1

An employee with s3:GetObject permission downloads a private photo. With AWS-managed encryption (before this lab), how would you detect this? With customer-managed KMS keys (after this lab), how would you detect it and how would you prevent it?

Question 2

This lab uses two KMS keys — photoviewer-infra-key and photoviewer-data-key. Explain the security benefit of this separation. What would be the risk of using a single key for both Secrets Manager and S3/DynamoDB?
