Encryption at Rest with KMS

This course builds a Photo Viewer application across 12 weeks, adding one AWS security layer per week. Week 8 adds customer-managed encryption to the data infrastructure built in Weeks 5–7 — you now control not just who can access data, but who can read its contents.

Learning objectives
  • Explain the difference between AWS-managed keys and customer-managed KMS keys, and why the distinction matters for access control and audit
  • Describe how KMS key policies create an authorization layer independent of IAM — and why two independent layers are stronger than one
  • Use CloudTrail to audit kms:Decrypt events and identify which principal accessed which data
  • Demonstrate that revoking KMS key access blocks data access even when IAM permissions still allow the API call
  • Explain the separation of duties principle using two KMS keys with different key policies
  • Compare KMS with CloudHSM and explain when each is appropriate

1. Where we left off

Week 7 added authorization — Cognito groups drive capability differences, presigned URLs control photo delivery, and ownership checks prevent BOLA/IDOR. Two issues remain.

Uploaded files pass envelope checks but content is not inspected

Week 7 presigned URL conditions enforce Content-Type and file size at the S3 layer — a file claiming to be a 500 MB executable will be rejected. But a file that passes those checks can still be harmful: an image with embedded malware, a JPEG with a PHP payload in its EXIF data, a photo containing PII (someone's driver's license), or inappropriate content. The presigned URL conditions check the envelope, not the contents. This is a detection problem addressed in later weeks.

All data at rest is encrypted with AWS-managed keys

S3, DynamoDB, and Secrets Manager all encrypt data at rest — but with AWS-managed keys. This means there is no CloudTrail audit trail when data is decrypted, no way to scope decryption to specific IAM principals via a key policy, and no ability to revoke decryption access independently of IAM permissions. You control who can call GetObject — but you do not control who can decrypt what GetObject returns. These are two different questions, and right now only one has an answer.

2. This week's solution

Week 8 replaces AWS-managed keys with customer-managed KMS keys. The data doesn't change. The encryption algorithm doesn't change. What changes is who controls the keys — and therefore who controls the ability to read the data.

3. The core insight

IAM controls the API call. KMS controls the decryption.

A Lambda function can have s3:GetObject permission — IAM says yes. But if the KMS key policy does not grant that Lambda role kms:Decrypt, S3 returns an error: the object is retrieved but cannot be decrypted. Two independent authorization layers, evaluated separately, both must pass. This is the same pattern as Week 7 (group check + ownership check) — applied to encryption instead of application logic.

This separation means you can answer questions that IAM alone cannot:

  • "Who decrypted this photo in the last 24 hours?" — CloudTrail kms:Decrypt event, filtered by key ID
  • "Revoke this contractor's access to all photos immediately" — remove their role from the key policy. Takes effect in seconds, no IAM policy changes needed, no code deployment
  • "Make all data unreadable right now" — disable the key. One toggle, instant. Every copy of the data (including backups, replicas, stolen copies) becomes cryptographically inaccessible

4. Two keys, two scopes

The Photo Viewer has two categories of sensitive data with different access requirements. Using a single key would mean anyone who can decrypt secrets can also decrypt photos — violating the principle of least privilege. Two keys enforce separation of duties.

INFRASTRUCTURE

photoviewer-infra-key

Protects operational secrets

  • Secrets Manager (origin-verify secret)
  • Future: database credentials, API keys

Key policy grants: Lambda authorizer role (reads origin secret at runtime)

APPLICATION DATA

photoviewer-data-key

Protects user content

  • S3 photos (new uploads; pre-seeded photos remain SSE-S3)
  • DynamoDB photo metadata

Key policy grants: Lambda execution role (reads/writes photos and metadata at runtime)

Separation of duties in practice

The infra-admin (Week 9) can rotate the origin secret but cannot view user photos — they don't have kms:Decrypt on the data key. The photos-admin (Week 9) can manage pre-seeded photos but cannot read the origin secret — they don't have kms:Decrypt on the infra key. Lambda can decrypt photos at runtime but reads secrets only through Secrets Manager's service integration. Three principals, two keys, no one has access to everything.

5. Key concepts

🔐
Envelope encryption
KMS doesn't encrypt your data directly — it encrypts a data key that encrypts your data
▼

When S3 encrypts an object with SSE-KMS, it does not send the photo to KMS. Instead, S3 calls kms:GenerateDataKey, which returns a plaintext data key and an encrypted copy of that data key. S3 uses the plaintext key to encrypt the photo, stores the encrypted data key alongside the encrypted photo, and discards the plaintext key from memory.

On read, S3 sends the encrypted data key to KMS (kms:Decrypt), gets back the plaintext key, decrypts the photo, and returns it. KMS never sees the photo — it only sees the small data key.

This is why KMS has a 4 KB limit on direct encryption — it's designed for keys, not data. Envelope encryption means KMS scales to any data size because the actual encryption is done locally by S3 (or DynamoDB, or any service) using the data key.

📋
Key policies vs IAM policies
KMS is the only AWS service where the resource policy is mandatory
▼

Most AWS services (S3, DynamoDB, Lambda) evaluate IAM policies and resource policies together — if either allows the action, access is granted. KMS is different: the key policy is the primary access control. An IAM policy alone cannot grant access to a KMS key unless the key policy explicitly allows it.

In practice, most key policies include a statement that allows the account root to use IAM policies for key management. But for data access (kms:Decrypt, kms:Encrypt), you explicitly name the principals in the key policy. This means removing a role from the key policy revokes access even if the IAM policy still allows it.

📊
CloudTrail + KMS = data access audit
Every decrypt call is logged — who, when, which key
▼

With AWS-managed keys, CloudTrail logs S3 API calls (GetObject, PutObject) but does not log the underlying KMS operations. You know someone accessed the object, but not whether they decrypted its contents.

With customer-managed keys, every kms:Decrypt and kms:GenerateDataKey call appears in CloudTrail with the principal ARN, the key ARN, and the timestamp. You can trace a specific decryption event back to a specific IAM role at a specific time.

This is the audit trail that compliance frameworks (SOC 2, PCI-DSS, HIPAA) require: proof of who accessed sensitive data and when.

🏛️
KMS vs CloudHSM
Shared service vs dedicated hardware — cost, control, compliance
▼

KMS is a shared, multi-tenant service. AWS manages the hardware security modules (HSMs) that store your key material. You control the key policy, but AWS controls the HSM infrastructure.

CloudHSM gives you a dedicated, single-tenant HSM in your VPC. You have full control over the key material — AWS cannot access it, even under subpoena. The HSM is FIPS 140-2 Level 3 certified (tamper-evident hardware).

PropertyKMSCloudHSM
Cost$1/month per key~$1,100/month per HSM
ManagementFully managed by AWSYou manage the HSM cluster
Key materialAWS-managed HSMs (you can import your own)You generate and control all key material
ComplianceFIPS 140-2 Level 2FIPS 140-2 Level 3
Use caseMost applicationsGovernment, financial, specific regulatory requirements

For the Photo Viewer — and most applications — KMS is the right choice. CloudHSM is for organizations with specific regulatory requirements that mandate dedicated hardware and full key material control.

6. What's still missing

Click to expand.

Uploaded files are still not scanned for malicious content
click to expand

The problem: Encryption protects data at rest from unauthorized access — it does not inspect data for harmful content. A photo containing embedded malware or PII is now encrypted with a customer-managed key, which makes it harder for unauthorized users to access but does nothing to detect that the content is harmful in the first place.

What needs to happen: Uploaded objects need to be scanned after they land in S3. Macie can detect PII in S3 objects. GuardDuty Malware Protection can scan uploads for known malware signatures. These are detection services that analyze object contents — a different layer from encryption.

No employee access management
click to expand

The problem: The key policies name specific Lambda execution roles — but there are no human operator roles yet. The infra-admin and photos-admin roles referenced in the key policy design don't exist as real IAM principals. In production, employees need to manage pre-seeded photos, rotate secrets, and inspect encrypted data — each with appropriate key access.

What needs to happen: IAM Identity Center creates employee permission sets that map to IAM roles. Those roles are then added to the appropriate KMS key policies — infra-admin gets the infra key, photos-admin gets the data key. The key policies are already designed for this separation; the principals just need to be created.
