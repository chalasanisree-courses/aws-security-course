What we are building

Photo Viewer is the course project for CS 55D (Security in Amazon Web Services) at Foothill College. Students build this cloud-native photo-sharing application from scratch on AWS, securing it week by week. Each week adds a new layer — CDN, a serverless backend, authentication, encryption, threat detection — learning each security control by actually deploying it.

The three tiers below show the full product vision. The same application serves all users — what changes is what each tier can see and do.

What users can do
Any visitor can open the Photo Viewer and click through a set of travel photos — no login, no account. The photo list is fixed at five photos. There is no search, no upload, no user accounts.
How it is built on AWS
Browser → HTTP → S3 static website hosting
HTML, CSS, JavaScript, and a static photos.json file all live in a single public S3 bucket. The browser fetches photos.json to get the photo list, then requests each image. S3 serves everything. There is no backend server — all logic runs in the browser.

What users can do
The experience is identical to Week 2 — visitors click through photos without logging in. The improvements are entirely infrastructure: the app is now served over HTTPS, loads faster globally, and the S3 bucket is no longer publicly accessible.
How it is built on AWS
Browser → HTTPS → CloudFront → OAC → S3 (private bucket)
CloudFront sits in front of S3. Origin Access Control (OAC) makes the S3 bucket fully private — only CloudFront can read from it. HTTPS is enforced at the edge; HTTP requests are automatically redirected. A CloudFront Function blocks non-web file types. Response headers add HSTS, X-Frame-Options, and X-Content-Type-Options.

What users can do
Visitors still browse photos without logging in — the user-facing experience is unchanged. The difference is architectural: the photo catalog is now stored in DynamoDB. Add a row to the database and it appears to all visitors immediately, with no redeployment.
How it is built on AWS
Browser → HTTPS → CloudFront → ALB (public subnet) → EC2 (private subnet) → DynamoDB
CloudFront routes /photos requests to an ALB, which forwards to an EC2 app server in a private VPC subnet — no public IP, no SSH. SSM Session Manager handles remote access. DynamoDB is accessed via a VPC Gateway endpoint, never over the internet.

What users can do
The user-facing experience is identical to Week 4 — unauthenticated visitors browse photos served from DynamoDB. The change is entirely architectural: the backend is now serverless. No EC2, no ALB, no OS to patch.
How it is built on AWS
Browser → HTTPS → WAF + CloudFront → API Gateway → Lambda → DynamoDB
EC2 and ALB are replaced by Lambda and API Gateway. A Lambda authorizer checks a secret header CloudFront adds to every origin request — direct calls to the API Gateway URL are rejected. WAF adds a rate-based rule on /photos. API Gateway enforces HTTPS natively — no certificate needed.

Application features — building
6
Login with Google
Unauthenticated: public photos · Logged in (free or premium): all photos
Cognito User Pool Google federation Hosted UI OAuth 2.0 / OIDC JWT + claims Cognito groups Extended Lambda authorizer Secrets Manager
›
What users can do
Visitors can click Login and authenticate with their Google account via Cognito. Unauthenticated visitors see public photos only. Any logged-in user — free or premium — sees all photos including private ones. Free and premium groups are set up but the capability distinction takes effect in Week 7.
How it is built on AWS
Browser → Cognito Hosted UI ↔ Google (OIDC)
Browser + JWT → WAF + CloudFront → API Gateway → Lambda authorizer → Lambda + DynamoDB
Cognito User Pool with Google as a federated IdP handles login via the Authorization Code flow. Cognito holds the Google client secret and issues its own JWT. The Lambda authorizer is extended to fetch the origin secret from Secrets Manager and optionally validate the JWT — passing group context to the main Lambda, which filters DynamoDB results accordingly.

7
Upload & delete with access control
Premium: upload photos · All users: delete own uploads
S3 presigned URLs Object ownership RBAC enforcement Endpoint authorization Resource authorization
›
What users can do
Premium users can upload photos directly from the browser using S3 presigned URLs. Premium users can delete and toggle visibility of their own uploaded photos — Lambda validates ownership before allowing any mutation. All photos (pre-seeded and uploaded) are now served via presigned GET URLs — no permanent CloudFront photo URLs exist. Demonstrates two authorization patterns: endpoint-level (only premium users can access mutation endpoints) and object-level (only the owner can modify a specific photo).
How it is built on AWS
Browser (premium) → request URL → API Gateway → Lambda authorizer → presigned URL → S3
Lambda generates presigned PUT URLs for premium users after the Lambda authorizer validates group membership. Photos are uploaded directly to S3 without routing through Lambda. All photos — pre-seeded and uploaded — are served via presigned GET URLs generated by Lambda on every GET /photos call. DynamoDB tracks photo ownership (owner = JWT sub claim). Delete and toggle endpoints validate that the requesting user owns the photo before modifying S3 and DynamoDB. CORS on S3 allows cross-origin PUT from the CloudFront domain.

Application features — hardening
8
Encryption at rest
Customer-managed keys for S3, DynamoDB, and Secrets Manager
KMS Customer-managed keys Key policies Separation of duties Envelope encryption CloudTrail audit CloudHSM
›
What changes
User-facing experience is unchanged. All data at rest — S3 photos, DynamoDB metadata, and Secrets Manager secrets — is now encrypted with customer-managed KMS keys instead of AWS-managed keys. You control who can decrypt the data via key policies, every decryption is logged in CloudTrail, and keys can be disabled instantly to make all encrypted data unreadable.
How it is built on AWS
Two KMS customer-managed keys enforce separation of duties. The infrastructure key (photoviewer-infra-key) encrypts operational secrets in Secrets Manager — only the Lambda authorizer role can decrypt. The data key (photoviewer-data-key) encrypts user content in S3 and DynamoDB — only the main Lambda execution role can decrypt. Key policies create an authorization layer independent of IAM: a role needs both IAM permission for the API call and key policy permission for decryption. Presigned URL uploads include KMS encryption headers so S3 encrypts user-uploaded photos with the data key. All kms:Decrypt and kms:GenerateDataKey calls appear in CloudTrail with principal ARN, key ARN, and timestamp.

Employee SSO via Identity Center, permission sets for KMS key access
IAM Identity Center Permission sets Employee vs app user auth
›
What changes
App users (Cognito) and employee users (IAM Identity Center) are now managed separately. Developers log into the AWS console via SSO — no long-lived IAM users. PhotoViewer employees can manage pre-seeded photos — flip visibility, delete, and add new showcase photos — through a separate auth path from Cognito app users. Permission sets map to IAM roles with appropriate KMS key access.
How it is built on AWS
IAM Identity Center replaces individual IAM users for developer access — single sign-on with permission sets mapped to AWS accounts. The infra-admin permission set gets kms:Decrypt on the infra key. The photos-admin permission set gets kms:Decrypt on the data key. This completes the separation of duties designed in Week 8 — the key policies are already scoped, now the human principals exist.

Detect and respond
10
Visibility and compliance
Monitoring, vulnerability scanning, sensitive data discovery
CloudWatch AWS Config Inspector (Lambda) Trusted Advisor Macie CVE/NIST
›
What changes
Automated compliance checks, vulnerability scanning on the Lambda function, security best practice assessment, and sensitive data detection on the S3 bucket. Config rules alert on drift from the desired security posture. Trusted Advisor checks account-wide security best practices. Macie scans S3 for personally identifiable information in user-uploaded photos.
How it is built on AWS
CloudWatch alarms on Lambda error rates and DynamoDB throttling. AWS Config managed rules enforce S3 public access block, KMS encryption on DynamoDB, and CloudTrail enabled. Amazon Inspector scans the Lambda function for known CVEs in its dependencies. Trusted Advisor reviews security checks — unrestricted security groups, MFA on root, S3 bucket permissions. Macie monitors the S3 bucket and generates findings when it detects PII. CVE, NIST, CISA, and CIS vulnerability frameworks covered as lecture context for Inspector.

Threat detection and automated response
GuardDuty findings trigger automated remediation via EventBridge
GuardDuty Security Hub CloudTrail deep dive EventBridge Automated remediation

What changes
GuardDuty continuously analyzes CloudTrail events and DNS logs for threat indicators. Security Hub aggregates findings from GuardDuty, Config, Inspector, and Macie into a single dashboard. EventBridge rules trigger Lambda remediation functions automatically when high-severity findings are raised.
How it is built on AWS
GuardDuty enabled on the account — detects credential exfiltration, unusual API calls, and S3 data exposure. Security Hub with AWS Foundational Security Best Practices standard. EventBridge rule matches GuardDuty HIGH severity findings and invokes a Lambda function that revokes IAM credentials, isolates resources, or sends notifications via SNS.

Multi-account governance
Organizations, SCPs, Control Tower, Route 53 lecture
AWS Organizations SCPs Control Tower Route 53

What changes
Now that you've built one account properly, how do you manage hundreds? AWS Organizations groups accounts into OUs. Service Control Policies enforce guardrails org-wide — no CloudTrail disable, no public S3, region restrictions. Control Tower Landing Zone automates this for new accounts. Route 53 DNS security covered as lecture — custom domains, health checks, DNSSEC.
How it is built on AWS
AWS Organizations creates an OU structure. SCPs prevent any account from disabling CloudTrail, leaving a specific region, or creating public S3 buckets. Control Tower provides a pre-configured landing zone with guardrails, Account Factory, and a compliance dashboard. Route 53 alias records point to CloudFront with health checks for DNS failover.

Production Hardening Guide
What we could have done better — and when you'd choose it
›
This course prioritizes learning concepts over production perfection. Each week makes deliberate trade-offs: simpler over more secure, faster to build over fully hardened, cost-effective over enterprise-grade. Below is a week-by-week catalog of security improvements we skipped — explaining what the production alternative is, why it's better, and when the additional complexity is worth it.
Week 1: IAM + CloudTrail
Could have done:
  • MFA enforcement via IAM policy
  • Password complexity requirements
  • Least-privilege IAM user instead of AdministratorAccess
  • Multi-region CloudTrail with log file validation
  • KMS-encrypted CloudTrail logs
Why we skipped: Students need admin access for learning. MFA enforcement complicates workflow.
When you'd use it: Production accounts, SOC 2 / PCI-DSS compliance, any shared team environment.
Week 2: S3 Static Hosting
Could have done:
  • S3 Versioning (protect against accidental deletion)
  • S3 Object Lock for WORM compliance
  • S3 Access Logging (audit all bucket requests)
  • S3 Lifecycle policies (transition to cheaper tiers)
Why we skipped: Focus on basic bucket security (policies, ACLs). Versioning and access logging add cost and complexity.
When you'd use it: Data retention policies, compliance audits, financial/healthcare data.
Week 3: CloudFront + Edge Security
Could have done:
  • CloudFront signed URLs/cookies (time-limited access to private content)
  • Field-level encryption for sensitive data
  • Origin failover with secondary S3 bucket in different region
  • AWS Managed Rules for WAF (OWASP Top 10)
  • Shield Advanced ($3,000/month — 24/7 DRT support)
Why we skipped: Week 7 moves all photos to S3 presigned URLs. CloudFront signed URLs would be the production upgrade but require RSA key pair infrastructure.
When you'd use it: CloudFront signed URLs for production photo delivery, paid content, PII/PHI data, DDoS-prone applications.
Week 4: VPC + EC2 Backend
Could have done:
  • VPC Flow Logs (capture all network traffic)
  • Network ACLs in addition to security groups (defense in depth)
  • IMDSv2 enforcement (prevent SSRF on instance metadata)
  • HTTPS listener on ALB instead of HTTP
  • Auto Scaling Group across multiple AZs
Why we skipped: Flow Logs add cost. IMDSv2 breaks some libraries. Internal ALB traffic already encrypted at CloudFront edge.
When you'd use it: Network forensics, zero-trust architecture, highly available production workloads.
Week 5: Serverless Migration
⚙ Always use in production: REST API with IAM resource policy instead of HTTP API with shared secret. IAM-enforced — no way for attacker to bypass CloudFront even if they discover the API URL.
Also could have done:
  • Lambda in VPC for private resource access
  • API Gateway access logging
  • Request validation at API Gateway before invoking Lambda
  • X-Ray tracing for distributed debugging
Why we skipped: HTTP API is simpler ($1.00 vs $3.50/million requests). Shared secret is easier to understand for students.
When you'd use it: Always use REST API in production. Lambda VPC for accessing RDS, ElastiCache, or internal services.
Week 6: Authentication
⚙ Always use in production: HttpOnly cookies instead of sessionStorage — tokens not accessible to JavaScript (XSS protection), SameSite attribute prevents CSRF.
Also could have done:
  • Cognito Advanced Security (adaptive auth, compromised credentials detection)
  • Multi-factor authentication (SMS or TOTP)
  • Email verification before account activation
  • Custom domain (auth.yourdomain.com)
  • Lambda triggers for pre/post authentication logic
Why we skipped: HttpOnly cookies add CORS complexity. Week 6 scope is already full (Cognito + Google OAuth + Secrets Manager + authorizer). MFA adds friction to demo.
When you'd use it: Always use HttpOnly cookies. MFA for any financial or healthcare application.
Week 7: Authorization
⚙ Always use in production: CloudFront signed URLs instead of S3 presigned URLs — same per-URL access control with CDN edge caching. Requires RSA key pair (generate, upload public key to CloudFront key group, store private key in Secrets Manager, change Lambda signing from SigV4 to RSA).
Also could have done:
  • Separate S3 bucket for user uploads (isolate untrusted content)
  • File type validation (verify Content-Type and magic bytes)
  • Virus scanning via Lambda + ClamAV on S3 upload
  • Content moderation using Rekognition DetectModerationLabels
  • Image optimization (auto-generate thumbnails, convert to WebP)
  • Soft delete (mark deleted in DynamoDB, lifecycle policy after 30 days)
  • Cognito Identity Pool as alternative (browser gets temporary AWS credentials via STS)
Why we skipped: S3 presigned URLs require zero additional infrastructure — Lambda already has IAM credentials. File validation and virus scanning add scope.
When you'd use it: Always use CloudFront signed URLs in production. Separate upload buckets for untrusted content. Virus scanning for user-generated content platforms.
Week 8: Encryption at Rest
Could have done:
  • Multi-region KMS keys (disaster recovery)
  • Separate KMS key per service (one for S3, one for DynamoDB, one for Secrets Manager — finer blast radius)
  • Key policy conditions (restrict usage to specific VPCs, IP ranges, time windows)
  • Encryption context in KMS API calls (additional authenticated data binding key to object)
  • AWS CloudHSM for FIPS 140-2 Level 3 (~$1,100/month)
Why we skipped: Two keys (infra vs data) demonstrate separation of duties. Per-service keys add key management overhead without new conceptual value. CloudHSM requires specialized HSM administration.
When you'd use it: Multi-region for DR, per-service keys for PCI-DSS/HIPAA audits requiring granular blast radius, CloudHSM for government/finance regulatory requirements.
Week 9: Employee Identity
Could have done:
  • ABAC in Identity Center (permissions based on user attributes like department or team)
  • Just-in-time access (temporary elevated permissions with automatic expiration)
  • MFA enforcement on all Identity Center users
  • Session duration limits on permission sets
  • Integration with external IdPs (Okta, Azure AD) instead of Identity Center's built-in directory
Why we skipped: ABAC is advanced IAM. External IdP requires organizational infrastructure. MFA adds lab friction.
When you'd use it: External IdP for any company with existing identity infrastructure. ABAC for large teams. JIT access for break-glass scenarios.
Week 10: Monitoring & Compliance
Could have done:
  • CloudWatch Synthetics (canary monitoring, automated user journey testing)
  • CloudWatch Contributor Insights (top talkers, error patterns)
  • Config Conformance Packs (pre-built PCI-DSS, HIPAA, CIS rule sets)
  • Config Aggregator (multi-account, multi-region)
  • Config automatic remediation via Systems Manager Automation
  • Inspector continuous scanning (always-on instead of on-demand)
  • Macie automated full-estate sensitive data discovery
Why we skipped: Synthetics and continuous scanning add cost. Conformance Packs are bundles of rules we already cover individually.
When you'd use it: Synthetics for production SLA monitoring. Conformance Packs for SOC 2/ISO 27001 certification. Macie for regulated industries.
Week 11: Threat Detection
Could have done:
  • GuardDuty EKS/RDS/S3/Malware Protection (full coverage)
  • Trusted IP lists (whitelist office/VPN IPs)
  • Security Hub integrations (50+ AWS and partner services)
  • Security Hub standards (AWS Foundational Security Best Practices, CIS)
  • EventBridge advanced content-based filtering
  • Automated incident response (auto-isolate instances, auto-disable IAM users, auto-snapshot for forensics, auto-block IPs in WAF)
Why we skipped: EKS/RDS not relevant (no EKS/RDS in Photo Viewer). Advanced auto-response risks breaking things in learning environment.
When you'd use it: All GuardDuty protections in production. Automated response for 24/7 incident handling without on-call staff.
Week 12: Multi-Account Governance
Could have done:
  • Deny-by-default SCPs (explicitly allow only required services)
  • Require encryption via SCP (deny S3 PutObject without encryption header)
  • Require MFA for sensitive actions (deny DeleteBucket, StopLogging without MFA)
  • Tag-based SCPs (require CostCenter, Environment tags)
  • Route 53 DNSSEC (cryptographically sign DNS responses)
  • Route 53 Resolver DNS Firewall (block queries to malicious domains)
  • Health checks with multi-region active-passive failover
  • AWS Firewall Manager (centralized WAF management across organization — covered in Firewalls concept page)
Why we skipped: Deny-by-default SCPs too restrictive for learning. DNSSEC complex with limited learning benefit. Firewall Manager covered as a concept, not a lab.
When you'd use it: Deny-by-default for highly regulated environments. DNSSEC for high-security apps (financial, government). Firewall Manager for large multi-account organizations.
How to use this reference: For students — see what "production-grade" looks like and understand trade-offs in system design. For interview prep — answer "What would you change for production?" For professionals — migration checklist from proof-of-concept to production and risk assessment framework.
