Week 9 Lab — IAM Deep Dive

CS 55D: Security in Amazon Web Services  ·  Foothill College  ·  100 pts

Objective: The Photo Viewer team has grown. Tom (customer support) needs access to photos and metadata. Jerry (security engineer) needs access to infrastructure secrets and configuration. Set up IAM Identity Center with permission sets scoped to the KMS keys from last week, enforcing separation of duties at the human level. Create an external auditor scenario using IAM role assumption to demonstrate trust policies and dual-policy authorization. Use the IAM Policy Simulator to map the complete access landscape.

What changes this week: No user-facing changes to the Photo Viewer. All changes are on the operator side — who can log into the AWS console and what they can access. Identity Center provides employee SSO with temporary credentials. The auditor exercise demonstrates role assumption mechanics. The Policy Simulator maps who can access what.

Pre-flight checklist

Run the pre-flight script from CloudShell before starting:

cd ~
git -C aws-security-course pull
bash aws-security-course/photoviewer/week09/week9-preflight.sh

The script verifies your Week 8 environment is intact: both KMS keys exist and are enabled, S3/DynamoDB are encrypted with the data key, Secrets Manager is encrypted with the infra key, and the Photo Viewer loads. It also prints the key ARNs you'll need for permission sets and policies. Address any errors before proceeding.

Part 1 Identity Center for employee access

Tom (customer support) needs access to S3 photos and DynamoDB metadata — scoped to the data key. Jerry (security engineer) needs access to Secrets Manager, CloudFront, and API Gateway — scoped to the infra key. In this part, you'll set up IAM Identity Center so Tom and Jerry can log in via SSO with temporary credentials.

Step 1 Enable AWS Organizations

Go to AWS Organizations in the console. Click Create an organization.

Your current account becomes the management account. This is a prerequisite for Identity Center and for multi-account governance later in the course.

AWS Organizations console showing the organization created with your account as the management account
Step 2 Create Organizational Units

In the Organizations console, select Root → Actions → Create new. Create two OUs:

  • Production — for the current Photo Viewer deployment
  • Staging — empty for now, ready for a future staging environment where changes can be tested before reaching customers
Organizations console showing Root with two OUs: Production and Staging
Step 3 Move account into Production OU

Select your account (it's currently under Root). Click Actions → Move. Select Production as the destination.

The account now sits inside the Production OU. Later in the course, SCPs applied to this OU will govern what the account can do — and the Staging OU will hold a second account for testing changes before they reach customers.

Organizations console showing your account inside the Production OU
Step 4 Enable IAM Identity Center

Go to IAM Identity Center in the console. Click Enable.

When prompted for the identity source, choose Identity Center directory (the built-in directory). This is Identity Center's own user store — no external IdP needed for the lab. In production, you would federate with Okta, Azure AD, or Google Workspace.

Note the AWS access portal URL that appears after enabling — this is the SSO login page your Identity Center users will use. It looks like https://d-xxxxxxxxxx.awsapps.com/start.

IAM Identity Center dashboard showing enabled status and the AWS access portal URL
Step 5 Create two Identity Center users

Go to Identity Center → Users → Add user. Create two users:

UsernameEmailFirst nameLast name
jerryyour email with +jerry suffixJerry(your last name)
tomyour email with +tom suffixTom(your last name)

Each user will receive a one-time password email. You'll use these to log in via the SSO portal later.

Email suffix trick: Gmail treats you+anything@gmail.com the same as you@gmail.com. Both emails arrive in your inbox, but Identity Center sees them as distinct users.

Step 6 Create two groups

Go to Identity Center → Groups. Create two groups:

  • infra-team — add jerry
  • photos-team — add tom
Step 7 Create the InfraAdmin permission set

Go to Identity Center → Permission sets → Create permission set. Choose Custom permission set.

Name: InfraAdmin. Add an inline policy:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "InfraServices",
      "Effect": "Allow",
      "Action": [
        "secretsmanager:GetSecretValue",
        "secretsmanager:DescribeSecret",
        "secretsmanager:ListSecrets",
        "apigateway:GET",
        "cloudfront:Get*",
        "cloudfront:List*",
        "lambda:GetFunction",
        "lambda:ListFunctions",
        "cloudwatch:GetMetricData",
        "logs:GetLogEvents",
        "logs:DescribeLogGroups",
        "logs:DescribeLogStreams"
      ],
      "Resource": "*"
    },
    {
      "Sid": "InfraKeyDecrypt",
      "Effect": "Allow",
      "Action": [
        "kms:Decrypt",
        "kms:DescribeKey"
      ],
      "Resource": "arn:aws:kms:us-east-1:ACCOUNT-ID:key/INFRA-KEY-ID"
    }
  ]
}

Replace ACCOUNT-ID and INFRA-KEY-ID with your actual values. The infra key ARN is on the KMS console page for photoviewer-infra-key.

Step 8 Create the PhotosAdmin permission set

Create a second permission set. Name: PhotosAdmin. Add an inline policy:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DataServices",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket",
        "s3:PutObject",
        "s3:DeleteObject",
        "dynamodb:Scan",
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:DeleteItem",
        "dynamodb:DescribeTable"
      ],
      "Resource": [
        "arn:aws:s3:::BUCKET-NAME",
        "arn:aws:s3:::BUCKET-NAME/*",
        "arn:aws:dynamodb:us-east-1:ACCOUNT-ID:table/photoviewer-photos"
      ]
    },
    {
      "Sid": "DataKeyDecrypt",
      "Effect": "Allow",
      "Action": [
        "kms:Decrypt",
        "kms:GenerateDataKey",
        "kms:DescribeKey"
      ],
      "Resource": "arn:aws:kms:us-east-1:ACCOUNT-ID:key/DATA-KEY-ID"
    }
  ]
}

Replace BUCKET-NAME, ACCOUNT-ID, and DATA-KEY-ID with your actual values.

Identity Center showing both permission sets: InfraAdmin and PhotosAdmin
Step 9 Assign permission sets to the account

Go to Identity Center → AWS accounts. Select your account. Click Assign users or groups.

  • Assign the infra-team group → InfraAdmin permission set
  • Assign the photos-team group → PhotosAdmin permission set
Step 10 Log in as Jerry via SSO portal

Open an incognito/private browser window. Go to the SSO portal URL from Step 4. Log in as jerry with the one-time password, then set a new password.

The portal shows your AWS account with the InfraAdmin permission set. Click Management Console.

Look at the top-right of the console — you'll see a role name like AWSReservedSSO_InfraAdmin_..., not a username. This is the IAM role that Identity Center created behind the scenes and assumed on your behalf.

Step 11 Verify Jerry's access

Test what Jerry can and cannot do:

  • Go to Secrets Manager → view the photoviewer/origin-verify-secret value → CAN view it ✓
  • Go to S3 → navigate to the photos bucket → try to download a photo → CANNOT — Access Denied ✗
✓ Verify

Jerry can read Secrets Manager (has infra key decrypt) but cannot access S3 photos (no data key decrypt). The Week 8 KMS separation of duties is now enforced at the human level.

Secrets Manager showing the secret value visible to Jerry
S3 showing Access Denied when Jerry tries to download a photo
Step 12 Log in as Tom and verify

Open a different incognito window. Log in to the SSO portal as tom.

Test what Tom can and cannot do:

  • Go to S3 → navigate to the photos bucket → download a photo → CAN view photos ✓
  • Go to DynamoDB → scan the photoviewer-photos table → CAN see metadata ✓
  • Go to Secrets Manager → try to view the origin secret → CANNOT — Access Denied ✗
✓ Verify

Tom can access user data (S3 photos, DynamoDB metadata) but cannot access infrastructure secrets. Separation of duties is complete — for both machines (Lambda roles from Week 8) and humans (Identity Center users from this week).

S3 showing a photo successfully downloaded by Tom
Secrets Manager showing Access Denied for Tom
Part 2 External auditor — role assumption

Identity Center automates role assumption behind the scenes. In this part, you'll do it manually — creating an IAM user with no permissions, an IAM role with a trust policy, and using console Switch Role to assume temporary access. This is the mechanism Identity Center hides.

Step 13 Create an IAM user with no permissions

Go to IAM → Users → Create user.

  • Username: external-auditor
  • Select Provide user access to the AWS Management Console
  • Custom password (note it down)
  • Uncheck "Users must create a new password at next sign-in"
  • Do NOT attach any policies — click through to create

This represents a contractor from an outside audit firm. They have an AWS identity but zero standing permissions.

Step 14 Create the auditor role

Go to IAM → Roles → Create role.

  1. Trusted entity type: Select AWS account, then select This account. Click Next.
  2. Add permissions: Skip — don't attach any policies. Click Next.
  3. Name: Enter photo-auditor-role. Click Create role.

The console auto-generates a trust policy that trusts the entire account. Narrow it to the auditor user only:

  1. Go to IAM → Roles → photo-auditor-role
  2. Click the Trust relationships tab
  3. Click Edit trust policy
  4. Replace the content with:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::ACCOUNT-ID:user/external-auditor"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}

Click Update policy. This says: "I trust only the external-auditor user to assume me."

Now attach an inline policy to the role granting DynamoDB read access:

  1. Click the Permissions tab
  2. Click Add permissions → Create inline policy
  3. Switch to the JSON tab
  4. Replace the default content with the policy below
  5. Click Next, name the policy auditor-dynamodb-read, and click Create policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AuditDynamoDB",
      "Effect": "Allow",
      "Action": [
        "dynamodb:Scan",
        "dynamodb:GetItem",
        "dynamodb:DescribeTable",
        "dynamodb:ListTables"
      ],
      "Resource": "*"
    }
  ]
}
Step 15 Give the auditor user permission to assume the role

Go to IAM → Users → external-auditor.

  1. Click the Permissions tab
  2. Click Add permissions → Create inline policy
  3. Switch to the JSON tab
  4. Replace the default content with the policy below
  5. Click Next, name the policy auditor-assume-role, and click Create policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::ACCOUNT-ID:role/photo-auditor-role"
    }
  ]
}

This says: "I am allowed to assume the photo-auditor-role."

Both sides must agree. The user needs an identity-based policy (sts:AssumeRole). The role needs a trust policy naming the user. If either side is missing, the assumption fails. This is the same dual-policy pattern as KMS — same logic, different resource type.

Step 16 Log in as external-auditor

Open a new incognito window. Go to the regular IAM sign-in page (not the SSO portal): https://ACCOUNT-ID.signin.aws.amazon.com/console. Log in as external-auditor.

Try to access any service:

  • DynamoDB → Access Denied
  • S3 → Access Denied
  • Secrets Manager → Access Denied

The user has no permissions. Nothing works.

Console showing Access Denied on DynamoDB for external-auditor
Step 17 Switch Role to the auditor role

Click the username in the top-right of the console → Switch Role.

  • Account: your account ID
  • Role: photo-auditor-role
  • Display name: Auditor
  • Color: pick any color

Click Switch Role.

The console header changes color and shows Auditor — you are now operating as a different principal. You are no longer external-auditor (zero permissions). You are now photo-auditor-role (DynamoDB read access).

Console header showing the role name and changed color after Switch Role
Step 18 Verify auditor access
  • Go to DynamoDB → scan the photoviewer-photos table → WORKS ✓
  • Go to S3 → try to download a photo → Access Denied ✗ (role has no S3 permissions yet)
✓ Verify

The auditor can query DynamoDB metadata but cannot access S3 photos. The role's identity policy grants only what's needed for the metadata audit.

DynamoDB scan results showing photo metadata visible to the auditor role
Part 3 Expanding the auditor — the KMS wall

The auditor now needs to review the actual photos in S3, not just the metadata. You'll add S3 access and discover that S3 permission alone isn't enough — the photos are encrypted, and KMS needs to authorize the decryption.

Step 19 Add S3 permission to the auditor role

Switch back to your admin session. Go to IAM → Roles → photo-auditor-role → Permissions tab.

  1. Click the auditor-dynamodb-read policy name to expand it
  2. Click Edit
  3. Add the following statement to the Statement array (after the existing AuditDynamoDB statement, separated by a comma):
{
  "Sid": "AuditS3",
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::BUCKET-NAME/*"
}
Step 20 Test — try to download a photo as the auditor

Switch back to the auditor session (the incognito window where you're logged in as external-auditor with the role assumed). Go to S3 → navigate to the photos bucket → click on a photo → download.

Access Denied.

The auditor has s3:GetObject permission. Why doesn't it work? Because the photos are encrypted with the data key (from Week 8). When S3 tries to decrypt, it calls kms:Decrypt on behalf of the auditor role. The auditor role doesn't have kms:Decrypt permission on the data key. S3 can read the encrypted object, but KMS won't decrypt it.

S3 showing Access Denied when the auditor role (with s3:GetObject) tries to download an encrypted photo
Step 21 Add the auditor role to the data key's key policy

Switch back to admin. Go to KMS → Customer managed keys → photoviewer-data-key → Key policy tab.

  1. Click Edit
  2. Add the following statement to the Statement array:
{
  "Sid": "AllowAuditorDecrypt",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::ACCOUNT-ID:role/photo-auditor-role"
  },
  "Action": [
    "kms:Decrypt",
    "kms:DescribeKey"
  ],
  "Resource": "*"
}

Click Save changes.

This is a resource policy on the key itself — the key is explicitly granting the auditor role permission to decrypt. This is the same pattern as the trust policy on the IAM role: the resource names who can use it.

Step 22 Test again

Switch back to the auditor session. Try to download the photo again.

It works. ✓

Two things had to agree for this download to succeed:

  • S3 authorization: The auditor role's IAM policy grants s3:GetObject — S3 allows the read.
  • KMS authorization: The data key's key policy grants the auditor role kms:Decrypt — KMS allows the decryption.

This is the same dual-authorization pattern as role assumption: the role's trust policy and the user's identity policy must both agree. Here, the S3 identity policy and the KMS resource policy must both agree. Neither alone is sufficient.

✓ Verify

The auditor can now download photos. S3 permission alone was not enough — the key policy had to explicitly name the auditor role as a principal allowed to decrypt.

Security consequence: You just granted a third principal access to decrypt all user photos by modifying the key policy. In production, you would want a KMS grant instead of a permanent key policy statement (grants are revocable and can expire), time-bounded conditions, or MFA enforcement on the role assumption. You expanded the blast radius of the data key — that was a deliberate security decision.

S3 showing a photo successfully downloaded by the auditor role after adding the role to the data key's key policy
Step 23 Switch back

In the auditor session, click the role name in the top-right → Switch back. The console header reverts. You're back to external-auditor with zero permissions. The temporary role session is over.

Part 4 Policy Simulator — the access matrix

The Policy Simulator lets you test permissions for any IAM principal without actually making API calls. You'll map the complete s3:GetObject access landscape across all Photo Viewer principals.

Step 24 Open the IAM Policy Simulator

Log in with your original IAM admin user. Go to IAM → Policy Simulator (or navigate to https://policysim.aws.amazon.com).

Step 25 Test s3:GetObject for each principal

For each principal below, select the principal in the simulator, choose service S3, action GetObject, and resource arn:aws:s3:::BUCKET-NAME/*. Click Run Simulation.

PrincipalExpected resultWhy
Lambda execution roleAllowedIdentity policy from Week 5 + key policy from Week 8
photo-auditor-roleAllowedIdentity policy updated in Part 3
external-auditor (user, not role)DeniedNo policies — only sts:AssumeRole
Lambda authorizer roleDeniedOnly has Secrets Manager + infra key access

Limitation: The Policy Simulator evaluates identity-based policies only. It does not evaluate resource-based policies (bucket policies, key policies). So the simulator will show "Allowed" for principals that have s3:GetObject in their identity policy — but in practice, they also need the key policy to agree for encrypted objects. The Identity Center roles may not appear in the simulator directly — they are auto-generated IAM roles with names like AWSReservedSSO_PhotosAdmin_....

IAM Policy Simulator showing results for s3:GetObject across multiple principals — some allowed, some denied
Step 26 Check CloudTrail

Go to CloudTrail → Event history. Filter by event name AssumeRole.

You should see:

  • The Identity Center users' role assumptions (from Part 1) — showing the Identity Center username
  • The external-auditor's role assumption to photo-auditor-role (from Part 2) — showing the IAM user ARN

Each event shows an individual identity — not a shared credential. This is the auditability benefit of both Identity Center and explicit role assumption.

CloudTrail events can take 5–15 minutes to appear. If you don't see events yet, wait and refresh.

CloudTrail showing AssumeRole events with individual user identities

Cleanup

Delete or disable resources to avoid unexpected charges:

  • Delete the IAM user: external-auditor (delete inline policies first)
  • Delete the IAM role: photo-auditor-role
  • Identity Center users, groups, and permission sets can remain (no ongoing cost) or be deleted
  • Do NOT disable Organizations — it's needed for Week 12 (SCPs)
  • Do NOT disable Identity Center — it's needed for Week 12

Reflection Questions

Question 1

The external auditor needed three permissions to access a photo: sts:AssumeRole, s3:GetObject, and kms:Decrypt. For each one, explain what it controls and what would happen if it were missing.

Question 2

Compare how jerry (Identity Center) and external-auditor (IAM) log into the AWS console. What is different about their credentials, how they authenticate, and what CloudTrail records for each?
