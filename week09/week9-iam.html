IAM Deep Dive — Identities and Access Determination

The Infrastructure Identity Security concept module covered how IAM works. This week asks: where does IAM fall short, and what do you do about it?

Learning objectives
  • Identify the operational challenges of managing employee identity with IAM alone
  • Explain what IAM Identity Center adds on top of IAM and the mechanism underneath
  • Set up Identity Center with permission sets scoped to KMS keys
  • Demonstrate IAM role assumption via console Switch Role
  • Use the IAM Policy Simulator to map access — and recognize what it does not evaluate (KMS key policies, service principals)
  • Distinguish customer identity (Cognito) from employee identity (IAM / Identity Center)

1. Where we left off

Two issues remain from the prior concept page. First, uploaded files are still not scanned for malicious content — encryption protects data at rest but does not inspect it. That is a detection problem addressed in later weeks (Macie and GuardDuty). Second, there is no employee access management — the KMS key policies reference infra-admin and photos-admin roles that do not yet exist as real IAM principals. This week addresses the second gap.

The Photo Viewer has two populations of users, managed by different identity systems:

Cognito manages customer identity (application layer). IAM and Identity Center manage employee identity (infrastructure layer). The infrastructure layer has been managed with a single IAM admin user — AdministratorAccess — since the start of the course. As the team grows, this violates the principle of least privilege. Different employees need access to different resources.

The KMS separation of duties from last week maps directly: Tom needs the data key, Jerry needs the infra key. The key policies already enforce this boundary for Lambda roles — it now needs to extend to human operators.

2. This week's solution

Single account — scoped IAM users

Problem: One admin user with full access. No separation of duties for humans.

Solution: Create IAM users with scoped policies. Tom gets S3, DynamoDB, and kms:Decrypt on the data key. Jerry gets Secrets Manager, CloudFront, API Gateway, and kms:Decrypt on the infra key.

Tom can check customer photos and metadata but cannot access infrastructure secrets. Jerry can troubleshoot security configurations but cannot see user photos. For a single account, this is sufficient.

Multiple accounts

Problem: The Photo Viewer has real users. Deploying directly to production is risky — a bad Lambda update takes the app down for customers. A staging account lets the team test changes before they reach production. Now Tom and Jerry need access to both accounts. IAM users are per-account — they must be recreated with separate passwords and policies. If Tom leaves, his identity must be deleted from each account independently. Corporate identity policies (password rotation, MFA enforcement, automatic deactivation) do not apply to IAM users.

Two services address these problems — one for accounts, one for people.

3. Architecture

Two layers of management

AWS Organizations manages accounts — grouping them into organizational units (OUs), applying guardrails (SCPs), and consolidating billing. IAM Identity Center manages people — who can access which accounts, with what permissions. Identity Center requires Organizations as a prerequisite.

Click the left or right side of the diagram to learn more about each service.

AWS Organizations manages accounts. Accounts are grouped into Organizational Units (OUs) — Production and Staging in the lab. Service Control Policies (SCPs) set the maximum permissions for all accounts in an OU — even if an IAM policy allows an action, an SCP can block it. Consolidated billing aggregates costs across all accounts into a single bill. Organizations is a prerequisite for Identity Center.

IAM Identity Center manages people. Users are organized into groups (infra-team, photos-team). Each group is assigned a permission set (InfraAdmin, PhotosAdmin) for specific accounts. When a user logs in via the SSO portal and selects an account, Identity Center creates an IAM role from the permission set and calls STS:AssumeRole — issuing temporary credentials that expire automatically. One user, one directory, one disable to revoke all access.

Corporate identity — federation

Problem: Identity Center's built-in directory is still a separate identity silo. Tom has an Identity Center password and a corporate Okta password — two credentials, no connection. Disabling Tom's Okta account does not disable his Identity Center account.

Solution: Connect Identity Center to the corporate IdP. Tom authenticates through Okta. Identity Center maps him to the right permission sets. One identity, one deactivation point.

The lab uses Identity Center's built-in directory (no external IdP). The architecture is the same — centralized identity, permission sets, temporary credentials. Connecting an external IdP is a configuration step, not an architecture change.

Identity Center is IAM underneath

Identity Center is not a replacement for IAM — it is a layer on top. When a permission set is assigned to a user for an account, Identity Center creates an IAM role in that account. When the user logs in via the SSO portal and selects an account, Identity Center calls STS:AssumeRole and returns temporary credentials. Authorization still uses IAM policies and resource policies — on the assumed role, not a permanent user.

In the lab: After logging in via the SSO portal, the console top-right shows a role name like AWSReservedSSO_InfraAdmin_... — the IAM role Identity Center created. Part 2 of the lab does the same thing manually with Switch Role, exposing the mechanism Identity Center abstracts.

4. How a request flows — access determination

IAM does two things: identity verification (who are you?) and access management (are you allowed?). These happen in sequence — first you authenticate and get credentials, then every subsequent request is signed with those credentials and evaluated by the IAM engine.

Step 1 — Identity verification happens once per session. You authenticate with permanent credentials (username/password or API keys) or temporary credentials (STS). The result is credentials you can sign requests with.

Step 2 — Access management happens on every API call. The signed request reaches the resource. The resource hands it to the IAM policy engine, which evaluates the requester's IAM policy and the resource's resource policy (if one exists). The engine returns allow or deny. The resource does not evaluate policies itself.

The role of each policy differs by resource type. The decision tree below summarizes how a resource policy and an IAM policy combine to grant access; the tables that follow give the per-resource detail.

For mandatory resource policies (KMS key policies, role trust policies) the resource policy is the gatekeeper: it either delegates to IAM (then IAM grants access) or names the principal directly (then IAM can only deny). For optional resource policies (e.g. S3 buckets) either policy can grant.

Same-account access

ResourceIAM policyResource policyHow access is granted
S3 bucket Optional Optional Either IAM policy or bucket policy can grant access. An explicit deny in either one overrides. Policy evaluation = ED → EA → ID.
KMS key Optional ** Required The key policy is required. If it names the principal directly, the IAM policy isn’t needed and can only deny. But if the key policy delegates to IAM (the console default — see **), an IAM policy granting access is sufficient.
IAM role Optional * Required The trust policy is required. If it names the principal directly, the IAM policy isn’t needed and can only deny. But if it names the account root (the console default — see *), an IAM policy allowing sts:AssumeRole is also required.

* If the trust policy names the account root instead of a specific user, the IAM policy with sts:AssumeRole becomes required. When the trust policy names a specific user directly, the trust policy alone is sufficient.

** The KMS console wizard adds a statement to every key policy that delegates authority to IAM — it tells KMS to also evaluate IAM policies when a principal requests access. With this delegation in place, an IAM policy granting kms:Decrypt is sufficient even if the key policy does not name the principal directly. This is why Tom and Jerry's permission sets include kms:Decrypt — the delegation makes it work. In Part 3 of the lab, we take the direct approach instead: adding the auditor role to the key policy explicitly, without relying on delegation. Both approaches work — delegation is convenient for established employees, direct key policy grants are more explicit for temporary access.

Cross-account access

ResourceIAM policyResource policyHow access is granted
S3 bucket Required Required Both the IAM policy in the caller's account and the bucket policy in the resource's account must grant access.
KMS key Required Required Both the IAM policy in the caller's account and the key policy in the resource's account must grant access.
IAM role Required Required Both the IAM policy in the caller's account (allowing sts:AssumeRole) and the trust policy in the target account must grant access.

Cross-account access always requires both policies — the resource policy in the target account grants access, and the IAM policy in the caller's account allows the action. Neither alone is sufficient. This is why resource policies exist: they are the mechanism by which one account grants access to principals in another account.

KMS keys and IAM roles share the same posture for same-account access: the resource policy (key policy / trust policy) is mandatory. It grants access one of two ways — by naming the principal directly (then the IAM policy isn’t needed and can only deny), or by delegating to IAM (the console default: the key policy’s “enable IAM policies” statement, or a trust policy naming the account root), in which case an IAM policy granting the action does open the gate. S3 is more permissive: either policy can open the gate independently. Across accounts, all three resource types require both policies.

5. Key concepts

👥
IAM Identity Center & permission sets
Central employee identity — one user, per-account roles, temporary credentials
▼

Identity Center manages people from one central directory. A permission set (e.g. InfraAdmin, PhotosAdmin) assigned to a group for an account becomes an IAM role in that account. When a user signs in through the SSO portal and picks an account, Identity Center calls sts:AssumeRole and issues temporary credentials that expire automatically — the console then shows a role name like AWSReservedSSO_InfraAdmin_....

One user, one directory, one disable to revoke access everywhere. Identity Center requires AWS Organizations as a prerequisite.

🏢
AWS Organizations & SCPs
Account management — OUs, guardrails, consolidated billing
▼

Organizations manages accounts. Accounts are grouped into Organizational Units (OUs) — Production and Staging in the lab. Service Control Policies (SCPs) set the maximum permissions for every account in an OU: even if an IAM policy allows an action, an SCP can block it. Consolidated billing aggregates costs across all accounts into one bill. Organizations is the prerequisite for Identity Center.

🔄
Role assumption — STS & trust policies
Temporary credentials via sts:AssumeRole; the trust policy says who may assume
▼

A role is a persistent identity with no long-term credentials. To use it, a principal calls sts:AssumeRole and receives temporary credentials (access key, secret key, session token) that auto-expire. The role persists; only the credentials are temporary.

The role's trust policy — a resource-based policy — names who is allowed to assume it. Same-account: if the trust policy names the principal directly, that alone is sufficient; if it names the account root, the caller also needs sts:AssumeRole in their own IAM policy. Identity Center automates this whole path; Part 2 of the lab does it manually with console Switch Role.

🧪
IAM Policy Simulator
Tests whether access would be allowed or denied without real API calls — evaluates identity policies; two caveats
▼

The Policy Simulator lets you test whether a principal's access to a resource would be allowed or denied without making real API calls. It evaluates identity-based (IAM) policies.

Example: downloading an object from an SSE-KMS–encrypted bucket needs both your IAM policy to allow s3:GetObject and the KMS key policy to allow decrypt. Two caveats follow from this.

Caveat 1 — it doesn't evaluate KMS key policies. It only checks identity (IAM) policies. So it can report s3:GetObject as Allowed while the real download still fails because KMS denies the decrypt. You saw exactly this with the auditor in Part 3: Allowed in the simulator (Step 25), Access Denied in practice (Step 20), until the role was added to the data key's policy (Step 21). An IAM "allow" is necessary but not sufficient.

Caveat 2 — it can't evaluate Service principals in a resource policy. The simulator can evaluate bucket policies (via the "Include Resource Policy" option), but it can't model service principals. Our bucket policy still has the CloudFront OAC statement from Week 3, whose principal is a service (cloudfront.amazonaws.com). If the simulator tries to evaluate that, it halts with a yellow "Principal type 'Service'" banner and the result stays on "Not simulated."

Using it in the lab (Step 25): use the wildcard ARN arn:aws:s3:::YOUR-BUCKET/*. The Lambda execution role has s3:GetObject only on the uploads/* and photos/* prefixes (least privilege, from Week 7), so against the bucket-wide /* it shows Denied — expected, not an error; point the resource at a specific covered object to see Allowed. If you test a specific object and an "Include Resource Policy" box appears, leave it unchecked so the simulator doesn't try to evaluate our bucket policy and hit Caveat 2.

6. What's still missing

Uploaded files are still not scanned for malicious content
▼

Encryption protects data at rest from unauthorized access — it does not inspect data for harmful content. Macie detects PII in S3 objects. GuardDuty Malware Protection scans uploads. These are detection services — a different layer from encryption and access control.

No automated monitoring of security posture
▼

Security controls have been built manually — encryption, key policies, permission sets, role-based access. There is no mechanism to detect drift. AWS Config rules enforce desired state. CloudWatch alarms catch operational anomalies. Inspector scans for vulnerabilities. These are visibility and compliance tools — coming next.
