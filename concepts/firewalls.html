Firewalls — Types and Differences

Network firewalls and web application firewalls — what they inspect, where they sit, and how AWS managed services redistribute the responsibilities. Click any component in the diagrams to learn what it does.

Firewalls can be classified along two dimensions: what they inspect (which network layer) and how they process traffic (whether they track connections).

By inspection layer

Inspects packet headers — source IP, destination IP, port, protocol. Does not look inside the payload. Can be stateless or stateful (see below).

Limitation: No payload understanding. A SQL injection looks identical to a legitimate request at the IP/port level.

AWS examples: Security Groups, NACLs.

Everything a packet-filtering firewall does, plus deep packet inspection across all protocols. Application identification, IPS, TLS decryption. Broad coverage, shallower HTTP inspection than WAF.

Examples: Palo Alto, Fortinet. AWS: Network Firewall.

HTTP/HTTPS only. Parses headers, query strings, bodies, cookies, JSON/XML. Blocks SQLi, XSS, CSRF, OWASP Top 10. Narrow scope, extreme depth.

Examples: AWS WAF (CloudFront, ALB, API Gateway), Cloudflare WAF, Imperva.

By connection tracking

Evaluates each packet in isolation. No memory of previous packets. If you allow inbound traffic, you must write a separate rule to allow the outbound response — the firewall has no concept of "this response belongs to that request."

A stateless rule allowing inbound on ephemeral ports can't distinguish a legitimate response from an unsolicited probe on the same port. It also can't detect invalid TCP states (a SYN-ACK arriving without a preceding SYN) or enforce connection timeouts.

On-prem: Router ACLs. AWS: NACLs. In practice, both are usually left at default allow-all, with the stateful layer doing the real filtering.

Maintains a connection table. When an outbound request is sent, the firewall remembers it and automatically allows the matching response — no separate return rule needed. It knows "this inbound packet on ephemeral port 52341 is a response to the outbound request my server made to google.com:443 three seconds ago."

This means it can reject unsolicited inbound packets on ephemeral ports (no matching outbound request), detect invalid TCP states (SYN-ACK without SYN), and expire stale sessions (connection closed, stop allowing traffic).

On-prem: Traditional firewalls (both external and internal), host-based firewalls (iptables). AWS: Security Groups. This is why Security Groups only need inbound rules — return traffic is automatically allowed.

Internet — the hostile pipe

Carries all protocols — HTTP, SSH, DNS, SMTP, custom protocols, malicious traffic. Port scans, spoofed packets, fragmentation attacks all arrive here. This is why the perimeter NGFW is critical.

NGFW — Perimeter Firewall

Outermost boundary. L3/L4 filtering, application identification, IPS, TLS decryption. Blocks unauthorized protocols — only HTTP/HTTPS passes through to the DMZ. Broad L7 but doesn't parse HTTP requests deeply.

Load Balancer — TLS termination

First stop in the DMZ. Terminates TLS so downstream traffic is decrypted HTTP. Distributes requests across web servers. Sometimes integrated with WAF (F5 BIG-IP combines both).

In AWS: ALB or CloudFront.

WAF — Reverse Proxy

Behind the load balancer, in front of web servers. Sees clean, parsed HTTP. Inspects headers, query strings, POST bodies, cookies, JSON/XML. Catches SQLi, XSS, command injection, CSRF — attacks the NGFW can't see.

Web Servers

In the DMZ. Process HTTP requests that passed through NGFW and WAF. Communicate with backend app servers on the private network. Never talk directly to the database in three-tier architecture.

Internal Firewall — Segmentation + Egress

A stateful firewall between the DMZ and internal network, doing two jobs. First, east-west segmentation: controlling which internal resources can talk to which — app servers only accept traffic from web servers, workstations can't reach databases directly. This prevents lateral movement if a web server is compromised. Second, egress filtering: controlling what outbound connections internal servers can make, preventing compromised hosts from contacting attacker infrastructure.

In AWS, these two jobs get unbundled into separate services. Segmentation is handled by Security Groups — both are stateful, but SGs attach to individual hosts rather than sitting at a network boundary. SGs are so easy to manage in AWS (reference by SG ID, managed via API) that they absorbed this role without needing a separate appliance. Egress filtering is handled by Network Firewall at the VPC boundary — or eliminated entirely by going serverless.

Router + ACLs

Stateless rules on routers/switches filtering by IP, port, protocol per interface (Cisco IOS, Juniper JunOS). The on-prem equivalent of NACLs — both stateless, both at network infrastructure level, both evaluated in rule-number order.

Workstations — Client Endpoint Protection

Host-based firewalls (Windows Firewall, macOS Firewall) plus AV/EDR. Closest architectural equivalent of Security Groups — both host-level, both stateful. On-prem, managing these across hundreds of machines is painful, so organizations lean on the internal firewall instead.

App Servers

Private network, behind internal firewall and router ACLs. Only receive traffic from web servers. Run host-based firewalls (iptables on Linux) and endpoint protection.

Database Servers

Deepest layer — only talk to app servers. Non-HTTP protocols (MySQL 3306, PostgreSQL 5432), so WAF can't inspect this traffic.

Internet → CloudFront — no hostile pipe

CloudFront only forwards HTTP/HTTPS. Nobody can send SSH probes or DNS queries through it. The perimeter NGFW's protocol-filtering job is handled by the nature of the service.

CloudFront — absorbs perimeter duties

Terminates TLS at edge locations, only forwards HTTP/HTTPS. Traffic to origin runs over AWS's private backbone. Shield Standard (free) provides L3/L4 DDoS protection.

AWS WAF — at the CDN edge

On-prem, WAF sat in the DMZ behind the perimeter NGFW. In AWS, it attaches to CloudFront and runs at the CDN edge — in front of everything. Malicious requests are blocked at edge locations worldwide, never consuming your origin's bandwidth or compute.

Uses Web ACLs containing rule groups (AWS Managed Rules, third-party, or custom) evaluated in priority order. Each rule can count, allow, block, or CAPTCHA a request.

Security Groups + NACLs

NACLs are stateless, subnet-level rules — the equivalent of router ACLs on-prem. Security Groups are stateful, host-level — the equivalent of host firewalls (iptables), but they also absorbed the on-prem internal firewall's segmentation role because they're so easy to manage. You reference one SG from another by ID: "ALB security group only accepts from CloudFront IPs. EC2 security group only accepts from ALB security group. DynamoDB endpoint security group only accepts from EC2 security group." That's microsegmentation without a separate boundary device.

ALB — Application Load Balancer

Distributes traffic to compute targets (EC2 instances, containers). Should be locked down so only CloudFront can reach it — typically via a custom origin header stored in Secrets Manager — preventing attackers from bypassing the CDN edge and its WAF.

You can attach a second WAF Web ACL here with app-specific rules that differ from the broad rules at the CloudFront edge. For example: the edge WAF handles the OWASP core rule set, bot filtering, and geo-blocking (rules that apply to all traffic). The ALB WAF handles application-specific logic like "this endpoint only accepts POST with a JSON body" or "rate-limit the /login path to 10 requests per minute per IP." Two layers, different rule sets, different concerns.

Lambda / EC2

With a server-based backend (EC2), instances are persistent machines with an operating system, a writable filesystem, a shell, and network tools. A compromised server becomes a platform — an attacker can install reconnaissance tools, scan internal networks for open ports, attempt lateral movement to other servers, and establish outbound connections to command-and-control infrastructure. This is why the on-prem model needed both an internal firewall (to contain lateral movement) and egress filtering (to block C2 callbacks).

With a serverless backend (Lambda), both threats collapse. There is no persistent host — functions execute in ephemeral containers for milliseconds, then disappear. No SSH, no writable persistent filesystem, no long-lived network stack to pivot from. Even if an attacker achieves code execution inside a Lambda invocation, there's nothing to pivot to — and nothing persists for a command-and-control channel to take over. This is one of the strongest security arguments for serverless — not just less infrastructure to manage, but the entire lateral movement threat model disappears.

DynamoDB / RDS

DynamoDB: HTTPS API, no database port to protect. Access via IAM policies, not network rules. Managed services shrink the surface area firewalls need to cover.

Network Firewall — NGFW for what remains

With the perimeter role absorbed by CloudFront and Security Groups, Network Firewall's primary value in AWS is egress filtering — controlling which outbound destinations your servers can reach. For example, whitelisting pypi.org for package downloads and blocking all other outbound connections to prevent compromised instances from contacting attacker infrastructure.

It also applies to organizations with multiple VPCs or hybrid connections to on-premises networks, where traffic hasn't been filtered by CloudFront and needs network-level inspection.

Internet → CloudFront — same as server-based

CloudFront only forwards HTTP/HTTPS. The perimeter NGFW's protocol-filtering role is handled by the nature of the service — identical in both architectures.

CloudFront — same role, same position

Terminates TLS, filters protocols, routes to origin over private backbone. Shield Standard provides L3/L4 DDoS. No change from server-based.

AWS WAF — still at the CDN edge

Same WAF, same position, same rules. The CDN edge remains your first line of L7 defense regardless of backend architecture. OWASP rules, bot filtering, rate limiting — all still here.

API Gateway + Lambda Authorizer

In the server-based model, checking the secret header from CloudFront required a WAF Web ACL on the ALB — a heavyweight tool for a simple string match. API Gateway provides Lambda authorizers — a lightweight Python function that reads the header, compares it to the value in Secrets Manager, and returns allow or deny.

Same L7 inspection, but done in a few lines of code rather than a full WAF deployment. This is a natural fit because it's an authorization decision ("are you allowed in?"), not a content inspection decision ("is this payload malicious?").

Lambda — no persistent server

Functions execute in ephemeral containers for milliseconds, then disappear. No OS, no writable persistent filesystem, no shell, no network stack to pivot from. Even with code execution, an attacker has nothing to pivot to.

What disappeared: No VPC means no Security Groups, no NACLs, no Network Firewall. The entire internal firewall layer — segmentation and egress control — is eliminated because the threat it protected against (lateral movement) no longer exists.

DynamoDB — IAM-controlled access

No database port, no network-level access control needed. The Lambda execution role determines what the function can read and write — access control through identity, not firewalls. If you follow least privilege, the role allows access to one table and nothing else.

2 AWS Firewall Manager

In the diagrams above, we looked at individual firewalls — WAF, Security Groups, Network Firewall. But in a real enterprise with dozens or hundreds of AWS accounts, the problem isn't configuring one firewall correctly. It's ensuring every firewall across every account is correctly and consistently configured. A single missed WAF rule or an overly permissive security group in one account is all an attacker needs.

AWS Firewall Manager solves this. It's not a firewall — it's the management plane for all firewall types. From a single administrator account, you define security policies and Firewall Manager enforces them across your entire AWS Organization.

Ensure every CloudFront distribution and every ALB in the organization has the required Web ACL with your baseline rule groups (e.g., AWS Managed Rules Core Rule Set, SQLi protection, known bad inputs). If a developer in any account creates a new ALB without attaching a WAF, Firewall Manager detects it and auto-remediates — attaching the required Web ACL automatically.

This is the most commonly used policy type and remains relevant in both server-based and serverless architectures, since CloudFront + WAF is the edge defense in both.

Audit and enforce security group configurations across all accounts. Two modes: audit policies flag violations (e.g., any security group with SSH port 22 open to 0.0.0.0/0) and usage policies identify and clean up unused security groups that accumulate over time.

For common baselines, Firewall Manager can distribute a standard set of security group rules to all VPCs — ensuring, for example, that every EC2 instance blocks inbound SSH from the public internet regardless of which account or team deployed it.

Deploy and manage Network Firewall endpoints and rule groups across VPCs consistently. Define egress filtering rules centrally — for example, whitelist pypi.org and npmjs.com for package downloads, block all other outbound traffic — and Firewall Manager ensures every VPC with EC2 instances has the Network Firewall endpoint deployed with those rules.

Less relevant in fully serverless architectures where there is no VPC, but essential for organizations with EC2-based workloads or hybrid connectivity to on-premises networks.

Enable AWS Shield Advanced DDoS protection consistently across accounts and resources — CloudFront distributions, ALBs, Elastic IPs. Shield Advanced provides real-time attack visibility, automatic application-layer mitigations, and access to the AWS DDoS Response Team (DRT).

Shield Standard (free, L3/L4 DDoS protection) is automatically enabled on all AWS resources. Shield Advanced ($3,000/month subscription) adds application-layer protections and is typically deployed through Firewall Manager to ensure consistent coverage.

Key point: Firewall Manager doesn't replace any firewall. It ensures they are all consistently deployed and correctly configured across every account in the organization. The on-prem equivalent is a vendor management console (Panorama for Palo Alto, FortiManager for Fortinet) — but Firewall Manager is unique in that it manages multiple types of firewalls (WAF, SGs, Network Firewall, Shield) from a single pane. At $100 per policy per region per month, this is a concept-only topic — no lab — but it represents a critical distinction: configuring security for one application vs governing security across an enterprise.

Firewalls in our Photo Viewer project

Here's how the firewall layers we've discussed apply to the two Photo Viewer architectures we've built:

Photo Viewer (server-based): Internet → CloudFront + WAF → AWS backbone → ALB (+ WAF for secret check) → EC2 → DynamoDB. Security Groups handle segmentation between tiers. Network Firewall handles egress filtering for outbound EC2 traffic (e.g., whitelisting pypi.org). The full firewall stack is needed — L7 content inspection at the edge, L3/L4 segmentation inside the VPC, and egress control at the VPC boundary.
Photo Viewer (serverless): Internet → CloudFront + WAF → AWS backbone → API Gateway + Lambda Authorizer → Lambda → DynamoDB. No VPC, no ALB, no EC2, no NAT Gateway. The Lambda Authorizer — a lightweight Python function — replaces the WAF secret-header check on the ALB. There is no persistent server to compromise, no internal network to scan. Security Groups, NACLs, and Network Firewall are all unnecessary. The entire internal firewall layer disappears because the threat it protected against — lateral movement — no longer exists.
