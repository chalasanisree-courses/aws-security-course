Understanding Vulnerabilities

What vulnerabilities are, how they are classified and scored, and how AWS services detect them. Background reading for the Week 10 vulnerability assessment lab.

1. Threat, vulnerability, and risk

These three terms are distinct. A threat is anything that can cause harm — an attacker, a natural disaster, a careless employee. A vulnerability is a weakness in a system that could be exploited. A vulnerability exists whether or not anyone exploits it. Risk is what happens when the two meet: the likelihood and impact of a threat exploiting a vulnerability.

The risk equation
Threat
What can cause harm
×
Vulnerability
Weakness that makes harm possible
=
Risk
Likelihood & impact of harm

A vulnerability does not cause harm by itself. An attacker scanning the internet is a threat, but harmless if there is no vulnerability to exploit. Risk only exists when both are present.

2. Three types of vulnerabilities

Configuration vulnerabilities

The system works, but it is not set up correctly. These are the most common real-world vulnerabilities and are often the easiest to fix.

Examples: An S3 bucket with public read access enabled. A Lambda function with an overly permissive IAM role. An RDS instance using default credentials. A security group allowing SSH from 0.0.0.0/0. CloudTrail encryption downgraded from KMS to SSE-S3.

Why they’re dangerous: The application keeps working. No errors, no outages. The misconfiguration is invisible until someone exploits it — or until a monitoring tool catches it.

In the course: AWS Config detects configuration vulnerabilities. You define rules that describe the desired configuration, and Config flags any resource that drifts. AWS Trusted Advisor checks a fixed set of configuration best practices across the account.
Software vulnerabilities

The code — either yours or a dependency you included — has a flaw that can be exploited. Not all bugs are vulnerabilities; only bugs that can be used to cause harm qualify.

Examples: A Python library (Pillow 9.5.0) with a known arbitrary code execution flaw in ImageMath.eval. Apache Log4j 2.14.1 allowing remote code execution via crafted log messages. A buffer overflow in an HTTP server.

Why they’re dangerous: You may not even know the vulnerability exists. It lives inside a dependency you imported, in code you never read. Attackers can find it by checking the CVE databases and matching it against your exposed software versions.

In the course: Amazon Inspector detects software vulnerabilities. It scans your Lambda deployment packages against the National Vulnerability Database, identifying which packages have known CVEs, what severity they carry, and how to remediate them.
Architectural vulnerabilities

The design of the system itself creates weakness. Individual components may be configured correctly and running clean code, but the way they connect creates exposure.

Examples: A flat network where a compromised vendor system can reach the point-of-sale system (Target, 2013). An IAM role on an EC2 instance with access to every S3 bucket in the account (Capital One, 2019). Implicit trust inside a VPC with no segmentation.

Why they’re dangerous: Architectural vulnerabilities magnify the impact of other failures. A single compromised component can reach everything because the design didn’t enforce boundaries. These are the hardest to fix because they require redesigning the system, not just changing a setting.

In the course: Architectural vulnerabilities are addressed through design decisions across the entire course — VPC segmentation, least-privilege IAM, defense-in-depth layering, CloudFront + OAC instead of direct S3 access. The AWS Well-Architected Framework is the methodology for identifying these weaknesses.

3. CVE, CVSS, and the National Vulnerability Database

When a vulnerability is discovered, it needs a name, a severity score, and a public record. Three systems provide this.

CVE — Common Vulnerabilities and Exposures

A CVE is a unique identifier for a specific vulnerability. The format is CVE-YYYY-NNNNN — year of assignment followed by a sequence number. A CVE is not an exploit; it is a label. Two examples from the course:

CVENameWhat it affectsImpact
CVE-2021-44228Log4ShellApache Log4j (Java logging library)Remote code execution via crafted log messages
CVE-2023-50447—Pillow (Python imaging library)Arbitrary code execution in ImageMath.eval

CVSS — Common Vulnerability Scoring System

CVSS assigns a severity score from 0.0 to 10.0 based on how easily the vulnerability can be exploited and how much damage it can cause. The score determines how urgently you need to respond.

None0.0
Low0.1–3.9
Medium4.0–6.9
High7.0–8.9
Critical9.0–10.0

Log4Shell scored 10.0 — the maximum. Remote code execution, no authentication required, trivially exploitable. The Pillow vulnerability (CVE-2023-50447) scored 8.1 — high, but not critical, because the vulnerable code path (ImageMath.eval) is not commonly used.

NVD — National Vulnerability Database

The NVD, maintained by NIST, is the public database where CVEs are recorded with full details: affected products, severity scores, references to vendor advisories, and remediation guidance. When Amazon Inspector finds a vulnerability in your Lambda function, the CVE identifier it reports links back to this database.

Other useful resources: CVE Details provides a searchable interface for browsing vulnerabilities by vendor, product, or year. CISA’s Known Exploited Vulnerabilities (KEV) catalog lists CVEs that are confirmed to be actively exploited in the wild — these are the ones that demand immediate attention.

4. Vulnerability lifecycle

Every vulnerability follows a lifecycle. Understanding where a vulnerability sits in this lifecycle determines how you respond.

1
Introduction: The vulnerability is created — a developer writes a bug, an administrator misconfigures a setting, or an architect makes a design decision that creates exposure. Nobody knows it exists yet.
2
Silent existence: The vulnerability is live in production. The application works fine. Months or years may pass. The longer this phase lasts, the greater the risk — attackers are always looking.
3
Discovery: Someone finds the vulnerability. This could be a security researcher (good), Google’s Project Zero team (good), or an attacker (bad). If the good guys find it first, there is time to prepare a fix before disclosure.
4
Disclosure: The vulnerability is publicly documented — a CVE is assigned, the NVD entry is created. Ideally, the vendor releases a patch at the same time. If the flaw is being exploited before a fix exists — the vendor has had “zero days” to patch — it is a zero-day. Log4Shell was a zero-day: it was exploited in the wild within hours of disclosure, before most systems could be patched.
5
Patch available: The vendor releases a fix. The vulnerability is no longer a mystery — the CVE is public, the patch is public, and the clock is ticking. Attackers now know exactly what to look for in unpatched systems.
6
Unpatched window: Some systems are patched. Others are not. Known vulnerabilities are exploited long after disclosure because organizations are slow to patch. The Equifax breach (2017) exploited a vulnerability that had been patched two months earlier.

Why this matters for the lab: Amazon Inspector continuously scans your Lambda functions for known CVEs. It catches vulnerabilities in phase 5 — the patch exists but you haven’t applied it yet. Without Inspector, your functions sit in phase 2 indefinitely: vulnerable, working fine, and invisible.

5. How vulnerabilities are discovered

Both attackers and defenders use the same techniques to find vulnerabilities. The difference is what they do with the information.

Port scanning

Scanning a target system to identify open network ports and the services running on them. An open port running an outdated web server version tells an attacker exactly which CVEs to try. In AWS, security groups and NACLs control which ports are exposed. Trusted Advisor checks for unrestricted security groups as one of its fixed best-practice rules.

Reconnaissance

Gathering information about a target’s internal architecture without directly attacking it. What operating system is the server running? What web server version? What frameworks? Attackers use HTTP response headers, error messages, and DNS records to build a picture of the target. In AWS, services like CloudFront strip server headers and error details to reduce the information available to attackers.

Vulnerability scanning

Automated tools that inventory your software and compare versions against the National Vulnerability Database. This is exactly what Amazon Inspector does for Lambda functions and EC2 instances. The scanner doesn’t try to exploit anything — it checks whether the version you are running has known CVEs.

Penetration testing

Authorized simulated attacks against your own systems to find vulnerabilities before real attackers do. Unlike scanning, penetration testing actually attempts to exploit weaknesses. AWS allows penetration testing on your own resources without prior approval for most services, but some activities (like DDoS simulation) require authorization.

6. AWS tool mapping

In AWS, the three vulnerability types map to specific services:

⚙
AWS Config + AWS Trusted Advisor → Configuration vulnerabilities

Config continuously records resource configuration and evaluates managed rules to detect drift. Trusted Advisor runs a fixed set of best-practice checks — unrestricted security groups, MFA on root, S3 bucket permissions. Together, they catch misconfigured knobs — the settings AWS exposes to you.

🐛
Amazon Inspector → Software vulnerabilities

Inspector scans your Lambda deployment packages and EC2 instances against the NVD. It identifies CVEs in your dependencies — the code you bring to AWS. It reports the CVE identifier, CVSS score, affected package version, and remediation guidance.

🏗
AWS Well-Architected Framework → Architectural vulnerabilities

Architectural vulnerabilities require human judgment, not automated scanning. The Well-Architected Framework provides the methodology — six pillars of review questions that surface design-level weaknesses like missing network segmentation, implicit trust, and excessive permissions.

The boundary: Config and Trusted Advisor watch the knobs that AWS exposes to you — are they set correctly? Inspector watches what you bring to AWS — are your dependencies secure? The Well-Architected Framework evaluates how you connect everything together — is the design sound?
