Infrastructure Identity Security

IAM identity types, policy families, access evaluation logic, and identity federation — the framework for how AWS decides who can do what. This concept module bridges application-layer identity (Weeks 6–7) and encryption access control (Week 8).

1. Two layers of identity

In Weeks 6 and 7, we secured identity at the application layer — the people who use the Photo Viewer. Cognito and Google login handle authentication, JWT claims and Lambda logic handle authorization, and ownership checks prevent users from modifying each other's photos.

But there's another set of people: the ones who operate the Photo Viewer. Developers who update Lambda code, infrastructure admins who manage API Gateway and CloudFront, security auditors who review CloudTrail logs. These people log into the AWS Console — not the Photo Viewer. Their identity and access is managed by a different system: AWS IAM.

Every SaaS product has both layers. They should never be the same system.

2. Three IAM identity types

Click to expand each identity type.

👤
IAM Users
Permanent identity with long-lived credentials
▼

An IAM user is a permanent identity within an AWS account. It has a username, a console password, and optionally access keys for CLI or API access. These credentials are long-lived — they don't expire unless you manually rotate them.

The IAM admin user you created in Week 1 is an IAM user. It's what you've been logging into the console with every week. The policy attached to it was permissive — AdministratorAccess — which is why you've been able to use every AWS service freely.

The problem with IAM users: If credentials leak — pasted into a GitHub repo, stored in a script, left on a stolen laptop — they remain valid until someone manually revokes them. There is no automatic expiration. In a team, if multiple people share one IAM user, CloudTrail shows which credentials were used but not which human. You can't investigate an incident if you can't distinguish between people.

👥
IAM Groups
Container for users — simplifies policy assignment
▼

A group is a container for IAM users. You attach policies to the group; every user in the group inherits those policies. Groups don't have credentials — you can't log in as a group. They're purely an organizational and policy-assignment mechanism.

Instead of writing the same IAM policy for ten developers individually, you create a developers group, attach the policy once, and add all ten users. If a new developer joins, add them to the group. If someone leaves, remove them.

In the Week 9 lab, you'll create developers and infra-admins groups — each with policies scoped to different KMS keys, enforcing the separation of duties from Week 8 at the human level.

🎭
IAM Roles
Temporary identity with short-lived credentials — assumed by services or humans
▼

A role has no permanent credentials. When something assumes a role, it gets temporary credentials from STS (Security Token Service) that expire automatically — typically in minutes to hours.

You've already been using roles. The Lambda execution role from Week 5 is an IAM role. Every time Lambda runs your function, it assumes that role and gets temporary credentials for the duration of that invocation. The EC2 instance profile from Week 4 is also backed by an IAM role. Roles aren't just for services — humans can assume roles too.

When a human assumes a role via the console's "Switch Role" feature or via sts:AssumeRole in the CLI, they get temporary credentials scoped to that role's policies. When the session expires, the credentials are gone. No keys to leak, no passwords to rotate.

In the Week 9 lab, an external auditor with zero standing permissions will assume an auditor role to get temporary access to DynamoDB — and you'll see both sides of the trust relationship required for this to work.

Identity federation — the Cognito parallel

In Weeks 6–7, Photo Viewer users were redirected to Google to log in, then returned to the app with a JWT. The same pattern works for AWS access: Foothill College's identity system (Duo) can be trusted by AWS IAM, so when an instructor tries to access AWS, they're redirected to Duo, authenticated, and returned with temporary credentials mapped to a role. The user directory stays at Foothill — no need to recreate all users inside AWS IAM. This is called identity federation, and it's the conceptual foundation for IAM Identity Center (covered in Week 12).

3. Two policy families

Every access decision in AWS involves the same question: does this principal have permission to perform this action on this resource? The answer comes from two types of policies.

📋
Identity-based policies (IAM policies)
Attached to a principal — "what is this identity allowed to do?"
▼

An identity-based policy is attached to a user, group, or role. It answers: "what is this principal allowed to do?"

You've been writing these since Week 4. The Lambda execution role's policy says:

{
  "Effect": "Allow",
  "Action": [
    "dynamodb:Scan",
    "dynamodb:GetItem",
    "dynamodb:PutItem",
    "dynamodb:DeleteItem"
  ],
  "Resource": "arn:aws:dynamodb:us-east-1:ACCOUNT-ID:table/PhotoViewerPhotos"
}

This policy follows the principle of least privilege — it grants only the specific DynamoDB actions needed, only on the specific table needed. Not dynamodb:*, not Resource: *.

🏷️
Resource-based policies
Attached to a resource — "who is allowed to access this resource?"
▼

A resource-based policy is attached to the resource itself, not to a principal. It answers: "who is allowed to access this resource?"

You wrote one in Week 3 — the S3 bucket policy that allows CloudFront's Origin Access Control to read from the bucket:

{
  "Effect": "Allow",
  "Principal": {
    "Service": "cloudfront.amazonaws.com"
  },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::BUCKET-NAME/*",
  "Condition": {
    "StringEquals": {
      "AWS:SourceArn": "arn:aws:cloudfront::ACCOUNT-ID:distribution/DISTRIBUTION-ID"
    }
  }
}

Because it's on an S3 bucket, we call it a bucket policy. On a KMS key, it's a key policy. On an SQS queue, a queue policy. On an IAM role (its trust policy), a trust policy. They're all resource-based policies — same concept, different resource.

4. Policy evaluation — how AWS decides

When a request is made, AWS collects all applicable policies — identity-based and resource-based — and evaluates them together. The rule is simple:

⚖️
Explicit deny → Explicit allow → Implicit deny
Deny always wins. Silence means no.
▼

1. Explicit deny always wins. If any policy — identity-based or resource-based — contains an explicit "Effect": "Deny" for the action, access is denied. No other policy can override this.

2. Explicit allow. If no policy explicitly denies, and at least one policy explicitly allows, access is granted.

3. Implicit deny. If no policy says anything — no allow, no deny — the default is denied. Silence means no.

Example: A developer named Mike has an IAM policy allowing s3:DeleteObject on the Photo Viewer bucket. But the bucket policy explicitly denies s3:DeleteObject for everyone except the Lambda execution role. Mike tries to delete a photo. The bucket policy's explicit deny wins — Mike cannot delete, even though his IAM policy allows it.

This is a powerful security property: a resource owner can always protect their resource, regardless of what IAM policies exist on the other side.

5. Why both policy families exist

🏦
Cross-account access
Two accounts, both must agree
▼

Imagine the Photo Viewer grows, and now there's a separate AWS account for production and one for development. A developer in the dev account needs to access an S3 bucket in production. The dev account's IAM policy alone isn't sufficient — the production account doesn't know about it. The production S3 bucket must explicitly say, via a resource policy, "I allow this role from this other account." Both sides must agree.

Think of it like a bank: to transfer money from another person's account, you need permission to initiate the transfer, and the other account must authorize it.

🛡️
Protecting a resource within the same account
Resource policies as a defensive boundary
▼

Even within one account, you might want to ensure that only the Lambda execution role can write to DynamoDB — not any developer, not any admin, regardless of what IAM policies get attached to them in the future. A resource policy with an explicit deny for all principals except Lambda ensures this. The explicit deny wins over any IAM policy, providing a defensive boundary at the resource level.

What's next — KMS key policies

In Week 8, you'll see a service where the resource-based policy isn't just optional — it's required. KMS key policies are resource policies on encryption keys, but unlike S3, where a bucket policy is optional, KMS won't even evaluate your IAM policies unless the key policy explicitly enables it. The key policy is the root of trust. This makes encryption keys the most tightly controlled resource in AWS — even a compromised IAM admin can't decrypt data if they're not in the key policy.
