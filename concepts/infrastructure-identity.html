Infrastructure Identity Security

IAM answers two questions: who are you? (identity types) and what are you allowed to do? (policies). This page covers both. Click any element in the diagrams to jump to its explanation.

1. Two layers of identity

We've already secured identity at the application layer — app users logging in via Google, authorized by JWT claims and Lambda logic. This module covers the infrastructure layer — the developers, admins, and auditors who log into the AWS Console to operate the Photo Viewer. Their identity is managed by AWS IAM.

Application layerInfrastructure layer
WhoApp users (customers)Employees (operators)
AuthenticationCognito + Google → JWTIAM login or role assumption
AuthorizationJWT claims → Lambda logicIAM + resource policies

Every SaaS product has both layers. They should never be the same system.

2. IAM at a glance

Click any box to jump to its explanation.

Policies can attach to either side. An IAM policy attaches to an identity and says "what can this identity do?" A resource policy attaches to a resource and says "who can access me?" When an access request happens, both are evaluated together. The rest of this page walks through each part.

3. WHO — Three IAM identity types

Click to expand each.

👤
IAM Users
Permanent identity with long-lived credentials
▼

An IAM user is a permanent identity within an AWS account. It has a username, a console password, and optionally access keys for CLI or API access. These credentials are long-lived — they don't expire unless you manually rotate them.

The IAM admin user you created at the start of this course is an IAM user. It's what you've been logging into the console with every week. The policy attached to it — AdministratorAccess — is why you've been able to use every AWS service freely.

The problem with IAM users: If credentials leak — pasted into a GitHub repo, stored in a script, left on a stolen laptop — they remain valid until someone manually revokes them. There is no automatic expiration. In a team, if multiple people share one IAM user, CloudTrail shows which credentials were used but not which human.

👥
IAM Groups
Container for users — simplifies policy assignment
▼

A group is a container for IAM users. You attach policies to the group; every user in the group inherits those policies. Groups don't have credentials — you can't log in as a group. They're purely an organizational and policy-assignment mechanism.

Instead of writing the same IAM policy for ten developers individually, you create a developers group, attach the policy once, and add all ten users. If a new developer joins, add them to the group. If someone leaves, remove them.

🎭
IAM Roles
Temporary identity with short-lived credentials — assumed by services or humans
▼

A role has no permanent credentials. When something assumes a role, it gets temporary credentials from STS (Security Token Service) that expire automatically — typically in minutes to hours.

You've already been using roles. The Lambda execution role is an IAM role. Every time Lambda runs your function, it assumes that role and gets temporary credentials for the duration of that invocation. The EC2 instance profile is also backed by an IAM role. Roles aren't just for services — humans can assume roles too.

When a human assumes a role via the console's "Switch Role" feature or via sts:AssumeRole in the CLI, they get temporary credentials scoped to that role's policies. When the session expires, the credentials are gone.

Identity federation — the Cognito parallel

Photo Viewer users are redirected to Google to log in, then returned with a JWT. The same pattern works for AWS: Foothill College's identity system (Duo) can be trusted by AWS IAM, so an instructor is redirected to Duo, authenticated, and returned with temporary credentials mapped to a role. This is identity federation — a pattern we'll return to later in the course.

4. WHAT — Anatomy of a policy

Policies are JSON documents with a consistent structure. Click any highlighted field to see what it does. The example below includes a Principal, which makes it a resource-based policy (e.g. a bucket policy). An identity-based policy looks identical but omits the Principal — the principal is whoever the policy is attached to.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::ACCOUNT-ID:user/mike" },
    "Action": [
      "s3:GetObject",
      "s3:ListBucket"
    ],
    "Resource": [
      "arn:aws:s3:::cs55d-bucket",
      "arn:aws:s3:::cs55d-bucket/*"
    ],
    "Condition": {
      "IpAddress": { "aws:SourceIp": "12.34.56.0/24" }
    }
  }]
}
↑ Click any highlighted field above to see what it does.

Version — policy language version

This is the IAM policy language version, not a date you set. It's always "2012-10-17". AWS uses it to determine which policy features are available (for example, policy variables like ${aws:username} require this version).

Just include it in every policy and move on. There is no newer version.

Effect — allow or deny?

"Allow" or "Deny". Only two options. Says whether the statement grants or blocks access.

In this example: Allow — Mike is being granted access.

Principal — who?

Who is this policy about? Can be a specific IAM user, a role, a service ("Service": "cloudfront.amazonaws.com"), or everyone ("*").

Key distinction: In identity-based policies (attached to a user/group/role), Principal is omitted. In resource-based policies (attached to a resource), Principal is required.

Here: the principal is IAM user mike. Since Principal is present, this is a resource-based policy.

Action — what can they do?

Specified as service:operation. You can list multiple or use wildcards like s3:Get*. Principle of least privilege: list only the specific actions needed.

Least privilege question: Does Mike need s3:ListBucket? If he only downloads specific files, removing it tightens the policy.

Here: Mike can download objects and list bucket contents.

Resource — which specific resource?

Specified as an ARN (Amazon Resource Name). "*" means all resources — violates least privilege. Always scope to the specific resource.

Two ARNs here because ListBucket operates on the bucket while GetObject operates on objects inside. S3 treats these as different resources.

Here: the cs55d-bucket and all objects inside it.

Condition — under what circumstances?

Optional. Adds constraints: source IP, time of day, MFA required, encryption key. If the condition isn't met, the statement doesn't apply.

Here: only applies from IP range 12.34.56.0/24. From any other IP, this statement is ignored.

5. Two policy families and how they're evaluated

The overview diagram showed that policies can attach to either side. Here's the detail. Click on the policies to expand their explanations below.

📋
Identity-based policies (IAM policies)
Attached to a principal — "what is this identity allowed to do?"
▼

Attached to a user, group, or role. No Principal field — the principal is whoever the policy is attached to.

The Lambda execution role's policy:

{
  "Effect": "Allow",
  "Action": [
    "dynamodb:Scan",
    "dynamodb:GetItem",
    "dynamodb:PutItem",
    "dynamodb:DeleteItem"
  ],
  "Resource": "arn:aws:dynamodb:us-east-1:ACCOUNT-ID:table/photoviewer-photos"
}

Notice there's no Principal — the principal is implicit (the Lambda role this policy is attached to). Least privilege: only the specific DynamoDB actions needed, only on the specific table.

🏷
Resource-based policies
Attached to a resource — "who is allowed to access this resource?"
▼

Attached to the resource itself. Principal is required — it names who can access.

The S3 bucket policy that allows CloudFront's OAC to read from the bucket:

{
  "Effect": "Allow",
  "Principal": {
    "Service": "cloudfront.amazonaws.com"
  },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::BUCKET-NAME/*",
  "Condition": {
    "StringEquals": {
      "AWS:SourceArn": "arn:aws:cloudfront::ACCOUNT-ID:distribution/DIST-ID"
    }
  }
}

Notice the Principal field names CloudFront, and the Condition restricts it to one specific distribution.

On an S3 bucket: bucket policy. On a KMS key: key policy. On an IAM role: trust policy. All resource-based policies — same concept, different resource.

⚖
Policy evaluation — explicit deny > explicit allow > implicit deny
Deny always wins. Silence means no.
▼

1. Explicit deny always wins. If any policy — identity-based or resource-based — contains "Effect": "Deny", access is denied. Nothing overrides this.

2. Explicit allow. If nothing denies and at least one policy allows, access is granted.

3. Implicit deny. If no policy says anything, the default is denied. Silence means no.

Example: A developer named Mike has an IAM policy allowing s3:DeleteObject on the Photo Viewer bucket. But the bucket policy explicitly denies s3:DeleteObject for everyone except the Lambda execution role. Mike tries to delete a photo — the bucket policy's explicit deny wins. Mike cannot delete, even though his IAM policy allows it.

This is a powerful security property: a resource owner can always protect their resource, regardless of what IAM policies exist on the other side.

6. Why both policy families exist

Why not just use identity-based policies for everything? Two scenarios where resource policies are essential.

🏦
Cross-account access
Two accounts, both must agree
▼

A developer in a dev account needs to access an S3 bucket in production. The dev account's IAM policy alone isn't sufficient — the production account doesn't know about it. The bucket must explicitly say, via a resource policy, "I allow this role from this other account." Both sides must agree.

Think of it like a bank: to transfer from another person's account, you need permission to initiate, and the other account must authorize it.

🛡
Protecting a resource within the same account
Resource policies as a defensive boundary
▼

Even within one account, you might want to ensure only the Lambda execution role can read objects from the Photo Viewer S3 bucket — not any developer, regardless of what IAM policies get attached in the future. A bucket policy with an explicit deny for all principals except Lambda ensures this. The explicit deny wins over any IAM policy, providing a defensive boundary at the resource level.

What's next — KMS key policies

Next, you'll see a service where the resource-based policy isn't just optional — it's required. KMS key policies are resource policies on encryption keys, but unlike S3, KMS won't even evaluate your IAM policies unless the key policy explicitly enables it. The key policy is the root of trust — even a compromised IAM admin can't decrypt data if they're not in the key policy.
