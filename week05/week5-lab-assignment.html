Week 5 Lab — Serverless Backend

CS 55D: Security in Amazon Web Services  ·  Foothill College  ·  100 pts

Objective: Replace the EC2 and ALB backend from Week 4 with AWS Lambda and API Gateway. Add AWS WAF to protect the /photos endpoint. By the end of this lab, the Photo Viewer backend is fully serverless — no servers to patch, no ALB to misconfigure, end-to-end HTTPS, and WAF rate limiting at the edge.

Browser → WAF/CloudFront → API Gateway → Lambda → DynamoDB ↘ S3 (static files via OAC — unchanged)
WAF runs at the CloudFront edge POP, evaluating requests before CloudFront routes to any origin. A WAF-blocked request never reaches API Gateway or Lambda.

Pre-flight checklist

Before building anything, run the pre-flight script from the course repo to verify your Week 4 environment is in the correct state. Open CloudShell (top nav in the AWS console) and run:

git clone https://github.com/chalasanisree-courses/aws-security-course.git 2>/dev/null || \
  git -C aws-security-course pull
bash aws-security-course/photoviewer/week05/week5-preflight.sh
The script checks five things: EC2 and ALB are gone, DynamoDB table exists with 5 items (creates and seeds automatically if missing), S3 bucket has photo files, and CloudFront distribution is found. It prints your CloudFront domain name — keep that handy. Address any warnings before proceeding.
Files for this lab: Get all files from the course GitHub repository → photoviewer/week05

Part 1 — Clean Up Week 4 Infrastructure

Step 1Delete ALB and EC2

The ALB and EC2 are no longer needed — Lambda replaces them this week. Remove them now before building the new backend.

  1. Delete ALB: EC2 → Load Balancers → select photoviewer-alb → Actions → Delete load balancer → confirm
  2. Terminate EC2: EC2 → Instances → select photoviewer-ec2 → Instance state → Terminate instance → confirm
  3. Delete target group: EC2 → Target Groups → select photoviewer-tg → Actions → Delete
Keep the VPC, DynamoDB table, S3 bucket, CloudFront distribution, and IAM roles — all still needed. The EC2 IAM role (photoviewer-ec2-role) can be kept for reference or deleted.

Part 2 — Lambda Function

Step 2Create the Lambda function

Go to Lambda → Create function → Author from scratch:

  • Function name: photoviewer-lambda
  • Runtime: Python 3.12
  • Architecture: x86_64
  • Execution role: Create a new role with basic Lambda permissions
  • Click Create function
AWS creates the function and an IAM role named photoviewer-lambda-role-XXXXXXXX. The auto-created role includes CloudWatch Logs permissions only — you will add DynamoDB access in the next step.
Step 3Add DynamoDB permission to the execution role

Go to Configuration tab → Permissions → click the role name to open it in IAM.

Click Add permissions → Create inline policy → JSON tab and paste:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["dynamodb:Scan"],
    "Resource": "arn:aws:dynamodb:us-east-1:[your-account-id]:table/photoviewer-photos"
  }]
}

Policy name: photoviewer-dynamodb-read → Create policy

Verify the role now shows two policies:

  • AWSLambdaBasicExecutionRole — CloudWatch Logs (auto-created)
  • photoviewer-dynamodb-read — DynamoDB Scan on one table
Screenshot: IAM role showing both policies — AWSLambdaBasicExecutionRole and photoviewer-dynamodb-read — with the DynamoDB policy expanded to show the Scan action on the correct table ARN
Step 4Deploy lambda_function.py

Go back to your Lambda function → Code tab. You will see a default lambda_function.py with a placeholder. Replace the entire contents with the code from the Week 5 GitHub repo.

Click Deploy to save and activate the new code.

The function uses Attr('is_public').eq(True) to filter the DynamoDB scan — the same logic as app.py in Week 4 but without Flask, ports, or a server process. No packages need to be installed — boto3 is provided by the Lambda runtime automatically.
Step 5Test the Lambda function in isolation

Go to Test tab → Create new test event:

  • Event name: test-photos
  • Template: leave as hello-world — the event body doesn't matter for this function
  • Click Test

The execution result should show:

  • Status code: 200
  • Body: a JSON array of 5 photo objects from DynamoDB
What this test actually does: Clicking Test sends a synthetic event directly to the function — bypassing API Gateway, WAF, and CloudFront entirely. It verifies three things: the function code runs without errors, the execution role can call dynamodb:Scan on the correct table, and the table contains the 5 seeded items. This is a useful early sanity check — if something is wrong with the permissions or the function code, you catch it here rather than debugging through multiple layers later.

Why the template doesn't matter here: When API Gateway invokes Lambda, it passes the HTTP request as a JSON event object — method, path, headers, query parameters, body. This function ignores the event entirely and just calls DynamoDB. But if the function used request data — for example, filtering photos by a query parameter like ?owner=mary, or reading a JWT from the Authorization header (which Week 6 will add) — the test event template would matter. You'd need to construct a mock event with the correct structure so the function has the data it expects.
If you see an error: Check the execution role has dynamodb:Scan on the correct table ARN with your account ID. Check that the DynamoDB table photoviewer-photos exists in us-east-1.
Screenshot: Lambda test result showing status 200 and the JSON array of photos in the response body
✓ CloudShell verify: Confirm DynamoDB has 5 items: 
aws dynamodb scan --region us-east-1 --table-name photoviewer-photos --select COUNT
Expected: "Count": 5

Part 3 — API Gateway + Lambda Authorizer

Step 6Create HTTP API with Lambda integration

Go to API Gateway → Create API → HTTP API → Build:

  • Click Add integration → select Lambda → select photoviewer-lambda
  • API name: photoviewer-api
  • Click Next

On the Configure routes screen:

  • Method: GET — Resource path: /photos — Integration target: photoviewer-lambda
  • Click Next

On the Define stages screen: leave $default with Auto-deploy enabled → Next → Create.

To find the Invoke URL: go to Deploy → Stages in the left nav → click $default. The Invoke URL is displayed at the top — it looks like https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com. Copy the hostname only (no https://) — you will need it for the CloudFront origin in Step 10.

Screenshot: API Gateway Stages page showing the $default stage and Invoke URL
Step 7Create the Lambda authorizer function

The authorizer is a separate Lambda function that API Gateway calls before routing to photoviewer-lambda. It checks for a secret header that CloudFront will add to every origin request.

Go to Lambda → Create function → Author from scratch:

  • Function name: photoviewer-authorizer
  • Runtime: Python 3.12
  • Execution role: Create a new role with basic Lambda permissions
  • Click Create function

In the Code tab, replace the default code with:

import os

SECRET = os.environ['ORIGIN_SECRET']

def lambda_handler(event, context):
    token = event.get('headers', {}).get('x-origin-verify', '')
    return {'isAuthorized': token == SECRET}
Click Deploy after pasting the code. The function will not update until you click Deploy — leaving the default hello-world code in place will cause all requests to fail.

Go to Configuration tab → Environment variables → Edit → Add environment variable:

  • Key: ORIGIN_SECRET
  • Value: generate a random secret — open CloudShell and run python3 -c "import secrets; print(secrets.token_hex(32))" — paste the output here

Click Save. Copy the secret value — you will need it again in Step 10 when configuring CloudFront.

Keep this secret safe. Anyone who knows this value can call the API directly by adding the header. Do not commit it to GitHub.
Screenshot: Lambda authorizer function showing the environment variable configured
Step 8Attach the authorizer to the API Gateway route

Go to API Gateway → photoviewer-api → Authorization in the left nav:

  • Click Manage authorizers → Create
  • Authorizer type: Lambda
  • Name: photoviewer-cf-authorizer
  • Lambda function: select photoviewer-authorizer
  • Payload format version: 2.0
  • Response mode: Simple
  • Identity source: clear the default value and enter $request.header.x-origin-verify — this tells API Gateway which header to use when deciding whether to invoke the authorizer
  • Authorizer cache duration: 0
  • Click Create

Now attach it to the route. Go to Attach authorizers to routes tab:

  • Select GET /photos → click Attach authorizer → select photoviewer-cf-authorizer → Attach authorizer
The identity source tells API Gateway which header to inspect. If that header is missing from the request, API Gateway returns 401 immediately without even invoking the authorizer function. Setting it to $request.header.x-origin-verify ensures API Gateway invokes your authorizer to check the secret — not the default Authorization header.
Screenshot: Authorization page showing photoviewer-cf-authorizer attached to GET /photos with identity source set to $request.header.x-origin-verify
Step 9Verify the authorizer is enforced

Open a new browser tab and navigate directly to your API Gateway invoke URL with the /photos path:

https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos

You should see {"message":"Unauthorized"} — the Lambda authorizer ran, found no x-origin-verify header, and blocked the request. The main Lambda function was never invoked.

✓ CloudShell verify: Confirm the authorizer blocks requests without the header, and passes with it: 
# Should return Unauthorized
curl -s https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos

# Should return 5 photos
curl -s https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos \
  -H "x-origin-verify: YOUR_SECRET"
If the second command returns {"message":"Unauthorized"}, the secret doesn't match — recheck the ORIGIN_SECRET environment variable and that you clicked Deploy after updating the code.
Screenshot: Browser showing {"message":"Unauthorized"} when accessing the API Gateway URL directly

Part 4 — Update CloudFront

Step 10Add API Gateway as a CloudFront origin with secret header

Go to CloudFront → your distribution → Origins tab → Create origin:

  • Origin domain: type your API Gateway hostname — XXXXXXXXXX.execute-api.us-east-1.amazonaws.com (hostname only, no https://, no path). You can select it from the dropdown if it appears.
  • Protocol: HTTPS only
  • Origin name: photoviewer-apigw-origin

Scroll down to Add custom header:

  • Header name: x-origin-verify
  • Value: paste the secret you generated in Step 7

Click Create origin.

Why the custom header is needed: CloudFront adds x-origin-verify to every request it sends to the API Gateway origin. The Lambda authorizer checks for this header — requests arriving directly at the API Gateway URL without it are rejected.
Step 11Update the /photos cache behavior

Go to Behaviors tab. If a /photos behavior already exists from Week 4, click it → Edit. If it does not exist, click Create behavior and set the path pattern to /photos.

In either case, set:

  • Origin and origin groups: set to photoviewer-apigw-origin
  • Viewer protocol policy: Redirect HTTP to HTTPS
  • Cache policy: CachingDisabled
  • Origin request policy: AllViewerExceptHostHeader
Why AllViewerExceptHostHeader is required: By default CloudFront forwards the viewer's Host header (your CloudFront domain) to the origin. API Gateway uses the Host header to identify which API to serve — if it receives the CloudFront domain instead of its own hostname, it returns 403. This policy tells CloudFront to forward all headers except Host, so API Gateway receives its own hostname and routes correctly.

Click Save changes.

Go to Invalidations tab → Create invalidation → path: /* → Create invalidation. Wait for status: Completed.

✓ CloudShell verify: Once the distribution shows Deployed, test the full path through CloudFront: 
curl -s https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net/photos
Expected: JSON array of 5 photos. If you get 403, the most likely cause is the AllViewerExceptHostHeader origin request policy is not set — go back and verify Step 11.
Screenshot: Behavior settings showing CachingDisabled and AllViewerExceptHostHeader

Part 5 — WAF

Step 13Create WAF Web ACL
Region matters: WAF for CloudFront must be created in us-east-1 (N. Virginia). Verify the region selector in the top right of the AWS console shows N. Virginia before proceeding. If you create WAF in another region, it will not be available to associate with CloudFront.

Go to WAF & Shield → Web ACLs → Create web ACL:

  • Resource type: Amazon CloudFront distributions
  • Name: photoviewer-waf
  • Associated AWS resources: click Add AWS resources → select your CloudFront distribution → Add
  • Click Next
Step 14Add rate-based rule

On the Add rules and rule groups screen:

  • Click Add rules → Add my own rules and rule groups → Rule builder
  • Rule type: Rate-based rule
  • Name: photos-rate-limit
  • Rate limit: 100
  • Evaluation window: 5 minutes
  • Scope of inspection: Only consider requests that match the criteria below
  • Criteria: URI path → starts with → /photos
  • Action: Block
  • Click Add rule

On the Set rule priority screen: leave the default order → Next.

On Configure metrics: leave defaults → Next.

On Review and create: verify the rule and associated CloudFront distribution → Create web ACL.

A rate of 100 requests per 5 minutes is appropriate for a lab. In production you would set this based on expected legitimate traffic patterns — typically 1,000–10,000 per 5 minutes for a public API.

Troubleshooting — CloudShell debug commands

If something isn't working, run these commands in CloudShell in order. Each one isolates a specific layer — find where the chain breaks and fix that layer before moving on.

Check 1Lambda + DynamoDB (bypasses everything else)

Tests that the Lambda function code runs and DynamoDB permissions are correct. API Gateway, authorizer, and CloudFront are not involved.

Use the Lambda console Test tab with a hello-world event. Expected result: status 200 with a JSON array of 5 photos.

If this fails: check the execution role has dynamodb:Scan on the correct table ARN, and that the DynamoDB table exists with 5 items. Run the pre-flight script to reseed if needed.

Check 2API Gateway + Lambda (no authorizer)

Tests that API Gateway routes correctly to Lambda. Temporarily detach the authorizer first.

curl -s https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos

Expected: JSON array of 5 photos. If this fails with 403, check that the Host header isn't the issue:

curl -s https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos \
  -H "Host: XXXXXXXXXX.execute-api.us-east-1.amazonaws.com"

If you get Forbidden with a Host header mismatch, your CloudFront behavior is missing the AllViewerExceptHostHeader origin request policy — see Step 11.

Check 3Lambda authorizer (with correct header)

Re-attach the authorizer, then test that it passes with the correct header:

curl -s https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos \
  -H "x-origin-verify: YOUR_SECRET"

Expected: JSON array of 5 photos. If this fails with {"message":"Unauthorized"}, the authorizer is rejecting the request — check that the ORIGIN_SECRET environment variable in the authorizer Lambda matches the value you're passing, and that you clicked Deploy after updating the code.

Also verify the identity source is $request.header.x-origin-verify — not the default $request.header.Authorization.

Check 4CloudFront Host header (common failure point)

Tests whether CloudFront is forwarding the wrong Host header to API Gateway. This is the most common failure mode when connecting CloudFront to API Gateway:

curl -s https://XXXXXXXXXX.execute-api.us-east-1.amazonaws.com/photos \
  -H "Host: YOUR_CLOUDFRONT_DOMAIN.cloudfront.net"

Expected: Forbidden — this confirms that a mismatched Host header causes 403. The fix is to set AllViewerExceptHostHeader as the origin request policy on the /photos behavior in CloudFront (Step 11).

Check 5Full end-to-end through CloudFront

Tests the complete path: browser → CloudFront → authorizer → Lambda → DynamoDB.

curl -s https://YOUR_CLOUDFRONT_DOMAIN.cloudfront.net/photos

Expected: JSON array of 5 photos. If this fails but Check 3 passes, the issue is between CloudFront and API Gateway — verify the /photos behavior origin request policy is set to AllViewerExceptHostHeader and the custom header x-origin-verify is configured on the origin.

After any CloudFront change, always run an invalidation (/*) and wait for Deployed status before retesting.

If the DynamoDB table was deleted or is empty, run this to recreate and reseed it:

Reflection

Answer all three questions in 2–3 sentences each.

Question 1

In Week 4, the ALB security group allowed inbound HTTP on port 80 from 0.0.0.0/0 — any IP could reach it directly, bypassing CloudFront entirely. In Week 5, a Lambda authorizer checks for a secret header that only CloudFront adds to origin requests. Explain why this is more secure than the open ALB security group, and what the remaining weakness of the secret header approach is compared to an IAM-enforced mechanism like aws:SourceArn.

Question 2

Week 4 required a NAT Gateway so EC2 could download packages from the internet during bootstrap. Week 5 has no NAT Gateway and no package installation step. Explain why Lambda eliminates the need for a NAT Gateway and what security benefit this provides — specifically in terms of supply chain risk.

Question 3

The WAF rate-based rule and the Lambda authorizer both protect the /photos endpoint, but they protect against different threats. Explain what each one does and why both are necessary — what does WAF stop that the Lambda authorizer does not, and vice versa?
