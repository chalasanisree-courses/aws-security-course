Week 10 Lab — Vulnerability Assessment, Configuration Management & Performance Monitoring

CS 55D: Security in Amazon Web Services  ·  Foothill College  ·  100 pts

Objective: The Photo Viewer has been built and secured over nine weeks — encryption, access control, identity management, key policies. But how would you know if something breaks, drifts from the intended baseline, or has a known vulnerability — before customers or attackers discover it? Set up CloudWatch alarms for operational monitoring, AWS Config rules for security baseline enforcement, Inspector for vulnerability scanning, and Trusted Advisor for account-level health checks.

What changes this week: No user-facing changes to the Photo Viewer. All changes are on the monitoring and compliance side — visibility into how the application is performing and whether its security configuration has drifted from the intended baseline.

Pre-flight checklist

Run the pre-flight script from CloudShell before starting:

cd ~
git -C aws-security-course pull
bash aws-security-course/photoviewer/week10/week10-preflight.sh

The script verifies your Week 9 environment is intact: both KMS keys, S3/DynamoDB encryption, Secrets Manager encryption, Lambda function, CloudFront distribution, Identity Center, and Organizations. It also confirms the SNS topic from Week 1 exists (needed for alarm notifications). Address any errors before proceeding.

Part 1 CloudWatch — operational monitoring

Customers are reporting that the Photo Viewer is slow and sometimes fails. You have no visibility into Lambda performance — you would only know about problems by checking the console manually. CloudWatch alarms fix this by monitoring metrics continuously and notifying you when thresholds are breached.

Step 1Find Lambda metrics in CloudWatch

Go to CloudWatch → Metrics → All metrics → Lambda → By Function Name. Find photoviewer-lambda. Select the Errors and Duration metrics. Observe the graphs — there are no alarms configured. You would only notice problems by opening this dashboard.

CloudWatch metrics dashboard showing photoviewer-lambda Errors and Duration metrics with no alarms configured
Step 2Create an error alarm

Go to CloudWatch → Alarms → Create alarm.

  • Select metric: Lambda → By Function Name → photoviewer-lambda → Errors
  • Statistic: Sum
  • Period: 5 minutes
  • Threshold: Static → Greater/Equal → 1
  • Notification: Select the SNS topic from Week 1 (the one used for billing alarms)
  • Alarm name: photoviewer-lambda-errors

This alarm fires if the Lambda function produces one or more errors in any 5-minute window. The SNS topic sends you an email — the same notification channel you have been using since Week 1.

Step 3Create a duration alarm

Create a second alarm:

  • Select metric: Lambda → By Function Name → photoviewer-lambda → Duration
  • Statistic: Average
  • Period: 5 minutes
  • Threshold: Static → Greater → 2000 (2 seconds in milliseconds)
  • Notification: Same SNS topic
  • Alarm name: photoviewer-lambda-duration

The Lambda timeout is 3 seconds — if it takes longer than that, the invocation is killed and the error alarm fires. Setting the duration threshold at 2 seconds gives you an early warning: something is degrading, investigate before it starts timing out.

CloudWatch Alarms console showing both alarms in OK state
Step 4Break the Lambda — trigger the error alarm

Go to Lambda → Functions → photoviewer-lambda → Configuration → Environment variables → Edit. Change the PHOTO_BUCKET value to wrong-bucket-name. Click Save.

Now load the Photo Viewer in your browser. The page itself loads (HTML/CSS/JS from CloudFront), but the photo list fails — Lambda tries to generate presigned URLs for a bucket that does not exist.

Wait a few minutes. Go to CloudWatch → Alarms. The photoviewer-lambda-errors alarm should transition to ALARM state. Check your email — the SNS notification should arrive.

✓ Verify

The error alarm is in ALARM state. You received an email notification. In production, this would wake someone up before customers start complaining.

CloudWatch alarm in ALARM state (red) for photoviewer-lambda-errors
Email notification from SNS showing the alarm details
Step 5Fix it — alarm returns to OK

Go back to Lambda → Environment variables → Edit. Change PHOTO_BUCKET back to the correct bucket name. Click Save.

Load the Photo Viewer — photos appear again. Wait for the next evaluation period (~5 minutes). The alarm transitions back to OK.

✓ Verify

Photo Viewer works. Alarm is back in OK state. The full cycle: break → alarm → diagnose → fix → alarm clears.

CloudWatch alarm back in OK state (green) after fixing the environment variable
Part 2 AWS Config — detecting drift

A junior developer was troubleshooting a photo upload issue and disabled S3 default encryption to rule out KMS as the cause. They forgot to re-enable it. The Photo Viewer still works — but every new photo is now stored unencrypted. Nothing in CloudWatch would catch this. CloudWatch monitors performance; Config monitors configuration.

Step 6Enable AWS Config

Go to AWS Config → Get started (or Settings if already visited).

  • Recording strategy: All resource types (or select specific types to reduce cost)
  • AWS Config role: let Config create a service-linked role
  • Delivery method: Create a new S3 bucket (Config stores configuration history snapshots here)

Click Confirm. Config begins recording resource configurations across the account.

Cost note: AWS Config charges per configuration item recorded (~$0.003 each) plus the S3 storage for history. With a small lab account, expect $1–2/month. Keep Config running through Week 11 — it is needed for Security Hub.

Step 7Add managed rules

Go to AWS Config → Rules → Add rule. Add the following four managed rules one at a time:

Rule nameWhat it checks
s3-default-encryption-kmsS3 buckets are encrypted with KMS (not just default SSE-S3)
s3-bucket-public-read-prohibitedS3 buckets do not allow public read access
cloud-trail-encryption-enabledCloudTrail trails are encrypted with KMS
iam-root-access-key-checkRoot account does not have active access keys

For each rule, accept the default parameters and click Save.

Why s3-default-encryption-kms instead of s3-bucket-server-side-encryption-enabled? Since January 2023, S3 encrypts all objects with SSE-S3 by default — you cannot disable encryption. The older rule checks whether any encryption is enabled, which is now always true. The KMS-specific rule checks whether the bucket uses a KMS key you control — the standard you set up in Week 8.

Step 8Wait for evaluation and screenshot

Config evaluates rules against current resource configurations. This can take a few minutes. Go to AWS Config → Rules and wait until all four rules show a compliance status.

If your environment is correctly configured from Weeks 1–9, all rules should show Compliant. If cloud-trail-encryption-enabled shows Non-compliant, it means your CloudTrail trail is using default encryption rather than a KMS key — this is a valid finding.

AWS Config Rules dashboard showing all four rules with compliance status
Step 9Break it — downgrade S3 encryption

Go to S3 → your Photo Viewer bucket → Properties → Default encryption → Edit. Change the encryption type from SSE-KMS to SSE-S3. Click Save changes.

The Photo Viewer still works — objects are still encrypted, just with Amazon’s S3-managed key instead of your customer-managed KMS key. No errors, no outages, no visible change. But you’ve lost control of the encryption key — you can no longer audit key usage in CloudTrail, rotate on your own schedule, or revoke access by disabling the key. This is exactly the kind of silent drift that Config catches.

Step 10Observe Config catch the drift

Go to AWS Config → Rules → s3-default-encryption-kms. Click Re-evaluate (or wait 5–10 minutes for automatic re-evaluation).

The rule transitions to Non-compliant. Click into the rule to see which resource is non-compliant — your Photo Viewer bucket.

✓ Verify

Config detected the encryption drift. Without Config, this change would be invisible — the app works fine, no errors, no alarms. Only Config knows the configuration has changed.

AWS Config showing s3-default-encryption-kms as Non-compliant with the Photo Viewer bucket listed
Step 11Fix it — restore encryption

Go back to S3 → bucket → Properties → Default encryption → Edit. Change back to SSE-KMS and select photoviewer-data-key. Click Save changes.

Return to Config and re-evaluate the rule. It should return to Compliant.

AWS Config showing the rule back to Compliant after restoring KMS encryption
Part 3 Inspector — vulnerability scanning

The Photo Viewer Lambda function uses several Python packages (boto3, botocore). Each package has dependencies. Any one of them could have a published CVE — a known vulnerability cataloged by the NIST National Vulnerability Database. Inspector scans Lambda functions and reports any findings.

Step 12Enable Inspector

Go to Amazon Inspector → Get Started → Enable Inspector.

On the activation page, ensure Lambda standard scanning is selected. You can also enable EC2 scanning, but since we removed EC2 in Week 5, Lambda scanning is the relevant option.

Inspector starts a 15-day free trial. It automatically discovers all Lambda functions in the account and begins scanning their deployment packages for known CVEs.

Step 13Review findings

Wait a few minutes for the initial scan to complete. Go to Inspector → Findings → By Lambda function. Look for photoviewer-lambda and photoviewer-authorizer.

Review any findings. Each finding includes the CVE ID, severity (Critical / High / Medium / Low), the affected package and version, and a link to the NIST NVD entry.

A clean scan (no findings) is a valid and good result — document it. If there are findings, note the CVE ID and severity. In production, you would update the affected package.

✓ Verify

Inspector has scanned photoviewer-lambda. You can see either findings with CVE details or a clean scan result. Either outcome demonstrates that you now have automated vulnerability visibility.

Inspector findings for photoviewer-lambda — showing CVE details or a clean scan
Part 4 Trusted Advisor — account health check

Trusted Advisor checks your account against AWS best practices across five categories: cost optimization, performance, security, fault tolerance, and service limits. Think of it as a doctor's annual physical for your AWS account.

Step 14Review security checks

Go to AWS Trusted Advisor. Click the Security tab.

Review the checks. Common findings in a lab account include:

  • MFA on Root Account — should be green if you enabled MFA in Week 1
  • Security Groups — Specific Ports Unrestricted — may flag if any security groups are too permissive
  • S3 Bucket Permissions — should be green after your bucket policy work
  • IAM Use — should be green since you have created IAM users

Note: Some Trusted Advisor checks are only available with a Business or Enterprise Support plan. Free-tier accounts see a subset of checks — that is expected.

Trusted Advisor Security tab showing check results — green (ok), yellow (warning), and red (action recommended)
Step 15Compare Trusted Advisor with Config

Trusted Advisor and Config both check security posture, but they work differently:

Trusted AdvisorAWS Config
ScopeAccount-wide, fixed checksPer-resource, customizable rules
FrequencyOn-demand or weeklyContinuous — detects changes in near real-time
CustomizationCannot add custom checksCan add custom rules with Lambda
RemediationRecommendations onlyCan trigger automated remediation via EventBridge

Both are useful. Trusted Advisor is a quick health check. Config is continuous compliance monitoring. In Week 11, Config findings will flow into Security Hub alongside findings from GuardDuty, Inspector, and Macie.

Cleanup

All three services from this lab are needed in Week 11. Do not disable them yet.

  • Keep Inspector running — Week 11 deploys a new Lambda with a deliberately vulnerable dependency. Inspector needs to be active to scan it. Free trial runs for 15 days.
  • Keep AWS Config running — Config findings flow into Security Hub in Week 11. Cost is ~$1–2/month.
  • Keep CloudWatch alarms — no cost for two alarms on Lambda metrics. They provide ongoing monitoring.

Reflection Questions

Question 1

In Step 9, you removed S3 default encryption. The Photo Viewer continued to work normally — no errors, no CloudWatch alarms. Explain why CloudWatch did not catch this change, and why a different tool (Config) was needed.

Question 2

You now have four monitoring and compliance tools running: CloudWatch, Config, Inspector, and Trusted Advisor. For each of the following scenarios, which tool would detect the problem first? Explain your reasoning.

  • (a) A Lambda code deployment introduces a bug that causes every third request to time out.
  • (b) Someone changes the S3 bucket policy to allow public read access.
  • (c) A new CVE is published for a Python package used by the Lambda function.
