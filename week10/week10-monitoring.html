Vulnerability Assessment, Configuration Management & Performance Monitoring

This course builds a Photo Viewer application across twelve weeks, adding one AWS security layer per week. This page addresses three operational concerns: are our dependencies free of known vulnerabilities? Has our security configuration drifted? Is the application performing well?

Learning objectives

  • Place the course within the seven pillars of enterprise application security and the NIST Cybersecurity Framework
  • Distinguish between building securely (systems and architecture) and running securely (people and operations)
  • Identify the three operational concerns addressed this week: vulnerability assessment, configuration management, and performance monitoring
  • Explain how Inspector performs vulnerability assessment by scanning Lambda deployment packages for known CVEs
  • Explain how AWS Config performs configuration management by detecting security baseline drift
  • Explain how CloudWatch performs performance monitoring via metrics, alarms, and SNS notifications
  • Distinguish between CloudTrail (who did what), CloudWatch (how is it performing), and Config (what does it look like now)
  • Describe vulnerability assessment vocabulary: CVE, CVSS, NVD, CISA KEV, CIS Benchmarks

1. Where we left off

The Photo Viewer is well-secured. S3 objects encrypted with customer-managed KMS keys. Identity Center enforcing separation of duties between Tom and Jerry. Cognito groups driving RBAC. Presigned URLs controlling object-level access. Two problems remain from the prior concept page:

Uploaded files are still not scanned for malicious content
▼

Encryption protects data at rest from unauthorized access — it does not inspect data for harmful content. A user could upload a file containing credit card numbers, or an image that is actually a disguised executable. Macie detects PII in S3 objects. GuardDuty Malware Protection scans uploads. These are detection services — a different layer from encryption and access control. Not addressed this week — coming in the next concept page.

No automated monitoring of security posture
▼

Security controls have been built manually — encryption, key policies, permission sets, role-based access. There is no mechanism to detect if any of it has drifted, degraded, or developed a known vulnerability. The application could be broken, misconfigured, or running vulnerable code — and nobody would know until customers complain or an attacker exploits it. This is what we fix this week.

The second problem breaks down into three distinct visibility gaps:

GapWhat could go wrongWould you know?
No vulnerability assessmentA dependency in the Lambda deployment package has a published CVENo — until it is exploited
No configuration managementSomeone downgrades S3 encryption from KMS to SSE-S3 while troubleshooting and forgets to restore itNo — the app keeps working
No performance monitoringLambda starts timing out or throwing errorsOnly when customers complain

Security without visibility is security by hope.

2. The big picture — seven pillars of application security

Every enterprise application — whether it runs on AWS, Azure, on-premises, or a mix — needs the same seven security pillars. This is not an AWS framework. It is how the industry thinks about application security, captured formally in the NIST Cybersecurity Framework (CSF) 2.0 — a six-function lifecycle (Govern, Identify, Protect, Detect, Respond, Recover) used by organizations worldwide to manage cybersecurity risk. These are independent failure modes. An application can pass vulnerability assessment but perform badly (a code bug). 4. Key concepts

The assurance panels above explain the AWS services. The concepts below go deeper — distinguishing services that are easy to confuse, and introducing the industry vocabulary for vulnerability management.

Configuration Management & Performance Monitoring — three services, three questions

CloudTrail vs CloudWatch vs Config

These three services sound similar and are easy to confuse. Each answers a fundamentally different question:

ServiceQuestionRecordsExample
CloudTrailWho did what?API calls — every action taken by every principalPutBucketEncryption called by user tom at 14:32 UTC
CloudWatchHow is it performing?Metrics — numerical measurements over timeLambda Errors = 3 in the last 5 minutes
ConfigWhat does it look like now?Resource configuration stateS3 bucket encryption changed from SSE-KMS to SSE-S3

A single incident touches all three. CloudTrail tells you who changed the encryption setting. Config tells you the bucket is now non-compliant. CloudWatch tells you the application is throwing errors. Three services, three perspectives — who, what state, and what impact.

Vulnerability Assessment — industry vocabulary

CVE, NVD, CISA KEV, CIS Benchmarks

The security industry maintains several interconnected databases for tracking and communicating about vulnerabilities. These are not AWS-specific — they apply to any software, on any platform.

CVE — Common Vulnerabilities and Exposures

A unique identifier for a specific vulnerability, assigned by MITRE. Example: CVE-2021-44228 (the Log4Shell vulnerability in Apache Log4j). A CVE is a name, not a score — it identifies the vulnerability but does not rate its severity.

NVD — National Vulnerability Database

Maintained by NIST. Takes each CVE and adds a severity score (CVSS), affected software versions, and references. CVSS scores range from 0.0 to 10.0: Low (0.1–3.9), Medium (4.0–6.9), High (7.0–8.9), Critical (9.0–10.0). Inspector findings link directly to NVD entries.

CISA KEV — Known Exploited Vulnerabilities

CISA (Cybersecurity and Infrastructure Security Agency) maintains a catalog of CVEs that are known to be actively exploited in the wild. Federal agencies are required to patch KEV entries within specific timelines. Not every CVE is a KEV — only those with confirmed exploitation.

CIS Benchmarks

The Center for Internet Security publishes configuration benchmarks — prescriptive guidance for securely configuring specific platforms (AWS, Linux, Windows, databases). These are different from vulnerability scans — they check configuration, not software versions.

5. What’s still missing

Two pillars remain on the running side of the diagram.

Uploaded files are still not scanned for malicious content
▼

This issue was identified in the prior concept page and is not solved this week. Encryption protects confidentiality; it does not classify or inspect content. A user could upload a file containing credit card numbers or a disguised executable. Macie detects PII patterns in S3 objects. GuardDuty Malware Protection scans for malware. Both are detection services addressed in the next concept page.

No detection of adversarial behavior
▼

This week monitors configuration drift, performance degradation, and known vulnerabilities — all inward-facing concerns. None of these tools detect an attacker. If someone exfiltrates IAM credentials and makes API calls from an unfamiliar IP, CloudWatch won’t flag it (no errors), Config won’t flag it (no configuration changed), and Inspector won’t flag it (no vulnerability involved). GuardDuty detects adversarial behavior by analyzing VPC flow logs, DNS logs, and CloudTrail events for patterns that indicate credential compromise, reconnaissance, or data exfiltration.
